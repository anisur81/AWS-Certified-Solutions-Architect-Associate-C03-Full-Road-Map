# 1.1.2: AWS federated access and identity services (for example, IAM, AWS IAM Identity Center)

## What is IAM Identity Center?
<a name="what-is"></a>

AWS IAM Identity Center is the AWS solution for connecting your workforce users to AWS managed applications such as Kiro and Amazon Quick, and other AWS resources. You can connect your existing identity provider and synchronize users and groups from your directory, or create and manage your users directly in IAM Identity Center. You can then use IAM Identity Center for either or both of the following:
+ User access to applications
+ User access to AWS accounts

## Why use IAM Identity Center?
<a name="features"></a>

IAM Identity Center streamlines and simplifies workforce user access to applications or AWS accounts, or both, through the following key capabilities.

**Integration with AWS managed applications**  
[AWS managed applications](awsapps.md) such as Kiro and Amazon Redshift integrate with IAM Identity Center. IAM Identity Center provides AWS managed applications with a common view of users and groups.

**Trusted identity propagation across applications **  
With trusted identity propagation, AWS managed applications such as Amazon Quick can securely share a user’s identity with other AWS managed applications such as Amazon Redshift and authorize access to AWS resources based on the user’s identity. You can more easily audit user activity because CloudTrail events are logged based on the user and the actions the user initiated. This makes it easier to understand who accessed what. 

**One point of federation to simplify user access to AWS**  
By providing one point of federation, IAM Identity Center reduces the administrative effort required to use multiple AWS managed applications and AWS accounts. 

**Ability to manage workforce access to multiple AWS accounts**  
IAM Identity Center gives you options to manage centrally your workforce access to AWS accounts:  

**Two instance types**  
IAM Identity Center supports two types of instances: *organization instances* and *account instances*. An organization instance is the best practice. It's the only instance that enables you to manage access to AWS accounts and it is recommended for all production use of applications. An organization instance is deployed in the AWS Organizations management account and gives you a single point from which to manage user access across AWS.   
Account instances are bound to the AWS account in which they are enabled. Use account instances of IAM Identity Center only to support isolated deployments of select AWS managed applications. For more information, see [Organization and account instances of IAM Identity Center](identity-center-instances.md).

**User-friendly web portal access for your users**  
The AWS access portal is a user-friendly web portal that provides your users with seamless access to all their assigned applications, AWS accounts, or both.

**Multi-Region access to AWS accounts and applications**  
When you replicate your IAM Identity Center instance to additional Regions, your workforce can access their assigned AWS accounts and applications through all enabled Regions, and they can deploy AWS managed applications in each enabled Region.


### In AWS, IAM determines:
- Who can access AWS resources?
- What actions can they perform?
- Which resources can they access?
- Under what conditions is access allowed?


## Understanding Permission Sets

### What is a Permission Set?

A permission set is a collection of permissions that determines what a user or group can do in an assigned AWS account through AWS IAM Identity Center.

Think of a permission set as a reusable access template.

**Examples:**

| Permission Set | Intended Responsibility |
|---|---|
| AdministratorAccess | Full administrative access |
| ReadOnlyAccess | Read-only access |
| PowerUserAccess | Broad access to AWS services, with restrictions |
| SecurityAudit | Security auditing |
| DeveloperAccess | Defined development permissions |
| DatabaseAdministrator | Defined database administration permissions |

> Note: Some names above are examples of common access profiles. Custom permission sets can also be created.

### How Permission Sets Work

Consider a DevOps Engineer who needs access to two AWS accounts:

- **Development account:** Broad deployment and infrastructure permissions.
- **Production account:** Limited deployment permissions.

You can assign different permission sets to the same user in different accounts.

#### Permission Set Assignment Example

```text
                  IAM Identity Center
                          |
                  DevOps Engineer
                          |
             +------------+------------+
             |                         |
       Development                 Production
             |                         |
      DevOps Permission Set     Limited Deployment
             |                    Permission Set
             |                         |
      Broader Deployment          Restricted Access
          Access
```

## Understanding SAML 2.0

### What is SAML?

SAML stands for **Security Assertion Markup Language**.

It is an open standard used to exchange authentication and authorization-related information between an Identity Provider (IdP) and a Service Provider (SP).

SAML 2.0 is widely used for enterprise Single Sign-On (SSO).

### Main SAML Components

| Component | Meaning |
|---|---|
| Identity Provider (IdP) | Authenticates the user |
| Service Provider (SP) | Provides the service the user wants to access |
| SAML Assertion | Carries information about the authenticated user |
| Metadata | Describes the SAML configuration and endpoints |
| Certificate | Supports verification of signed SAML messages |

### SAML Authentication Flow

```text
              Employee
                  |
                  v
          AWS Access Portal
                  |
                  v
        External Identity Provider
                  |
          User Authentication
                  |
                  v
          SAML Assertion
                  |
                  v
          AWS Sign-in Service
                  |
          Validate Assertion
                  |
                  v
          AWS IAM Identity Center
                  |
                  v
          Authorized AWS Account
```

**Key benefits:**

- Enterprise Single Sign-On.
- Centralized authentication.
- Integration with corporate identity providers.
- Reduced need for separate AWS passwords.

## AWS Security Token Service (STS)

### What is AWS STS?

AWS Security Token Service (STS) is an AWS service that provides temporary security credentials for authorized identities.

Instead of using permanent credentials, applications and federated users can receive temporary credentials.

These credentials typically include:

- Access key ID.
- Secret access key.
- Session token.
- Expiration time.

### Why Do We Need STS?

Consider an application running on an EC2 instance that needs access to Amazon S3.

One approach would be to store long-term AWS access keys inside the application.

That introduces security risks:

- Keys may be exposed.
- Keys may be accidentally committed to source control.
- Credential rotation becomes difficult.
- Compromised keys may be used for unauthorized access.

**Recommended approach:**

Use an IAM role associated with the EC2 instance.

The instance receives temporary credentials through the AWS role mechanism.

### Important STS Operations

| STS Operation | Purpose |
|---|---|
| AssumeRole | Obtain temporary credentials for an IAM role |
| AssumeRoleWithSAML | Obtain credentials through SAML federation |
| AssumeRoleWithWebIdentity | Obtain credentials through supported web identity federation |
| GetSessionToken | Obtain temporary credentials for an IAM user or root user session |
| GetCallerIdentity | Identify the AWS principal making a request |

**Important distinction:**

AWS STS issues temporary credentials. IAM policies and role trust policies determine what access those credentials can obtain.

## Trust Policy vs. Permission Policy

This is one of the most important AWS IAM concepts.

### Trust Policy

A trust policy determines **who is allowed to assume an IAM role**.

It defines the trusted principal.

Examples:

- Another AWS account.
- An IAM user.
- An AWS service.
- A federated identity provider.

### Permission Policy

A permission policy determines **what the assumed role is allowed to do**.

For example:

- Read S3 objects.
- Start EC2 instances.
- View CloudWatch logs.
- Access specific database resources.

### Real-World Example

A DevOps Engineer belongs to the Development account but needs to access a specific role in the Production account.

- The Production role's trust policy determines whether the Development identity can assume it.
- The role's permissions policy determines what the engineer can do after assuming it.

**Remember:**

- Trust Policy = Who.
- Permission Policy = What.

## IAM vs. IAM Identity Center vs. Federation

This comparison is particularly important for AWS SAA-C03.

| Feature | AWS IAM | IAM Identity Center | Identity Federation |
|---|---|---|---|
| Main Purpose | AWS resource authorization | Central workforce access management | Trust external identities |
| User Management | IAM users and roles | Users and groups from configured identity source | External IdP |
| Multi-Account Access | Possible through roles | Designed for centralized multi-account access | Depends on architecture |
| SSO | Not its primary workforce management function | Yes | Yes, depending on protocol and integration |
| Temporary Credentials | Yes, through roles and STS | Yes | Yes, through federation |
| Typical Use | Resource permissions and workload identities | Employee access across AWS accounts | Corporate or workload identity integration |

### Which Should You Use?

- **IAM:** Define AWS permissions, roles, and policies.
- **IAM Identity Center:** Manage employee access across multiple AWS accounts.
- **Identity Federation:** Connect an external identity system to AWS.
- **STS:** Issue temporary credentials for authorized sessions.

These technologies work together rather than replacing one another.

## AWS IAM Security Best Practices

These principles are important for production environments and the AWS SAA-C03 exam.

| No. | Best Practice | Explanation |
|---|---|---|
| 1 | Use Federation for Workforce Access | Avoid unnecessary individual IAM users. |
| 2 | Enable MFA | Add another authentication factor. |
| 3 | Apply Least Privilege | Grant only required permissions. |
| 4 | Use IAM Roles | Prefer temporary credentials over long-term credentials. |
| 5 | Centralize Workforce Access | Use IAM Identity Center for multi-account environments. |
| 6 | Avoid Root User Access | Reserve root credentials for tasks that require them. |

| 12 | Automate Deprovisioning | Remove access promptly when employees leave. |

## What is Identity Federation?
Identity federation allows users to access AWS resources using identities managed by an external identity provider (IdP), rather than maintaining separate IAM user credentials for every AWS account.

An Identity Provider is a system responsible for managing and verifying user identities.

Examples include:
- Microsoft Entra ID.
- Active Directory Federation Services (AD FS).
- Okta.
- Google Workspace.
- Other compatible enterprise identity providers.
  
### Why Do Organizations Need Federation?
Imagine an international company with:
- 500 employees.
- 20 AWS accounts.
- Multiple development teams.
- Security and compliance teams.
- Centralized employee identity management.
Without federation, administrators may need to manage separate IAM users and credentials across many accounts.

### This creates problems:
- Difficult user lifecycle management.
- Multiple credentials.
- Complex access administration.
- Delayed employee offboarding.
- Increased credential-management risks.
With federation, employees can authenticate using the organization's central identity system and receive access to authorized AWS accounts.

Conceptually:
1. An employee opens the AWS access portal.
2. The employee authenticates with the organization's identity provider.
3. The identity provider verifies the employee's identity.
4. The identity provider provides a trusted authentication assertion or token.
5. AWS validates the federation trust.
6. AWS provides access through an authorized role or IAM Identity Center permission set.
7. The employee accesses only the permitted AWS resources.

## Benefits of Identity Federation

| Benefit | Explanation |
|---|---|
| Centralized Identity | Employees use an organizational identity to access authorized AWS accounts and applications. |
| Reduced Credential Management | Reduces the need to manage separate AWS user credentials for each account. |
| Centralized Offboarding | Employee access can be disabled centrally through the identity management process. |
| MFA Integration | Supports integration with enterprise authentication systems to enforce Multi-Factor Authentication (MFA). |
| Scalability | Supports large organizations and centralized access management across multiple AWS accounts. |
| Better Governance | Access can be assigned and managed according to employee roles and job responsibilities. |


### Federation with IAM Identity Center

For centralized access management of human users, we recommend that you use IAM Identity Center to manage access to your accounts and permissions within those accounts. Users in IAM Identity Center are granted short-term credentials to your AWS resources. You can use Active Directory, an external identity provider (IdP), or an IAM Identity Center directory as the identity source for users and groups to assign access to your AWS resources.

IAM Identity Center supports identity federation with SAML (Security Assertion Markup Language) 2.0 to provide federated single sign-on access for users who are authorized to use applications within the AWS access portal. Users can then single sign-on into services that support SAML, including the AWS Management Console and third-party applications, such as Microsoft 365, SAP Concur, and Salesforce.

### Federation with IAM

While we strongly recommend managing human users in IAM Identity Center, you can enable federated principal access with IAM for human users in short-term, small scale deployments. IAM allows you to use separate SAML 2.0 and Open ID Connect (OIDC) IdPs and use federated principal attributes for access control. With IAM, you can pass user attributes, such as cost center, title, or locale, from your IdPs to AWS, and implement fine-grained access permissions based on these attributes.

A workload is a collection of resources and code that delivers business value, such as an application or backend process. Your workload can require an IAM identity to make requests to AWS services, applications, operational tools, and components. These identities include machines running in your AWS environments, such as Amazon EC2 instances or AWS Lambda functions.
