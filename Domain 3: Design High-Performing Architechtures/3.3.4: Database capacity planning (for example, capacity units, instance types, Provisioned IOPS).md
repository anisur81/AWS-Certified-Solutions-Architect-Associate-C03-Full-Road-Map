# Database capacity planning 

### Capacity Units, Instance Types, and Provisioned IOPS (AWS)

---

## 1. Why capacity planning matters

Capacity planning means choosing how much compute, memory, storage throughput, and I/O a database needs, and how that capacity will change over time. Getting it wrong has two costs:

- **Under-provisioning** causes throttling (DynamoDB), CPU or memory starvation, I/O queueing, and slow queries.
- **Over-provisioning** means you pay for resources you do not use. Provisioned resources are billed whether or not the workload consumes them.

AWS gives you three different "capacity" vocabularies depending on the service, and this topic covers all three:

| Service | Unit you plan in | You choose |
|---|---|---|
| Amazon DynamoDB | Read/Write Capacity Units (RCU/WCU) | Throughput per second |
| Amazon RDS / Aurora provisioned | DB instance class + storage type/IOPS | vCPU, memory, network, I/O |
| Aurora Serverless v2 | Aurora Capacity Units (ACU) | A min–max capacity range |

---

## 2. Capacity units

### 2.1 DynamoDB capacity modes

DynamoDB has two read/write capacity modes: **on-demand** and **provisioned** (the default). The mode controls how you are billed and how you manage capacity, and it can be set at table creation or changed later. Secondary indexes inherit the mode of the base table.

- **On-demand** is pay-per-request. You do not specify expected throughput, and the table adapts to traffic. Usage is measured in *read request units* and *write request units*.
- **Provisioned** requires you to state the reads and writes per second you need. You are billed for the hourly capacity you provision, not for how much you actually consume.

**Switching limits:** a table can move from provisioned to on-demand up to four times in a rolling 24-hour window. Moving from on-demand back to provisioned is allowed at any time.

When a table switches from provisioned to on-demand, DynamoDB makes sure it can sustain at least its previously provisioned (or previously reached) throughput. After a switch back to provisioned, throughput matches the previous peak reached while in on-demand mode.

### 2.2 What one capacity unit means

| Unit | Definition |
|---|---|
| **1 RCU** | One *strongly consistent* read per second, for an item up to **4 KB** |
| **1 RCU (eventually consistent)** | Two reads per second, item up to 4 KB |
| **Transactional read** | Two RCUs per read of an item up to 4 KB |
| **1 WCU** | One write per second, for an item up to **1 KB** |
| **Transactional write** | Two WCUs per write of an item up to 1 KB |

Items larger than the unit size consume additional units, always **rounded up**. Strongly consistent reads use twice the resources of eventually consistent reads, which is why RCUs are defined against strong consistency.

### 2.3 Worked calculations

The AWS documentation uses these two examples; the third and fourth extend the same method.

**Example A, reads.** Item size 3 KB, 80 reads/second, strongly consistent.
- 3 KB ÷ 4 KB = 0.75, rounded up to **1 RCU per item**.
- 1 × 80 = **80 RCU**.

**Example B, writes.** Item size 512 bytes, 100 writes/second.
- 512 B ÷ 1 KB = 0.5, rounded up to **1 WCU per item**.
- 1 × 100 = **100 WCU**.

**Example C, larger item, eventually consistent.** Item size 9 KB, 60 reads/second.
- 9 ÷ 4 = 2.25, rounded up to 3 RCU per strongly consistent read.
- Strongly consistent: 3 × 60 = 180 RCU.
- Eventually consistent: 180 ÷ 2 = **90 RCU**.

**Example D, transactional write.** Item size 2.5 KB, 20 transactional writes/second.
- 2.5 ÷ 1 = 2.5, rounded up to 3 WCU, doubled for transactions = 6 WCU.
- 6 × 20 = **120 WCU**.

**Formula summary**

```
RCU (strong)     = ceil(item_KB / 4) × reads_per_sec
RCU (eventual)   = RCU (strong) / 2
RCU (transact.)  = RCU (strong) × 2
WCU              = ceil(item_KB / 1) × writes_per_sec
WCU (transact.)  = WCU × 2
```

### 2.4 Choosing initial throughput and using auto scaling

When picking initial values, consider item size, expected read and write rates, and read-consistency needs.

**DynamoDB auto scaling** manages provisioned capacity for tables and global secondary indexes. You define:

1. a **minimum** and **maximum** capacity, and
2. a **target utilization** percentage within that range.

Auto scaling raises capacity to absorb sudden traffic increases without throttling, and lowers it afterward. It can be configured from the console, the AWS CLI, or the SDKs. You can also change capacity manually with the `UpdateTable` operation.

### 2.5 Quotas to plan around

Default quotas (all can be raised through a Service Quotas request):

| Scope | Provisioned mode | On-demand mode |
|---|---|---|
| Per table | 40,000 RCU and 40,000 WCU | 40,000 read and 40,000 write request units |
| Per account (provisioned) | 80,000 RCU and 80,000 WCU | Not applicable |

AWS also places a default limit on active **reserved capacity** that an account can purchase. For steady, predictable workloads, reserved capacity lowers the cost of provisioned throughput.

### 2.6 Aurora Capacity Units (ACUs)

Aurora Serverless v2 plans capacity in **ACUs**. Each ACU combines roughly **2 GiB of memory** plus corresponding CPU and networking.

- You set a **minimum and maximum** ACU value per cluster; capacity of each writer or reader scales between them as a floating-point value.
- Capacity ranges from **0 (auto-pause) or 0.5 ACU up to 256 ACUs (about 512 GiB)**, in 0.5 ACU steps. The allowed minimum depends on the Aurora version.
- Instances use the special class `db.serverless`.
- On PostgreSQL-compatible instances, a minimum of 0.5 ACU caps `max_connections` at 2,000. The default connection limit is otherwise derived from the maximum ACU.

**Planning tips**

- The minimum is billed continuously (unless you use 0 ACU with auto-pause), so set it from real baseline needs.
- Memory pressure, such as large buffer pools, many connections, or big sorts, often determines the true floor rather than CPU.
- Treat the maximum as a cost ceiling as well as a performance ceiling.
- Serverless v2 is a good fit for variable or unpredictable workloads. At steady high utilization, provisioned instances (especially reserved) are often cheaper.

## 3. DB instance types (RDS and Aurora)

For provisioned relational databases, the **DB instance class** fixes vCPU, memory, and network bandwidth. A class name such as `db.r7g.large` reads as:

- `db.` prefix for database instances
- `r` is the **family** (workload category)
- `7` is the **generation**
- `g` is the **processor variant** (Graviton; `i` indicates Intel, `d` indicates local NVMe storage)
- `large` is the **size**

### 3.1 Families

| Family | Purpose | Current examples | Typical use |
|---|---|---|---|
| **General purpose (db.m)** | Balanced compute, memory, network | db.m7g, db.m8g (Graviton) | Default for most production databases |
| **Memory-optimized (db.r, db.x, db.z)** | More memory per vCPU | db.r7g, db.r8g, db.r7i | High-concurrency OLTP, large working sets, in-memory caching |
| **Burstable (db.t)** | Baseline CPU with ability to burst | db.t4g, db.t3 | Dev/test, staging, light or spiky workloads |
| **Optimized Reads (db.r6gd, db.r8gd)** | Memory-optimized plus local NVMe SSD | r6gd, r8gd | Scratch space, temporary objects, fast local storage |
| **Compute-optimized (db.c)** | CPU over memory | Limited availability | Specialized Multi-AZ DB cluster deployments |

Key facts from the documentation:

- **db.r8g** (Graviton4) offers larger sizes with up to three times the vCPUs and memory of db.r7g (Graviton3).
- **db.t4g** classes are configured in **Unlimited mode** on RDS, so a database can burst as long as needed (with possible surcharges for sustained high CPU).
- **Optimized Reads** classes provide up to 1.5 TiB of memory and up to 11.4 TB of direct-attached NVMe SSD (for example, db.r6gd).
- Older generations (db.m4, db.m3, db.r4, db.t2) are end-of-support or being retired for several engines. Plan migrations to current generations.
- Sample sizing for orientation: `db.m7g.large` is 2 vCPU and 8 GiB; `db.r7g.large` is 2 vCPU and 16 GiB. Memory-optimized classes double memory per vCPU.

### 3.2 Selecting an instance class

1. **Start from the working set.** Choose memory so the hot data and indexes fit in the buffer cache or shared buffers.
2. **Check CPU and connection counts.** Many concurrent sessions raise both memory and CPU needs.
3. **Check network and EBS bandwidth.** The instance class sets the network ceiling and the maximum storage throughput and IOPS the instance can drive (see section 4.3).
4. **Pick the cheapest family that fits.** Graviton-based classes generally offer better price performance than equivalent Intel classes, but verify engine and version support.
5. **Right-size using metrics.** Review CloudWatch metrics (CPU utilization, FreeableMemory, DatabaseConnections, ReadIOPS/WriteIOPS, queue depth) and Performance Insights, then scale up or down.
6. **Commit when stable.** Reserved Instances or Savings Plans suit steady workloads.

## 4. Provisioned IOPS

### 4.1 RDS storage types

Amazon RDS offers three storage types:

| Type | Names | Notes |
|---|---|---|
| **Provisioned IOPS SSD** | io1, io2 Block Express | For I/O-intensive, latency-sensitive production workloads |
| **General Purpose SSD** | gp2, gp3 | Balanced price and performance |
| **Magnetic** | standard | Deprecated; AWS scheduled retirement for April 30, 2026, with migration to gp3 or io2 recommended |

### 4.2 How Provisioned IOPS works

When you create a DB instance on Provisioned IOPS storage, you specify **both the IOPS rate and the volume size**. RDS then delivers that IOPS rate until you change it. You are **billed for the provisioned resources whether or not you use them** in a given month. Provisioned IOPS is described as best suited to production environments.

**io2 Block Express** is the recommended option:

- Up to **256,000 IOPS**.
- Higher storage durability (99.999%, compared with 99.9% for io1 and gp3) and sub-millisecond latency, compared with single-digit milliseconds for io1 and gp3.
- Available for all RDS engines, and for Multi-AZ DB clusters since March 2024.
- Billed at the same rate as io1.
- Available in all commercial and GovCloud (US) Regions, but not in the China Regions.

**io1** (previous generation) also reaches up to 256,000 IOPS.

**gp3** is the comparison point for most designs:

- Baseline of **3,000 IOPS and 125 MiBps**, with performance that can be scaled independently of storage size.
- Maximum of **64,000 provisioned IOPS**, compared with 256,000 for io1/io2.

### 4.3 The instance caps your IOPS

Provisioned IOPS only helps if the DB instance can drive it. Each instance class has its own limit on storage bandwidth and IOPS. In an AWS benchmark comparing gp3, io1, and io2 Block Express, the test capped IOPS at 20,000 because that was the maximum the chosen RDS instance could deliver. Buying 100,000 IOPS for a small instance class is wasted spend.

**Rule:** size IOPS to the *lower* of (a) what the workload needs and (b) what the instance class supports. Check the instance's EBS-optimized limits in the documentation before provisioning.

### 4.4 IOPS planning method

1. **Measure** current ReadIOPS and WriteIOPS at peak from CloudWatch (or estimate from queries per second × I/Os per query).
2. **Add headroom** for growth, backups, maintenance, and failover or recovery bursts.
3. **Compare to gp3.** If peak IOPS fits within gp3's range, gp3 with extra IOPS is usually the cheaper choice.
4. **Choose Provisioned IOPS (io2 Block Express)** when you need more than gp3's 64,000 IOPS, very consistent latency, sub-millisecond response, or the higher durability.
5. **Verify instance limits** and confirm the volume size supports the IOPS you want (Provisioned IOPS has ratio and size rules documented in the RDS storage page).
6. **Monitor** and adjust. Storage can be modified on an existing instance, including moving between gp2, gp3, io1, and io2.

### 4.5 Quick decision table

| Requirement | Suggested storage |
|---|---|
| Dev/test, small apps, modest and steady I/O | gp3 baseline |
| Production needing up to 64,000 IOPS | gp3 with provisioned IOPS and throughput |
| Latency-critical OLTP, over 64,000 IOPS, or strict consistency | io2 Block Express |
| Legacy io1 volumes | Plan move to io2 Block Express (same price, better durability) |
| Magnetic volumes | Migrate to gp3 or io2 |

## 5. Putting it together: a sizing walkthrough

**Scenario:** An e-commerce order system on RDS PostgreSQL. Peak: 2,500 transactions per second, hot dataset of about 90 GiB, p99 latency target of 5 ms.

1. **Memory:** the working set is about 90 GiB, so choose a memory-optimized class with at least 128 GiB, for example a `db.r7g` or `db.r8g` size with 128 to 256 GiB.
2. **IOPS:** CloudWatch shows peak WriteIOPS + ReadIOPS around 18,000. With 30% headroom that is about 24,000 IOPS, which is within gp3's 64,000 maximum.
3. **Storage choice:** gp3 would be the cost-effective choice. If the business requires sub-millisecond latency and 99.999% durability, choose io2 Block Express at 24,000 IOPS.
4. **Instance limit check:** confirm the selected instance class can drive 24,000 IOPS and the needed throughput.
5. **Monitoring:** alert on queue depth, freeable memory, and IOPS utilization; revisit sizing monthly.

For a **DynamoDB** version of the same system, with 1 KB items, 2,000 writes/second, and 4,000 strongly consistent 4 KB reads/second:

- WCU = 1 × 2,000 = **2,000**
- RCU = 1 × 4,000 = **4,000**
- Enable auto scaling (for example target utilization 70%) with a sensible minimum and maximum, or choose on-demand if traffic is unpredictable.

## 6. Best practices checklist

- Start from measured workload data, not guesses; use CloudWatch and Performance Insights.
- Prefer current-generation (Graviton) instance classes and avoid retiring generations.
- Match the instance class to the IOPS and throughput you provision; the instance is often the bottleneck.
- Default to gp3; use Provisioned IOPS (io2 Block Express) when requirements justify the higher price.
- For DynamoDB, use on-demand for unpredictable traffic and provisioned with auto scaling (plus reserved capacity) for steady traffic.
- Round item sizes **up** when calculating RCU/WCU, and account for consistency and transaction multipliers.
- For Aurora Serverless v2, set the minimum from baseline memory needs and the maximum as a cost guardrail.
- Request quota increases ahead of launches that will exceed default limits.
- Re-evaluate capacity regularly; capacity planning is continuous, not one-time.

---

## 7. Exam-style takeaways

- 1 RCU = one strongly consistent 4 KB read/s (or two eventually consistent); 1 WCU = one 1 KB write/s; transactions cost double.
- Provisioned DynamoDB is billed on provisioned, not consumed, capacity; mode switching to on-demand is limited to four times per 24 hours.
- 1 ACU is about 2 GiB of memory; Aurora Serverless v2 ranges from 0 or 0.5 to 256 ACUs.
- Instance families: m = general, r/x/z = memory, t = burstable, "d" suffix = local NVMe (Optimized Reads).
- Provisioned IOPS (io1/io2) reaches 256,000 IOPS; gp3 reaches 64,000 with a 3,000 IOPS / 125 MiBps baseline.
- io2 Block Express: 99.999% durability, sub-millisecond latency, same price as io1.
- You pay for provisioned IOPS whether or not you use them, and the instance class caps usable IOPS.
