# Database Replication on AWS (Read Replicas and Beyond)

*Based on the AWS documentation for Amazon RDS, Amazon Aurora, and Amazon DynamoDB. Summarized in original wording; always check the linked pages for the latest limits and Region availability.*

---

## 1. What Is Database Replication?

Database replication means keeping one or more copies of a database in sync with a source. In AWS, replication is used for four main goals:

| Goal | How replication helps |
|---|---|
| **Read scaling** | Send read-only queries (reports, dashboards, search) to copies so the primary handles writes. |
| **High availability (HA)** | A standby or replica can take over if the primary fails. |
| **Disaster recovery (DR)** | A copy in another AWS Region survives a Region-wide outage. |
| **Low-latency global access** | Users read (and sometimes write) from a Region close to them. |

Two vocabulary points matter throughout:

- **Synchronous replication**: a write is confirmed only after the copy has it. Safer (no data loss), but adds latency.
- **Asynchronous replication**: the primary confirms the write first and ships changes afterward. Faster, but the copy can **lag**, so a failover can lose the most recent changes.

Two DR measures are used to judge replication designs:

- **RPO (Recovery Point Objective)**: how much data, measured in time, you can afford to lose.
- **RTO (Recovery Time Objective)**: how long you can afford to be down.

## 2. Amazon RDS Read Replicas

### 2.1 Concept

An RDS **read replica** is a read-only copy of a DB instance. RDS builds it using the **native replication features of the database engine** (for example, MySQL binary log replication or PostgreSQL streaming replication). After you create a replica, the original instance is called the **primary** (source) DB instance. Clients can read and write on the primary but can only read from the replica.

Supported engines include RDS for MySQL, MariaDB, PostgreSQL, Oracle, SQL Server, and Db2, with engine-specific differences.

### 2.2 How it works

1. You choose an existing DB instance as the source.
2. RDS takes a snapshot of the source and creates a new read-only instance from it.
3. From then on, RDS applies the engine's **asynchronous** replication method to copy changes from the primary to the replica.
4. Applications connect to the replica with its own endpoint, just like any other DB instance.

Because replication is asynchronous, a replica can be slightly behind the primary. Your application must tolerate **eventual consistency** on reads from replicas.

### 2.2.1 Things to remember

- RDS replicates all databases on the source instance.
- Replicas are **billed like normal DB instances** of the same instance class.
- Data transfer for replication inside the same Region is not charged; **cross-Region replication data transfer is charged**.
- Replicas are created with automated backups disabled by default, and other attributes (such as security groups and parameter groups) are inherited from the source unless you override them.
- **RDS does not autoscale read replicas.** You must add or remove them yourself (or automate this with your own tooling) as read demand changes.
- If you delete a source instance without deleting its same-Region replicas, each replica is **promoted** to a standalone DB instance.

### 2.3 Use cases

- **Read-heavy workloads**: offload SELECT traffic from the primary.
- **Reporting and analytics**: run long queries without slowing transactional traffic.
- **Scaling beyond one instance's capacity**: spread reads across several replicas.
- **Disaster recovery**: promote a cross-Region replica if the primary Region fails.
- **Migration and upgrades**: build a replica, then promote it as part of a cutover plan.

### 2.4 Same-Region vs. cross-Region replicas

| | Same-Region replica | Cross-Region replica |
|---|---|---|
| Typical purpose | Read scaling, in-Region resilience | DR, local reads for distant users, Region migration |
| Network | Within AWS Region | Secure channel set up by RDS across Regions |
| Data transfer cost | Not charged | Charged |
| Parameter group | Inherits source's if not specified | You must specify a custom parameter group |

For cross-Region replicas, RDS sets up the secure channel and the needed security configuration (for example, security group entries) for you.

### 2.5 Promoting a replica

You can **promote** a read replica to become a standalone DB instance (for example, `aws rds promote-read-replica`). After promotion it stops replicating and accepts writes. Promotion is **a one-way operation**: it does not automatically become the new "source" for the old primary, and your application must be pointed to it. Use it for:

- Disaster recovery (failing over to another Region)
- Planned migrations
- Splitting a database into an independent copy

### 2.6 Monitoring replication

Watch the **`ReplicaLag`** metric in Amazon CloudWatch:

- It reports lag in **seconds** between the replica and its source.
- A value of **0** means the replica has caught up.
- A value of **-1** means replication is not active or RDS cannot determine lag (for example, during setup or in an error state).
- With multiple databases on a replica, the reported lag reflects the worst case.

RDS also exposes a **replication status** (for example, *replicating* or *replication degraded*) in the console and API.

### 2.7 Engine-specific notes (PostgreSQL example)

- A PostgreSQL read replica is strictly read-only, and you **cannot create a replica from another replica** (no cascading replicas in RDS for PostgreSQL).
- You cannot enable automated backups on PostgreSQL read replicas.
- `ReplicaLag` is derived from the time since the last replayed transaction on the replica.
- RDS for PostgreSQL uses **replication slots** for cross-Region replicas (and for in-Region replicas on version 14.1 and higher), plus Amazon S3 archived WAL for in-Region recovery. If a cross-Region replica falls far behind, the primary retains more WAL, and the **`TransactionLogsDiskUsage`** metric can grow significantly. Monitor it together with replication-slot lag.
- High lag often points to a **mismatch between source and replica instance classes or storage types**, or to network issues. Keeping them similar is recommended.
- RDS transparently recovers replicas after interruptions, but recovery can affect read performance, so it is best to avoid reaching that state.

## 3. Read Replicas vs. Multi-AZ

These two features are often confused. They solve different problems.

| Feature | Multi-AZ (instance deployment) | Read replica |
|---|---|---|
| Main purpose | High availability and automatic failover | Read scaling, DR, flexibility |
| Replication style | Synchronous standby copy | Asynchronous (engine-native) |
| Can you read from it? | Standby in a classic Multi-AZ instance deployment is **not** used for reads | Yes, read-only |
| Failover | Automatic | Manual promotion |
| Location | Different AZ, same Region | Same Region or different Region |

You can combine them: a Multi-AZ primary for HA plus read replicas for scale. Replicas can themselves be configured as Multi-AZ where the engine supports it.

**Multi-AZ DB clusters** are a separate RDS option with one writer and two readable standbys across AZs. They offer both HA and read capacity, and you can also create DB instance read replicas from such a cluster to scale beyond its compute or I/O capacity.

## 4. Amazon Aurora Replication

Aurora handles replication differently from standard RDS because of its **shared, distributed cluster storage volume**.

### 4.1 Aurora Replicas

- An Aurora DB cluster has one **writer** instance and up to 15 **Aurora Replicas** (reader instances).
- Replicas **share the same underlying storage volume** as the writer, so they do not need to replay a full copy of the data. They mainly update their in-memory caches.
- Replica lag is therefore typically very low, usually well under 100 milliseconds after the writer commits.
- Replicas serve two purposes: **scale reads** and **increase availability** (a replica can be promoted to writer during failover).
- Adding or removing a replica does not require copying data.

### 4.2 Endpoints

Aurora provides several endpoints:

- **Cluster (writer) endpoint**: always points to the current writer.
- **Reader endpoint**: balances **connections** (not individual queries) across available Aurora Replicas. To spread queries more evenly, open new connections. If the cluster has no replicas, the reader endpoint connects to the writer, so writes could succeed through it.
- **Instance endpoints**: connect to a specific instance.
- **Custom endpoints**: you define groups of instances (for example, bigger instances for analytics).

**RDS Proxy** can add read-only proxy endpoints with similar connection balancing. Applications can reconnect to those faster than to the built-in reader endpoint when readers become unavailable.

### 4.3 Monitoring lag

- **Aurora MySQL**: CloudWatch metrics such as `AuroraReplicaLag`, `AuroraReplicaLagMaximum`, and `AuroraReplicaLagMinimum`. Lag is also visible in `information_schema.replica_host_status`.
- **Aurora PostgreSQL**: the CloudWatch `ReplicaLag` metric, and the `aurora_replica_status` function.
- Lag can rise during periods of heavy writes.

### 4.4 Other replication options for Aurora

- **Binlog replication (Aurora MySQL)**: between two Aurora MySQL clusters, or from RDS for MySQL to Aurora MySQL, often used for migration rather than ongoing replication.
- **Logical replication (Aurora PostgreSQL)**: between clusters in the same Region.
- **Aurora Global Database**: see below.
- Features such as **replication filters**, **delayed replication**, and **multi-source replication** are available for Aurora MySQL.

## 5. Aurora Global Database (Cross-Region Replication)

Aurora Global Database spans multiple Regions: one **primary** cluster accepts writes, and up to several **secondary** clusters (read-only) replicate from it.

Key characteristics:

- Replication uses the **storage layer** (dedicated infrastructure), not engine-level binlog or logical replication, so the performance impact on the primary is small.
- Replication is **asynchronous**, with lag typically around a second or less across Regions.
- Secondary Regions serve **low-latency local reads** and act as DR targets.
- Each secondary cluster can have its own Aurora Replicas.
- A **writer endpoint** for the global database always points to the current primary cluster, even after a Region switch.

### 5.1 Switchover vs. failover

| | Switchover | Failover |
|---|---|---|
| When to use | **Planned** events (Regional rotation, failing back) | **Unplanned** outage in the primary Region |
| Process | Aurora waits for secondaries to be fully synchronized, then promotes the chosen secondary | Promotes a secondary immediately |
| RPO | **0** (no data loss) | Typically non-zero, measured in seconds (depends on lag at the time) |
| Topology | Existing replication topology is maintained | Managed failover keeps the topology and re-adds the old primary as a secondary once it recovers |

Practical guidance from the documentation:

- Check lag on every secondary and prefer the one with the **least lag** when failing over, to minimize data loss.
- Managed cross-Region operations require compatible engine versions across clusters.
- Settings such as parameter groups are not inherited from the old primary, so prepare them in advance.
- For Aurora PostgreSQL, the `rds.global_db_rpo` parameter can set an upper bound on RPO, at the cost of possibly slowing writes on the primary.
- Typical RTO is on the order of minutes.

## 6. DynamoDB Global Tables (Multi-Region Replication, Different Model)

DynamoDB is not a relational database, and it takes a different approach: **multi-active** replication. Each replica table in each Region can serve **both reads and writes**.

- Replication is automatic and fully managed; applications use the normal DynamoDB APIs against their **local Regional endpoint**. There is no single global endpoint.
- Two **consistency modes**, chosen at creation and **not changeable later**:
  - **MREC (multi-Region eventual consistency)**: default. A write is acknowledged locally and propagated asynchronously, usually within a second or two. Conflicts are resolved with **last-writer-wins**.
  - **MRSC (multi-Region strong consistency)**: a successful write is immediately readable from any replica, which supports a zero-RPO design, but it is limited to specific Region sets and has different latency trade-offs.
- A single global table cannot mix consistency modes.
- You can add a Region to an existing table at any time; DynamoDB performs the initial sync.
- Availability design target: a global table is designed for higher availability (99.999%) than a single-Region table (99.99%).
- Newer **multi-account global tables** allow replicas across AWS accounts (MREC only), useful for strong governance boundaries.

**Comparison with RDS/Aurora replication**

| | RDS / Aurora read replicas | DynamoDB global tables |
|---|---|---|
| Writes | Single writer (primary) | Any Region (multi-active) |
| Replica role | Read-only | Read and write |
| Conflict handling | Not needed (one writer) | Last-writer-wins (MREC) |
| Failover | Promote a replica | Redirect traffic to another Region |

## 7. Design Patterns and Best Practices

1. **Route reads and writes separately.** Use the cluster/primary endpoint for writes and the reader endpoint or replica endpoints for reads. Many database drivers and proxies can split traffic automatically.
2. **Design for replica lag.** Do not read a value from a replica immediately after writing it if you need that exact value. Read from the primary for read-your-own-writes scenarios, or tolerate staleness.
3. **Alarm on lag.** Create CloudWatch alarms for `ReplicaLag` (or the Aurora variants) and treat a value of -1 as a failure signal.
4. **Right-size replicas.** Keep replica instance classes and storage comparable to the primary so replicas can keep up with the write volume.
5. **Automate scaling.** RDS read replicas do not autoscale, so script replica creation or use Aurora, which supports replica auto scaling through Application Auto Scaling.
6. **Plan DR in advance.** For cross-Region DR, document the promotion or failover runbook, pre-create parameter groups and networking in the target Region, and **test it regularly**.
7. **Combine mechanisms.** A typical production setup uses Multi-AZ (or Aurora's multi-AZ replicas) for HA, plus cross-Region replicas or a global database for DR.
8. **Account for cost.** Each replica is a billable instance, and cross-Region transfer is charged.
9. **Secure the channel.** Use encryption in transit and at rest; keep replicas in private subnets with tight security groups.
10. **Use RDS Proxy where useful.** It can reduce connection overhead and speed reconnection after failures.

## 8. Quick Decision Guide

| Need | Best fit |
|---|---|
| Automatic HA in one Region (RDS) | Multi-AZ deployment |
| Scale read traffic on RDS | RDS read replicas |
| Scale reads with very low lag | Aurora Replicas |
| Cross-Region DR for RDS | Cross-Region read replica + promotion |
| Cross-Region DR with low RPO/RTO | Aurora Global Database |
| Multi-Region, multi-writer NoSQL | DynamoDB global tables |
| Zero data loss on planned Region move | Aurora Global Database switchover |

---

## 9. Key Takeaways

- A read replica is a **read-only, asynchronously updated copy**; use it for read scaling and as a DR building block.
- **Multi-AZ is for availability; read replicas are for scaling** (though Multi-AZ DB clusters blend the two).
- **Aurora Replicas share storage**, so lag is typically tens of milliseconds, and the **reader endpoint balances connections, not queries**.
- **Aurora Global Database** adds fast cross-Region replication, **switchover (RPO 0)** for planned moves and **failover** for outages.
- **DynamoDB global tables** are multi-active, with MREC or MRSC consistency chosen at creation.
- Always **monitor lag**, because asynchronous replication means failover can lose recent data.
