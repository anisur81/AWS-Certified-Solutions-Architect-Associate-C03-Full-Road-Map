# AWS Database Types and Services -(serverless, relational compared with non-relational, inmemory)

---

## 1. Why AWS Offers Many Databases

For a long time the relational database was the default for almost every application. AWS follows a **purpose-built database** approach instead: pick the database whose data model and access pattern match your workload, rather than forcing everything into one engine.

AWS Prescriptive Guidance describes two hosting approaches:

- **Purpose-built databases**: a specific engine for a specific workload or use case.
- **Converged databases**: a single database that supports different workloads.

Choosing the wrong database is expensive to reverse, so the decision should start from the data model, the query patterns, the scale, and the latency requirement.

### Key questions to ask

| Question | Why it matters |
|---|---|
| What is the data model (tables, key-value, documents, graph, time series)? | Determines the engine family |
| Are joins and multi-row ACID transactions required? | Favors relational |
| What scale and throughput are expected? | Favors horizontally scaling NoSQL for extreme scale |
| What latency is needed (ms vs. µs)? | Microsecond needs point to in-memory |
| Is traffic predictable or spiky? | Spiky or unknown traffic favors serverless |
| Who manages the infrastructure? | Managed vs. self-managed on EC2 |

---

## 2. Managed vs. Self-Managed

Running a database on **Amazon EC2** gives full control (OS, engine version, custom extensions) but you handle patching, backups, replication, and failover.

**Managed database services** (RDS, Aurora, DynamoDB, and others) shift much of the undifferentiated work to AWS:

- Provisioning and hardware management
- Automated backups and point-in-time recovery
- Patching and software updates
- Built-in high availability (for example Multi-AZ)
- Monitoring through Amazon CloudWatch

You keep responsibility for schema design, query tuning, access control, and data protection settings (the AWS **shared responsibility model**).

## 3. Relational Databases (SQL)

Relational databases store data in **tables with rows and columns** and use **SQL**. They enforce a predefined **schema**, support **joins**, and provide **ACID** transactions (Atomicity, Consistency, Isolation, Durability).

**Typical use cases:** traditional business applications, ERP, CRM, e-commerce, and anything with complex queries and strong consistency requirements.

### 3.1 Amazon RDS (Relational Database Service)

A managed service for running relational databases without administering the underlying servers.

- **Engines:** Amazon Aurora, MySQL, PostgreSQL, MariaDB, Oracle Database, Microsoft SQL Server, and IBM Db2.
- **Features:** automated backups, patching, **Multi-AZ** deployments for failover, **read replicas** for read scaling, encryption at rest (AWS KMS) and in transit.
- **Best for:** lift-and-shift of existing databases, or when you need a specific commercial or open-source engine.

**Multi-AZ vs. read replicas (common exam point):**

| Feature | Multi-AZ | Read replica |
|---|---|---|
| Purpose | High availability / failover | Read scaling |
| Replication | Synchronous (standby) | Asynchronous |
| Serves reads? | Standard Multi-AZ standby: no | Yes |
| Cross-Region | No (within a Region) | Supported |

### 3.2 Amazon Aurora

A **cloud-native relational database** compatible with **MySQL and PostgreSQL**, built into the RDS family.

- Higher performance and availability than standard RDS engines, with a distributed storage layer that grows automatically (up to 128 TiB).
- Data is replicated across **three Availability Zones** (six copies).
- Up to **15 read replicas**.
- **Aurora Global Database** for low-latency reads and disaster recovery across Regions.
- Typically costs more than standard RDS, but offers better performance and resilience.

### 3.3 Amazon Aurora DSQL

A newer **serverless, distributed SQL** database that is PostgreSQL-compatible and designed for highly available, multi-Region applications with active-active architecture. Check current documentation for feature and Region availability.

### 3.4 Amazon Redshift (Data Warehouse)

Redshift is relational and SQL-based, but built for **analytics (OLAP)**, not transactional (OLTP) workloads.

- Columnar storage and massively parallel processing for large analytical queries.
- Provisioned clusters or **Redshift Serverless**.
- Use it for BI, reporting, and large-scale aggregations over historical data.

### OLTP vs. OLAP

| | OLTP | OLAP |
|---|---|---|
| Workload | Many small reads/writes | Large scans and aggregations |
| Example service | RDS, Aurora, DynamoDB | Redshift |
| Storage orientation | Row-oriented | Column-oriented |

## 4. Non-Relational Databases (NoSQL)

Non-relational databases use **flexible schemas** and data models other than tables. They are generally built to **scale horizontally**, offer low latency, and are tuned for specific access patterns. Many trade some relational features (such as complex joins) for scale and flexibility.

| Data model | AWS service | Typical use cases |
|---|---|---|
| Key-value / document | **Amazon DynamoDB** | High-traffic web apps, gaming, shopping carts, serverless backends |
| Document (MongoDB-compatible) | **Amazon DocumentDB** | Content management, catalogs, user profiles |
| Wide-column (Cassandra-compatible) | **Amazon Keyspaces** | Large-scale, low-latency apps using Cassandra APIs |
| Graph | **Amazon Neptune** | Social networks, fraud detection, recommendation engines, knowledge graphs |
| Time series | **Amazon Timestream** | IoT telemetry, DevOps metrics, application monitoring |
| Ledger | **Amazon QLDB** | Verifiable change history (see note below) |

> **Note:** AWS has announced the end of support for Amazon QLDB, and recommends migrating ledger workloads to Aurora PostgreSQL. Verify the current status in AWS documentation before relying on it.

### 4.1 Amazon DynamoDB

A fully managed, **serverless** NoSQL database supporting **key-value and document** data models.

- **Single-digit millisecond** performance at virtually any scale.
- **Capacity modes:**
  - *On-demand*: pay per request, no capacity planning, good for unpredictable traffic.
  - *Provisioned*: specify read/write capacity (optionally with auto scaling), good for predictable traffic.
- **Global tables** for multi-Region, multi-active replication.
- **Streams** for change data capture (commonly paired with AWS Lambda).
- **TTL** to expire items automatically, **point-in-time recovery**, and on-demand backups.
- **Consistency options:** eventually consistent reads (default) or strongly consistent reads.
- Access patterns must be designed up front around the **partition key** (and optional sort key); secondary indexes (GSI/LSI) add query flexibility.

### 4.2 Amazon DocumentDB

A fully managed document database with **MongoDB API compatibility**. It stores JSON-like documents and suits workloads that need flexible schemas, rich querying on documents, and a managed alternative to self-hosted MongoDB. Its storage layer is distributed and replicated across multiple AZs.

### 4.3 Amazon Neptune

A purpose-built **graph database** engine optimized for storing billions of relationships and querying the graph with millisecond latency. It supports graph query languages such as **Gremlin**, **openCypher**, and **SPARQL**. Use it when relationships between data points are the core of the problem.

### 4.4 Amazon Keyspaces (for Apache Cassandra)

A scalable, highly available, managed service compatible with Apache Cassandra. Use it to run Cassandra workloads without managing clusters. It is **serverless**, so you pay for what you use.

### 4.5 Amazon Timestream

A serverless time-series database for data that is indexed by time, such as IoT sensor readings and operational metrics, with built-in time-series functions and data tiering.

## 5. Relational vs. Non-Relational: Side-by-Side

| Aspect | Relational (RDS, Aurora) | Non-relational (DynamoDB, DocumentDB, etc.) |
|---|---|---|
| Data model | Tables, rows, columns | Key-value, document, graph, wide-column, time series |
| Schema | Fixed, predefined | Flexible / schema-on-read |
| Query language | SQL | Service-specific APIs or languages |
| Joins | Native and powerful | Limited or not supported (model data to avoid them) |
| Transactions | Full ACID, multi-table | Varies; DynamoDB supports transactions with limits |
| Scaling | Vertical, plus read replicas (Aurora scales storage automatically) | Horizontal by design |
| Consistency | Strong | Configurable (eventual or strong) |
| Best for | Complex queries, reporting, structured data | Massive scale, simple access patterns, flexible data |
| Latency | Low milliseconds | Single-digit milliseconds (or less with caching) |

**Rule of thumb:** if you need complex joins and strict relational integrity, choose relational. If you need extreme scale, predictable low latency, and your access patterns are well known, choose NoSQL. Many real systems use **both**.

## 6. In-Memory Databases and Caching

In-memory data stores keep data in **RAM** rather than on disk, delivering **microsecond** read latency and very high throughput. They are used to accelerate applications, reduce load on primary databases, and handle real-time workloads.

### 6.1 Amazon ElastiCache

A managed in-memory caching and data store service.

- **Engines:** **Valkey**, **Redis OSS**, and **Memcached**.
- **Common patterns:**
  - **Caching** frequently read data in front of RDS, Aurora, or DynamoDB.
  - **Session stores** for web applications.
  - **Leaderboards**, rate limiting, real-time analytics, pub/sub messaging.
- Supports replication, Multi-AZ with automatic failover (Valkey/Redis), and data tiering options.
- Typically placed **between the application and the primary database**. It is usually not the system of record, so data can be lost if a node fails unless persistence/replication is configured.

**Redis/Valkey vs. Memcached:**

| Feature | Valkey / Redis OSS | Memcached |
|---|---|---|
| Data structures | Rich (lists, sets, sorted sets, hashes) | Simple key-value |
| Persistence / backups | Yes (snapshots) | No |
| Replication / failover | Yes | No |
| Multithreaded | Limited | Yes |
| Typical choice | Advanced features, HA | Simple, scalable cache |

### 6.2 Amazon MemoryDB

A **Valkey- and Redis OSS-compatible, durable, in-memory database** that delivers ultra-fast performance. It is purpose-built for modern applications with microservices architectures.

- Uses a **multi-AZ transactional log** to provide durability, so it can serve as a **primary database**, not just a cache.
- Microsecond reads and single-digit millisecond writes.
- Good fit when you want Redis-style data structures **and** durability without running a separate cache plus database.

### 6.3 DynamoDB Accelerator (DAX)

A fully managed, in-memory cache **specifically for DynamoDB**. It is API-compatible with DynamoDB and can reduce read latency from milliseconds to microseconds with little application change. It is best for read-heavy or repeated-read workloads and is not suited for strongly consistent reads or write-heavy patterns.

### ElastiCache vs. MemoryDB vs. DAX

| | ElastiCache | MemoryDB | DAX |
|---|---|---|---|
| Role | Cache / ephemeral store | Durable primary database | DynamoDB-specific cache |
| Durability | Optional / limited | Multi-AZ transaction log | Cache only |
| Compatibility | Valkey, Redis OSS, Memcached | Valkey, Redis OSS | DynamoDB API |
| Use when | Accelerating any backend | Redis API needed as the primary store | Accelerating DynamoDB reads |

## 7. Serverless Databases

**Serverless** means you do not provision or manage servers or instances. The service scales automatically with demand, you pay for what you use, and you avoid capacity planning. It is a strong fit for **unpredictable, spiky, or intermittent workloads**, dev/test environments, and new applications with unknown traffic.

| Service | Serverless offering | How it scales / bills |
|---|---|---|
| **Amazon Aurora** | **Aurora Serverless v2** | Scales compute capacity automatically in fine-grained increments, measured in Aurora Capacity Units (ACUs) |
| **Amazon DynamoDB** | Serverless by design (on-demand mode) | Scales automatically; pay per request or provisioned capacity |
| **Amazon Aurora DSQL** | Serverless distributed SQL | Scales automatically; pay for usage |
| **Amazon ElastiCache** | **ElastiCache Serverless** | Scales instantly with workload; data stored redundantly across multiple AZs; pay for data stored and compute consumed, with no upfront commitments |
| **Amazon Redshift** | **Redshift Serverless** | Set base capacity in RPUs (Redshift Processing Units); scales automatically |
| **Amazon Keyspaces** | Serverless | Pay per read/write or provisioned throughput |
| **Amazon Timestream** | Serverless | Scales automatically with ingestion and query load |
| **Amazon DocumentDB** | Elastic clusters (scale-out) | Elastic scaling of compute and storage (check current docs for details) |

### Serverless: benefits and trade-offs

**Benefits**

- No capacity planning or instance management
- Automatic scaling up and down
- Pay only for what you use
- Fits event-driven architectures with AWS Lambda

**Trade-offs**

- Steady, high-volume workloads can cost less on provisioned capacity or reserved pricing.
- Scaling can have minimum/maximum capacity limits you must configure.
- Less control over low-level tuning.

### Connecting Lambda to relational databases

Lambda can scale to thousands of concurrent executions, each opening its own connection, which can exhaust a relational database's connection limit. **Amazon RDS Proxy** sits between the application and RDS/Aurora to provide **connection pooling**, multiplexing, and faster failover. DynamoDB uses HTTP APIs and avoids this problem.

## 8. Choosing the Right Service

| Requirement | Recommended service |
|---|---|
| Managed MySQL, PostgreSQL, Oracle, SQL Server, MariaDB, Db2 | **Amazon RDS** |
| High-performance MySQL/PostgreSQL-compatible with strong HA | **Amazon Aurora** |
| Relational with variable or unpredictable load | **Aurora Serverless v2** |
| Multi-Region, active-active distributed SQL | **Aurora DSQL** |
| Data warehouse and analytics (OLAP) | **Amazon Redshift** |
| Key-value, serverless, single-digit ms at any scale | **Amazon DynamoDB** |
| MongoDB-compatible documents | **Amazon DocumentDB** |
| Cassandra-compatible workloads | **Amazon Keyspaces** |
| Highly connected data and relationship queries | **Amazon Neptune** |
| Time-series and IoT metrics | **Amazon Timestream** |
| Caching and sub-millisecond reads | **Amazon ElastiCache** |
| Redis-compatible **durable** primary database | **Amazon MemoryDB** |
| Microsecond reads for DynamoDB | **DynamoDB Accelerator (DAX)** |

### Decision flow

1. **What is the data model?**
   - Tables with joins and transactions: relational (RDS or Aurora).
   - Analytics over large historical data: Redshift.
   - Key-value or document at scale: DynamoDB (or DocumentDB for MongoDB compatibility).
   - Relationships are the focus: Neptune.
   - Time-stamped metrics: Timestream.
2. **Is latency in microseconds required?** Add ElastiCache or DAX, or use MemoryDB as the primary store.
3. **Is traffic spiky or unknown?** Prefer a serverless option.
4. **Is there an existing engine or API to keep?** Use the compatible service (RDS for the same engine, DocumentDB for MongoDB, Keyspaces for Cassandra, ElastiCache/MemoryDB for Redis/Valkey).

### Common architecture patterns

- **Cache-aside:** application checks ElastiCache first; on a miss it reads from RDS/Aurora/DynamoDB and writes the result to the cache.
- **Serverless API backend:** API Gateway + Lambda + DynamoDB, with no servers to manage.
- **Polyglot persistence:** Aurora for transactions, DynamoDB for session or catalog data, Redshift for analytics, ElastiCache for acceleration.
- **Zero-ETL integrations:** replicate transactional data from Aurora or DynamoDB to Redshift for analytics without building pipelines.

## 9. Migration and Related Services

- **AWS Database Migration Service (DMS):** migrates databases to AWS with minimal downtime, including continuous replication.
- **AWS Schema Conversion Tool (SCT)** and DMS Schema Conversion: convert schemas for **heterogeneous** migrations (for example Oracle or SQL Server to Aurora PostgreSQL).
- **Homogeneous migrations** (same engine) can often use native tools such as snapshots and replication.

| From | To | Typical tooling |
|---|---|---|
| Oracle / SQL Server | Aurora PostgreSQL | DMS + schema conversion |
| RDS / Aurora | DynamoDB | DMS or custom ETL (when access becomes key-value dominant) |
| Self-managed Redis | ElastiCache or MemoryDB | Snapshot import or online migration |

## 10. Security, Availability, and Operations (Applies to All)

- **Encryption** at rest (AWS KMS) and in transit (TLS).
- **Network isolation** with VPCs, subnets, and security groups; VPC endpoints (PrivateLink) for services such as DynamoDB.
- **Access control** with IAM, and Secrets Manager for credentials.
- **Backups and recovery:** automated backups, snapshots, point-in-time recovery.
- **High availability:** Multi-AZ designs; global options (Aurora Global Database, DynamoDB global tables).
- **Monitoring:** Amazon CloudWatch, Performance Insights (RDS/Aurora), and CloudTrail for auditing.

---

## 11. Quick Revision Summary

- **Relational:** RDS (six-plus engines), Aurora (cloud-native, MySQL/PostgreSQL compatible), Redshift (OLAP warehouse).
- **Non-relational:** DynamoDB (key-value/document), DocumentDB (MongoDB), Keyspaces (Cassandra), Neptune (graph), Timestream (time series).
- **In-memory:** ElastiCache (cache; Valkey/Redis OSS/Memcached), MemoryDB (durable primary), DAX (DynamoDB cache).
- **Serverless:** DynamoDB, Aurora Serverless v2, Aurora DSQL, ElastiCache Serverless, Redshift Serverless, Keyspaces, Timestream.
- **Multi-AZ** = availability; **read replicas** = read scaling.
- **OLTP** = RDS/Aurora/DynamoDB; **OLAP** = Redshift.
- **RDS Proxy** pools connections for Lambda and serverless workloads.
- **Match the database to the workload**: AWS's purpose-built philosophy.
