
# Caching Strategies and Services: Amazon ElastiCache

---

## 1. Why Caching?

Reading from a database or a remote API on every request is comparatively slow and expensive. A **cache** keeps frequently needed data in fast storage (usually memory) so repeated reads are served quickly, and the backing data store handles less load.

Typical benefits:

- **Lower latency**: in-memory reads are far faster than disk-based queries.
- **Higher throughput**: the same application can serve more requests.
- **Reduced database load**: fewer queries reach the primary data store.
- **Cost efficiency**: you can often delay scaling up the database.

The trade-off is **data freshness**: the cache holds a *copy*, and that copy can drift from the source of truth. Every caching strategy is essentially a different answer to the question: *when and how do we populate and refresh the cache?*

---

## 2. What Is Amazon ElastiCache?

Amazon ElastiCache is a fully managed web service for setting up, running, and scaling a distributed in-memory data store or cache in the cloud. It sits **between your application and its data store**. The application asks the cache first; the database is consulted only when needed.

AWS handles hardware provisioning, monitoring, node replacement, and software patching, so teams can focus on application logic.

### 2.1 Supported engines

ElastiCache works with three engines:

| Engine | Notes |
|---|---|
| **Valkey** | Open-source, Redis-compatible engine; supported in both serverless and node-based modes. |
| **Redis OSS** | Rich data structures, replication, persistence options. |
| **Memcached** | Simple, multithreaded key-value cache; good for plain object caching and easy scale-out. |

The AWS guide includes a dedicated comparison page ("Comparing node-based Valkey, Memcached, and Redis OSS clusters") to help you choose.

### 2.2 Two deployment options

**1) ElastiCache Serverless**
- Create a cache in about a minute by supplying little more than a name (console, SDK, or CLI).
- No instance types, nodes, or cluster design to manage; no capacity planning.
- The service continuously watches memory, compute, and network use and scales automatically.
- Exposes a simple endpoint that hides the underlying infrastructure.
- Compatible with Valkey 7.2+, Memcached 1.6.22+, and Redis OSS 7.1.
- Offers VPC or public connection types. Public endpoints (on newer Valkey versions) require IAM authentication and TLS.

**2) Node-based clusters**
- You choose the **node type**, **number of nodes**, and **placement across Availability Zones**.
- More control and flexibility, but you are responsible for sizing capacity correctly.
- You can run **single-AZ or Multi-AZ** depending on availability needs.
- Engines can run in **cluster mode** (horizontal scaling by sharding) or **without cluster mode** (vertical scaling only).
- You decide **when to apply patches** for Valkey and Redis OSS clusters.
- Node-based Valkey clusters can enable **durability**, persisting data to a distributed, Multi-AZ transactional log so data survives even a full node failure.

**Quick rule of thumb:** choose *Serverless* for speed of setup and hands-off scaling; choose *node-based* for fine-grained control, predictable capacity, and tuning.

## 3. Core Caching Strategies

The ElastiCache guide describes three foundational strategies. They are usually combined rather than used in isolation.

### 3.1 Lazy Loading (Cache-Aside)

Data is loaded into the cache **only when it is requested** and not already present.

**Flow**
1. The application requests data from the cache.
2. **Cache hit**: the cache returns the data. Done.
3. **Cache miss**: the cache returns nothing (or null).
4. The application reads the data from the database.
5. The application writes that data into the cache so the next request is a hit.

**Illustrative pseudocode**

```python
def get_customer(customer_id):
    record = cache.get(customer_id)
    if record is None:                    # cache miss
        record = db.query_customer(customer_id)
        cache.set(customer_id, record)    # populate for next time
    return record
```

**Advantages**
- **Only requested data is cached**, so memory isn't wasted on data nobody reads.
- **Node failures aren't fatal**: a replacement node starts empty, and the cache refills gradually as requests produce misses.

**Disadvantages**
- **Cache-miss penalty**: a miss costs three trips: (1) check the cache, (2) query the database, (3) write to the cache. The first request for any item is slower.
- **Stale data**: nothing updates the cache when the database changes, so the cached copy may be outdated until it is evicted or replaced.

### 3.2 Write-Through

Whenever data is **written to the database, the cache is updated at the same time**.

**Illustrative pseudocode**

```python
def save_customer(customer_id, values):
    record = db.update_customer(customer_id, values)
    cache.set(customer_id, record)        # keep cache in sync
    return "success"
```

**Advantages**
- **Cache data is never stale**, because every write refreshes it.
- **Write penalty vs. read penalty**: each write costs two operations (database + cache), which users often tolerate better than a slow read. Updates are commonly expected to take longer than reads.

**Disadvantages**
- **Missing data**: a new node (from scaling out or replacing a failed one) is empty. Data stays missing until it is next written to the database. Combining write-through with lazy loading mitigates this.
- **Cache churn**: much of the written data may never be read, wasting memory. Adding a TTL reduces this waste.

### 3.3 Adding a TTL (Time to Live)

A **TTL** is an expiry time attached to a cached item. After it elapses, the item is removed (or treated as expired) and must be reloaded from the source.

TTL is a **modifier** that improves both strategies above:

- **Lazy loading + TTL**: stale data lives only until the TTL expires, then a miss forces a refresh.
- **Write-through + TTL**: items that are written but never read disappear on their own, limiting clutter.

**Illustrative pseudocode**

```python
TTL_SECONDS = 300

def save_customer(customer_id, values):           # write-through with TTL
    record = db.update_customer(customer_id, values)
    cache.set(customer_id, record, ttl=TTL_SECONDS)
    return "success"

def get_customer(customer_id):                    # lazy loading with TTL
    record = cache.get(customer_id)
    if record is None:
        record = db.query_customer(customer_id)
        cache.set(customer_id, record, ttl=TTL_SECONDS)
    return record
```

**Summary from the AWS guidance:** lazy loading tolerates stale data but doesn't break on empty nodes; write-through keeps data fresh but can break on empty nodes and fill the cache with unneeded data. **Adding a TTL to each write gives you the benefits of both** while largely avoiding clutter.

**Choosing a TTL value**
- Short TTL: fresher data, more misses, more database load.
- Long TTL: better hit rate, higher risk of staleness.
- Pick based on how quickly the underlying data changes and how much staleness the business can accept. Volatile data (prices, stock) needs short TTLs; reference data (country lists, product categories) can use long ones.

### 3.4 Strategy comparison

| Aspect | Lazy Loading | Write-Through | Either + TTL |
|---|---|---|---|
| When cache is filled | On first read (miss) | On every write | Same, plus automatic expiry |
| Staleness risk | Yes | No (for written data) | Bounded by TTL |
| Handles empty/new nodes | Yes, refills naturally | No, data missing until written | Yes (if lazy loading is included) |
| Wasted memory | Low | Possible (unread data) | Low |
| Extra cost | Slow first read | Slower writes | Slight tuning effort |

## 4. Reading from Replicas

For ElastiCache **Serverless**, you can often get a significant performance boost by **reading from replicas instead of the primary node**. This spreads read traffic and lowers latency. AWS provides a separate "Best Practices for using Read Replicas" topic. Remember that replicas can lag slightly behind the primary, so reads from replicas may return marginally older data.

---

## 5. Putting It Together: A Practical Pattern

A common, robust design:

1. Use **lazy loading** as the default read path (resilient to node loss).
2. Add **write-through** for data that is read soon after being written and where freshness matters.
3. Put a **TTL on everything** as a safety net against staleness and bloat.
4. Add **monitoring** for hit rate, evictions, memory, and latency, then tune TTLs and sizing.

Additional design points worth knowing:

- **Cache only what benefits**: read-heavy, slow-to-compute, or rarely changing data gives the best return. Highly unique or rapidly changing data gives poor hit rates.
- **Plan for cache failure**: your application should still work (more slowly) if the cache is empty or temporarily unavailable.
- **Use sensible key design**: consistent, descriptive keys (for example `customer:12345`) make invalidation and debugging easier.
- **Beware of cold starts and stampedes**: after a restart or mass expiry, many simultaneous misses can hit the database at once. Staggering TTLs (adding small random jitter) helps.

## 6. Choosing Between Engines (Quick Guide)

- Choose **Memcached** when you need a simple, multithreaded object cache and easy horizontal scale-out/scale-in, and you don't need persistence or complex data types.
- Choose **Valkey or Redis OSS** when you need richer data structures, replication, high availability, and (with Valkey node-based durability) stronger data protection.
- Choose **Serverless** when you want minimal operations; choose **node-based** when you want to control node type, topology, patch timing, and cost shape.

---

## 7. Key Takeaways

- ElastiCache is a managed in-memory caching service that sits between your application and its database.
- It supports **Valkey, Redis OSS, and Memcached**, in **Serverless** or **node-based** form.
- The three core strategies are **lazy loading**, **write-through**, and **TTL**.
- Lazy loading: cache fills on demand; resilient but can be stale and has a miss penalty.
- Write-through: cache is always current for written data, but has write overhead, empty-node gaps, and churn.
- **TTL** balances freshness and efficiency, and is best combined with the other two.
- Reading from replicas can further improve read performance for serverless caches.
