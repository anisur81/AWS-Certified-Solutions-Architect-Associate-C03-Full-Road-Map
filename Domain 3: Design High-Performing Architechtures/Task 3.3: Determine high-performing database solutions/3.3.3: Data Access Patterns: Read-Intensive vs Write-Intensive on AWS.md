# Data Access Patterns: Read-Intensive vs Write-Intensive on AWS
---

## 1. What Is a Data Access Pattern?

A **data access pattern** describes *how* an application reads and writes its data: the ratio of reads to writes, how predictable the traffic is, which keys are touched, how fast responses must be, and how fresh the data must be.

The AWS Prescriptive Guidance states that workload data access patterns are either **read-intensive** or **write-intensive**, and that understanding this characteristic helps you pick the right architecture. The Well-Architected Framework asks the same question when evaluating a data store: *"Is the workload read-heavy or write-heavy?"* and then *"What solutions are available for offloading reads (read replicas, caching, etc.)?"*

In practice, three categories are used:

| Pattern | Description | Typical example |
|---|---|---|
| **Read-intensive** | Many more reads than writes | Product catalog, news site, reporting dashboards, user profile lookups |
| **Write-intensive** | Many more writes than reads | IoT telemetry, clickstream, logging, order/event ingestion |
| **Balanced** | Reads and writes roughly equal | Transactional apps, shopping carts, session stores |

**Design principle:** Identify the pattern *first*, then choose the service, then add "performance boosters" (read replicas, caching, connection pooling, partitioning).

---

## 2. Questions to Ask Before Choosing a Design

1. **Read/write ratio** – 100:1? 10:1? 1:1? 1:100?
2. **Data model** – relational (joins, transactions) or key-value/document?
3. **Latency target** – milliseconds, or microseconds?
4. **Consistency need** – can reads be slightly stale (eventual consistency), or must they always see the latest write (strong consistency)?
5. **Traffic shape** – steady, spiky, or unpredictable?
6. **Hot keys / hot data** – is a small subset of data requested repeatedly?
7. **Scale and geography** – single Region or multi-Region?
8. **Operational effort** – managed/serverless preferred?

## 3. Read-Intensive Workloads

### 3.1 Characteristics

- Reads vastly outnumber writes (for example, thousands of viewers and a handful of editors).
- Often tolerate slightly stale data.
- Frequently request the same "hot" items repeatedly.
- Bottleneck is usually **read throughput or latency** on the primary database.

### 3.2 Core Strategy: Offload Reads

The Well-Architected Framework (PERF03-BP02) recommends offloading the read portion of the workload using:

- **Read replicas** – supported by Amazon RDS, Amazon Aurora, and provisioned NoSQL databases such as Amazon Neptune and Amazon DocumentDB.
- **Caching** – for example Amazon ElastiCache, and **DAX** for DynamoDB tables.

A good rule of thumb from AWS-focused guidance: if the problem is *repeated reads*, the best answer is often to **remove load before it reaches the database**.

### 3.3 Amazon RDS / Aurora Read Replicas

- Allow multiple replicas to serve read traffic; **writes still go to the primary**.
- RDS read replicas use **asynchronous replication**, so replicas can lag slightly (eventual consistency).
- Used for **scaling reads**, workload sharing/offloading (e.g., analytics queries), and can serve as read-only disaster recovery targets.
- **Aurora** uses a shared cluster storage volume, supports up to 15 Aurora Replicas, and supports **automatic scaling of replicas** via Aurora Auto Scaling. A **reader endpoint** load-balances connections across replicas.
- Application change required: send read queries to the reader/replica endpoint and writes to the writer endpoint.

> **Note:** Read replicas are *not* the same as Multi-AZ. Multi-AZ (RDS) is for **high availability/failover**; read replicas are for **read scaling** (and optionally DR).

### 3.4 Amazon ElastiCache (Redis OSS / Valkey / Memcached)

- In-memory cache placed in front of a database to serve repeated queries with very low latency and to reduce database load.
- A Redis replication group has one primary and read replicas; replicas let you **separate read and write workloads** and scale reads by adding replicas. Replication to replicas is asynchronous.
- **Memcached** – simple, distributed cache, multi-threaded, no persistence.
- **Redis OSS / Valkey** – richer data structures, replication, persistence options, Multi-AZ failover, and **Global Datastore** for cross-Region replication.
- Works with *any* backend (RDS, Aurora, DynamoDB, on-premises).

Common caching patterns:

| Pattern | How it works | Best for |
|---|---|---|
| **Lazy loading (cache-aside)** | App checks cache; on miss, reads DB and populates cache | Read-heavy, tolerates misses |
| **Write-through** | App writes to cache and DB together | Keeping cache fresh; read-heavy with some writes |
| **TTL (expiration)** | Items expire after a set time | Limiting staleness |

### 3.5 DynamoDB Accelerator (DAX)

- A **fully managed, highly available, in-memory cache built specifically for DynamoDB**, delivering microsecond response times for cached reads.
- **API-compatible with DynamoDB**, so little application change is needed (use the DAX client instead of the standard client). This is the main differentiator versus ElastiCache.
- The DynamoDB Developer Guide notes DAX is a good fit for **read-heavy applications**; for applications with a high read-to-write ratio (for example **10:1 or more**), DAX results in more cache hits and less stale data, reducing reads against the table.
- Also helpful for **hot-key / bursty read** patterns and for lowering read capacity costs on repeated reads.
- DAX is **not** ideal for write-heavy workloads or for applications that require **strongly consistent reads** on every request (strongly consistent reads bypass the cache).

### 3.6 Other Read-Scaling Options

- **Amazon DynamoDB** – scales reads horizontally; ensure enough **read capacity units (RCU)** are provisioned (or use on-demand mode / auto scaling).
- **Amazon S3 + Amazon CloudFront** – for read-mostly static or semi-static content, cache at the edge for global low latency.
- **Amazon RDS Proxy** – pools and shares database connections; helps when many clients (e.g., Lambda) overwhelm the database with connections.
- **Aurora Serverless v2** – scales capacity up and down for variable read traffic.

### 3.7 Quick Decision Table – Reads

| Requirement | Suggested solution |
|---|---|
| Relational DB, reads overwhelm primary | RDS/Aurora **read replicas** |
| Repeated hot queries, lower latency | **ElastiCache** |
| DynamoDB reads, microsecond latency, minimal code change | **DAX** |
| Global static content | **S3 + CloudFront** |
| Highly variable read traffic, relational | **Aurora Serverless v2** + replicas |

## 4. Write-Intensive Workloads

### 4.1 Characteristics

- Constant, high-volume inserts or updates (IoT sensor data, clickstream, logging, order events, time-series).
- Often **append-heavy** and may arrive in bursts.
- Reads are less frequent, or are performed later on aggregated data.
- Bottleneck is **write throughput**, storage I/O, locking/contention, or a single writer node.

### 4.2 Why Writes Are Harder to Scale

Read replicas and caches do **not** help with writes. In most relational designs, **all writes go to a single primary/writer** instance. Scaling writes therefore requires one of the following:

- Scaling **up** the writer (larger instance, more IOPS).
- Scaling **out** by distributing writes through **partitioning/sharding**.
- Using a database designed for horizontally scalable writes (e.g., DynamoDB).
- **Buffering/decoupling** writes using a queue or stream.

The AWS Prescriptive Guidance echoes this for multi-Region: for write-intensive workloads, **select a primary Region** and engineer the ability to **fail over to a standby Region**.

### 4.3 Amazon DynamoDB

- Serverless NoSQL key-value/document database with single-digit millisecond performance at virtually any scale.
- Writes are distributed across **partitions** based on the partition key; throughput scales by spreading load across many distinct key values.
- **Capacity modes:**
  - **Provisioned** (with auto scaling) – predictable workloads; you set write capacity units (WCU).
  - **On-demand** – unpredictable or spiky traffic; pay per request, no capacity planning.
- **Partition key design is critical.** A poor key causes a **hot partition** and throttling. Choose high-cardinality keys (e.g., device ID + time bucket) to distribute writes evenly. Techniques include write sharding (adding a random/calculated suffix to the key).
- **Global Tables** provide multi-Region, multi-active replication (last-writer-wins conflict resolution).
- **TTL** can automatically expire old items (useful for logs/telemetry), and **DynamoDB Streams** can trigger downstream processing.

### 4.4 Amazon Aurora for Heavier Writes

- Aurora's storage layer is distributed and log-structured: the writer sends only redo log records to storage replicated six ways across three Availability Zones, which reduces write overhead versus traditional engines.
- Provides higher write throughput than standard RDS engines for many workloads, but there is still **one writer instance per cluster** in a standard configuration.
- **Aurora Global Database** – one primary Region for writes with low-latency read-only secondary Regions; supports **write forwarding** from secondary clusters to the primary.
- **Aurora I/O-Optimized** – pricing configuration that can reduce cost for I/O-heavy (read- or write-heavy) applications.
- **Aurora Limitless Database** – horizontally scales writes through sharding for very large relational workloads.

> **Exam caution:** Older study notes mention *Aurora Multi-Master*. That feature was limited to Aurora MySQL and has been discontinued. For current SAA-C03 questions, think DynamoDB (and Aurora Limitless / Global Database where relevant) for write scaling.

### 4.5 Streaming and Buffering Ingestion

When writes arrive faster than the database can handle, or in bursts, **decouple** the producer from the database:

- **Amazon Kinesis Data Streams** – ordered, high-throughput stream ingestion; consumers write to storage or analytics at their own pace.
- **Amazon Data Firehose** – fully managed delivery of streaming data to S3, Redshift, OpenSearch, etc., with batching and optional transformation.
- **Amazon SQS** – queue that buffers writes so a consumer can write to the database at a steady rate (smooths spikes).
- **Amazon MSK** – managed Apache Kafka for Kafka-based pipelines.
- **Amazon S3** – virtually unlimited, cost-effective landing zone for raw event data (query later with Athena).
- **Amazon Timestream** – purpose-built for time-series ingestion (IoT, metrics).

Typical pipeline: **Devices → Kinesis/Firehose → S3 (raw) → Athena/Glue/Redshift (analytics)**, or **Producers → SQS → Lambda/consumers → DynamoDB/Aurora**.

### 4.6 Quick Decision Table – Writes

| Requirement | Suggested solution |
|---|---|
| Massive, spiky key-value writes | **DynamoDB** (on-demand) |
| Predictable heavy writes, relational | **Aurora** (right-sized writer, I/O-Optimized) |
| Extremely high relational write scale | **Aurora Limitless Database** |
| Burst absorption / decoupling | **SQS** or **Kinesis Data Streams** |
| Log/clickstream to data lake | **Firehose → S3** |
| Time-series/IoT metrics | **Timestream** or **DynamoDB with TTL** |

## 5. Balanced and Mixed Workloads

Many real systems combine both patterns. AWS guidance is to **separate read behavior from write behavior and scale them independently**:

- **Aurora** or **DynamoDB on-demand** are common choices for balanced, variable workloads.
- Apply **CQRS-style** separation: writes go to a primary store (e.g., DynamoDB), and reads are served from a cache or a read-optimized store (e.g., ElastiCache, OpenSearch, a read replica).
- Use **DynamoDB Streams** or **change data capture (AWS DMS)** to keep read-optimized copies in sync.
- Consider **transaction-heavy** needs (ACID, joins) separately: relational engines (RDS/Aurora) or DynamoDB transactions.

## 6. Consistency and Trade-Offs

| Aspect | Read-intensive impact | Write-intensive impact |
|---|---|---|
| **Consistency** | Replicas and caches are eventually consistent (replication lag, stale cache). | Strong consistency on writes is simpler with a single writer but limits scale-out. |
| **Latency** | Cache gives microsecond to sub-millisecond reads. | Buffering adds latency between write and visibility. |
| **Cost** | Replicas and cache nodes add cost but cut DB size/IOPS needs. | Provisioned write capacity/IOPS can be expensive; on-demand costs rise with volume. |
| **Complexity** | Need cache invalidation and read/write endpoint routing. | Need good partition design, idempotency, and failure handling (retries, DLQs). |

DynamoDB gives a choice per request: **eventually consistent reads** (default, half the RCU cost) or **strongly consistent reads** (latest data, higher cost, not available on global secondary indexes, and not served from DAX cache).

## 7. Multi-Region Considerations

From the AWS Prescriptive Guidance (Multi-Region fundamentals):

- **Completely read-only content** (e.g., static content) → easiest to run **active-active** across Regions, with less engineering complexity.
- **Read-intensive with some writes** → use a **"read local, write global"** strategy: serve reads from a local Region replica; send writes to a single global primary.
- **Write-intensive** → choose a **primary Region** and build **failover to a standby Region** into the workload.
- **Write-everywhere (multi-active)** needs conflict resolution (e.g., DynamoDB Global Tables last-writer-wins), which adds design complexity.

Relevant services: **Aurora Global Database**, **DynamoDB Global Tables**, **ElastiCache Global Datastore**, **RDS cross-Region read replicas**, **S3 Cross-Region Replication**.

## 8. Capacity Planning Notes

- **DynamoDB provisioned**: Estimate RCUs/WCUs; use auto scaling for gradual changes. **On-demand** for unknown or spiky traffic.
- **Aurora / RDS**: Monitor **CPU, ReplicaLag, DatabaseConnections, IOPS** in CloudWatch; use **Performance Insights** to find slow queries and lock waits.
- **ElastiCache**: Monitor **CacheHitRate / CacheMisses, Evictions, memory usage**. A low hit rate means the cache is not helping.
- Watch for **throttling** (DynamoDB `ProvisionedThroughputExceededException`) and apply exponential backoff.
- Run **load tests** with realistic read/write mixes before committing to a design.

## 9. Summary Cheat Sheet

| Workload | Primary goal | Recommended AWS building blocks |
|---|---|---|
| **Read-intensive (relational)** | Offload reads | RDS/Aurora **read replicas**, **ElastiCache**, RDS Proxy |
| **Read-intensive (DynamoDB)** | Microsecond reads | **DAX**, on-demand/auto scaling, eventually consistent reads |
| **Read-intensive (static/global)** | Edge delivery | **S3 + CloudFront** |
| **Write-intensive** | Scale & absorb writes | **DynamoDB** (good partition keys), Aurora (right-sized/Limitless), **Kinesis/SQS/Firehose** buffering |
| **Balanced / variable** | Flexibility | **Aurora**, **DynamoDB on-demand**, separate read/write paths |
| **Multi-Region reads** | Low-latency local reads | Aurora Global DB, Global Tables, Global Datastore |
| **Multi-Region writes** | Resilience | Primary Region + standby failover (or multi-active with conflict handling) |

## 10. Exam Tips (SAA-C03)

1. **Identify the pattern first**: read-heavy, write-heavy, or balanced. Key phrases: "high read-to-write ratio," "repeated queries," "sudden spikes in writes," "IoT sensors," "reporting queries slowing down the primary."
2. **Reads → replicas + caching**:
   - Relational + slow reads → **read replicas** (or Aurora Replicas).
   - Repeated identical queries → **ElastiCache**.
   - DynamoDB + microsecond reads + minimal code change → **DAX**.
3. **Writes → scale-out or buffer**:
   - Massive/unpredictable writes → **DynamoDB (on-demand)**.
   - Bursty ingestion → put **SQS/Kinesis** in front.
4. **Read replicas ≠ Multi-AZ.** Replicas scale reads (asynchronous); Multi-AZ provides HA failover.
5. **Replicas don't scale writes.** If the question is about write bottlenecks, replicas and caches are the wrong answer.
6. **Strong consistency needed?** Read from the primary/writer or use DynamoDB strongly consistent reads (not through DAX cache); expect higher cost/latency.
7. **Reporting/analytics hurting OLTP performance?** Direct those queries to a **read replica** (or move to Redshift/Athena).
8. **Hot partition** in DynamoDB → redesign the partition key / write sharding.
9. **"Least operational overhead"** → favor serverless/managed options (DynamoDB, Aurora Serverless, Firehose).
10. **ElastiCache vs DAX**: ElastiCache works with any database and needs code to manage the cache; DAX is DynamoDB-only and API-compatible.

## 11. Self-Check Questions

1. A product catalog gets millions of views but only a few updates per hour on an RDS MySQL instance whose CPU is saturated by SELECT queries. Which two changes best reduce load? *(Read replicas; ElastiCache in front.)*
2. An IoT fleet sends millions of small readings per second in unpredictable bursts. Which database and ingestion service fit best? *(DynamoDB on-demand; Kinesis Data Streams/Firehose as buffer.)*
3. A DynamoDB-backed app needs microsecond latency for repeated reads with minimal code changes. *(DAX.)*
4. A write-heavy table is throttled even though overall capacity is sufficient. What is the likely cause? *(Hot partition/poor partition key.)*
5. A global app is read-heavy with few writes. Which multi-Region strategy fits? *(Read local, write global.)*
