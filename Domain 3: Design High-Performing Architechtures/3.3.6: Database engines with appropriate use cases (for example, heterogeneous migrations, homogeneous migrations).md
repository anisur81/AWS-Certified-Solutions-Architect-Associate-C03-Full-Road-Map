# Database engines with appropriate use cases (heterogeneous migrations, homogeneous migrations)
---

## 1. Overview

AWS follows a **purpose-built database** approach: instead of forcing every workload into one relational engine, you choose the engine that best fits the data model, access pattern, scale, and latency requirement. When moving to AWS, the key question is whether the **source and target engines are the same or different**, because that decides the migration strategy and tooling.

---

## 2. Database Engines and Their Use Cases

### 2.1 Relational (SQL) Engines

| Service / Engine | Description | Typical Use Cases |
|---|---|---|
| **Amazon RDS for MySQL** | Managed MySQL | Web apps, CMS, e-commerce, lift-and-shift of MySQL |
| **Amazon RDS for PostgreSQL** | Managed PostgreSQL | Complex queries, geospatial (PostGIS), open-source replacement for commercial DBs |
| **Amazon RDS for MariaDB** | Managed MariaDB | MariaDB-compatible apps |
| **Amazon RDS for Oracle** | Managed Oracle (License Included or BYOL) | Existing Oracle apps that cannot be refactored quickly |
| **Amazon RDS for SQL Server** | Managed Microsoft SQL Server | .NET and Windows-based enterprise applications |
| **Amazon RDS for Db2** | Managed IBM Db2 | Existing Db2 workloads |
| **Amazon Aurora (MySQL- / PostgreSQL-compatible)** | Cloud-native relational engine with a distributed, shared storage layer | High-throughput OLTP, SaaS, apps needing fast failover, read scaling, and up to 15 replicas |
| **Aurora Serverless v2** | Capacity scales automatically | Variable, unpredictable, or multi-tenant workloads |

**Key points**
- RDS automates provisioning, patching, backup, Multi-AZ failover, and read replicas.
- Aurora typically offers higher performance and availability than standard RDS engines, with storage that grows automatically and is replicated across multiple Availability Zones.
- Choose **RDS** when you need a specific commercial or community engine with minimal change; choose **Aurora** when you want cloud-native scalability and resilience with MySQL/PostgreSQL compatibility.
- When you need OS-level or full database-instance control, run the database on **Amazon EC2** (self-managed), accepting the operational overhead.

### 2.2 Key-Value and Wide-Column

| Service | Use Cases |
|---|---|
| **Amazon DynamoDB** | Serverless NoSQL key-value/document; single-digit millisecond latency at any scale; gaming leaderboards, shopping carts, session stores, IoT, high-scale serverless backends. Global tables provide multi-Region, multi-active replication. |
| **Amazon Keyspaces (for Apache Cassandra)** | Managed Cassandra-compatible service; migrate Cassandra workloads without managing clusters. |

### 2.3 Document

| Service | Use Cases |
|---|---|
| **Amazon DocumentDB (with MongoDB compatibility)** | JSON document workloads, content management, catalogs, user profiles; migrating MongoDB-style applications. |

### 2.4 In-Memory

| Service | Use Cases |
|---|---|
| **Amazon ElastiCache (Redis OSS / Valkey / Memcached)** | Caching, session management, real-time leaderboards, pub/sub. Reduces load on primary databases. |
| **Amazon MemoryDB** | Redis-compatible, durable in-memory primary database; ultra-fast reads with microsecond latency and multi-AZ durability. |

### 2.5 Graph

| Service | Use Cases |
|---|---|
| **Amazon Neptune** | Highly connected data: social networks, fraud detection, recommendation engines, knowledge graphs. Supports property graph and RDF models. |

### 2.6 Time Series and Ledger

| Service | Use Cases |
|---|---|
| **Amazon Timestream** | IoT telemetry, DevOps metrics, application monitoring. |
| **Amazon QLDB** | Immutable, cryptographically verifiable ledger. Note: AWS has announced end of support for QLDB; check the docs for the migration guidance (commonly to Aurora PostgreSQL). |

### 2.7 Analytics / Data Warehouse and Search

| Service | Use Cases |
|---|---|
| **Amazon Redshift** | Petabyte-scale data warehouse, OLAP, BI dashboards, complex analytical queries. Not intended for high-frequency OLTP. |
| **Amazon OpenSearch Service** | Full-text search, log analytics, observability. |

### 2.8 Quick Engine-Selection Guide

| Requirement | Recommended Engine |
|---|---|
| Transactional app with joins and ACID guarantees | RDS or Aurora |
| Massive scale, predictable single-digit ms latency, simple access patterns | DynamoDB |
| JSON documents with rich querying | DocumentDB |
| Sub-millisecond caching | ElastiCache |
| Relationship-heavy queries | Neptune |
| Large-scale analytics | Redshift |
| Time-stamped metrics | Timestream |
| Existing Oracle/SQL Server licence and features required | RDS for Oracle / SQL Server |

## 3. Migration Fundamentals

### 3.1 Why Migration Type Matters

The migration type is determined by comparing **source engine** and **target engine**:

- **Homogeneous migration**: source and target are the **same engine type** (or compatible engine family).
- **Heterogeneous migration**: source and target are **different engine types**, which usually means schema and code conversion is needed.

### 3.2 Core Migration Tools

| Tool | Purpose |
|---|---|
| **AWS Database Migration Service (AWS DMS)** | Migrates data between databases. Supports **full load**, **change data capture (CDC)**, and **full load + CDC**, so the source can stay operational during migration with minimal downtime. Available as replication instances or **DMS Serverless**. |
| **AWS Schema Conversion Tool (AWS SCT)** | Desktop tool that converts source schema and database code (views, stored procedures, functions) to a target engine format. Produces an **assessment report** showing conversion complexity and manual actions required. |
| **DMS Schema Conversion** | Schema conversion capability within the DMS console (a managed alternative to SCT for supported engine pairs). |
| **Native database tools** | `mysqldump`, `pg_dump`/`pg_restore`, Oracle Data Pump, SQL Server backup/restore, logical replication. Often the best choice for homogeneous migrations. |
| **DMS Homogeneous Data Migrations** | A DMS feature that uses native engine tools under the hood to migrate like-to-like (for example, MySQL to MySQL, PostgreSQL to PostgreSQL), preserving more database objects than a standard DMS task. |
| **AWS Snow Family** | Physical transfer when network bandwidth is a constraint for very large datasets. |

## 4. Homogeneous Migrations

### 4.1 Definition
Migrating between the **same database engine**, for example:

- MySQL on-premises → Amazon RDS for MySQL or Aurora MySQL
- PostgreSQL on EC2 → Amazon RDS for PostgreSQL or Aurora PostgreSQL
- Oracle → Amazon RDS for Oracle
- SQL Server → Amazon RDS for SQL Server
- MariaDB → Amazon RDS for MariaDB

### 4.2 Characteristics
- **No schema conversion** required (or only minimal changes), so SCT is generally not needed.
- Data types, stored procedures, and SQL dialect remain compatible.
- Lower risk, faster timeline, and lower cost than heterogeneous migration.
- Application code changes are typically limited to connection strings.

### 4.3 Typical Approaches
1. **Native backup and restore / dump and load**: simple, but requires a downtime window proportional to data size.
2. **Native replication** (MySQL binlog replication, PostgreSQL logical replication, Oracle Data Guard or Data Pump with GoldenGate where applicable): continuous sync with a short cutover.
3. **AWS DMS (full load + CDC)**: continuous replication until cutover; good for minimal downtime.
4. **DMS Homogeneous Data Migrations**: managed use of native tools with ongoing replication.
5. **Aurora read replica from RDS MySQL/PostgreSQL**: create an Aurora replica of an RDS source, then promote it for a low-downtime move into Aurora.
6. **Restore from Percona XtraBackup** (MySQL) from Amazon S3 into Aurora MySQL or RDS MySQL.

### 4.4 Appropriate Use Cases
- **Lift-and-shift / rehost** to reduce operational burden without redesigning the application.
- Moving from self-managed EC2 or on-premises databases to **managed RDS**.
- **Data centre exit** with tight timelines.
- Upgrading to a managed service for backups, patching, and Multi-AZ high availability.
- Consolidating multiple instances of the same engine.
- Moving from RDS MySQL/PostgreSQL to **Aurora** for higher performance and scale.

### 4.5 Considerations
- Check **engine version and extension compatibility** (for example, PostgreSQL extensions supported on RDS).
- Verify parameter groups, character sets, and collations.
- Some privileges (such as SUPER or sysadmin-level access) are restricted in managed services, so review scripts and jobs that depend on them.
- Plan network connectivity (VPN or Direct Connect), security groups, and encryption (KMS, SSL/TLS).
- Test the **cutover and rollback** plan.

## 5. Heterogeneous Migrations

### 5.1 Definition
Migrating between **different engines**, for example:

- Oracle → Amazon Aurora PostgreSQL or RDS for PostgreSQL
- Microsoft SQL Server → Aurora PostgreSQL / Aurora MySQL
- Oracle → Aurora MySQL
- IBM Db2 → PostgreSQL
- Sybase / Teradata / Netezza → Amazon Redshift
- MongoDB → Amazon DocumentDB (document to document, but different engines)
- Cassandra → Amazon Keyspaces or DynamoDB
- Relational → DynamoDB (data model change)

### 5.2 Characteristics
- Requires **schema and code conversion** (tables, indexes, constraints, procedures, triggers, functions, packages).
- Data type mappings differ between engines.
- Typically involves **application changes**: SQL dialect, ORM, error handling, transaction semantics.
- More testing, higher effort, and a longer timeline than homogeneous migration.
- Often the goal is **modernization**, not only relocation.

### 5.3 Typical Two-Step Process
1. **Convert the schema** using AWS SCT or DMS Schema Conversion:
   - Run the **assessment report** to estimate the percentage of objects converted automatically.
   - Review the **action items** for objects requiring manual rework.
   - Apply the converted schema to the target.
2. **Migrate the data** using AWS DMS:
   - Full load of existing data, then **CDC** to keep the target in sync.
   - Use **data validation** to compare source and target.
   - Cut over when replication lag is near zero.

### 5.4 Useful Complementary Capabilities
- **Babelfish for Aurora PostgreSQL**: lets Aurora PostgreSQL understand the SQL Server T-SQL dialect and TDS wire protocol, reducing application changes when moving from SQL Server.
- **DMS premigration assessments**: check for issues before running a task.
- **Generative AI-assisted conversion** features in AWS migration tooling may help with complex code objects; check the current docs for availability.
- **SCT data extraction agents** for moving large data warehouse datasets (for example, into Redshift) via Amazon S3.

### 5.5 Appropriate Use Cases
- **Eliminating commercial licence costs** (Oracle or SQL Server to open-source-compatible engines such as PostgreSQL or Aurora).
- **Modernizing** to cloud-native engines for better scalability and availability.
- **Moving from OLTP to analytics** (for example, a relational source to Redshift or an S3 data lake).
- **Re-architecting for scale**, such as moving a high-traffic relational workload to DynamoDB.
- **Consolidating** a mixed database estate onto fewer engines.
- Replacing **legacy or end-of-life** database platforms.

### 5.6 Considerations
- **Feature gaps**: Oracle PL/SQL packages, proprietary features, and certain data types may need redesign.
- **Performance differences**: query plans, indexing, and optimizer behaviour will differ, so benchmark early.
- **LOB handling**: DMS has specific LOB modes (limited, full, inline); tune them for speed and completeness.
- **Case sensitivity, character sets, null handling, and date formats** may differ.
- **Skills and training** for the new engine.
- Allow for **iterative conversion, testing, and parallel runs**.

## 6. Homogeneous vs Heterogeneous: Comparison

| Aspect | Homogeneous | Heterogeneous |
|---|---|---|
| Source and target engine | Same | Different |
| Schema conversion | Not needed or minimal | Required (SCT / DMS Schema Conversion) |
| Primary tools | Native tools, DMS Homogeneous Data Migrations, DMS | SCT + DMS |
| Application code change | Low (connection strings) | Moderate to high |
| Risk and effort | Lower | Higher |
| Typical goal | Rehost / replatform to managed service | Modernize / reduce licence cost / change data model |
| Downtime | Minimal with replication | Minimal with CDC, but longer preparation |
| Example | MySQL → RDS MySQL | Oracle → Aurora PostgreSQL |

## 7. Choosing the Right Migration Strategy (Decision Flow)

1. **Identify the source engine and version.**
2. **Decide the target**:
   - Same engine, managed → **homogeneous** (RDS).
   - Same family, cloud-native → **homogeneous** to Aurora.
   - Different engine for cost, scale, or modernization → **heterogeneous**.
3. **Assess**: run SCT / DMS assessment to gauge compatibility and effort.
4. **Choose tooling**:
   - Native tools for small databases or where downtime is acceptable.
   - DMS with CDC for minimal downtime.
   - SCT + DMS when conversion is needed.
   - Snow Family when data volume is huge and bandwidth is limited.
5. **Pilot** with a non-critical database.
6. **Validate** data and performance, then plan **cutover** and **rollback**.

### Scenario Examples

| Scenario | Recommended Approach |
|---|---|
| On-prem MySQL to RDS MySQL with a short maintenance window | Homogeneous: native dump/restore or DMS |
| Production PostgreSQL on EC2, near-zero downtime required | Homogeneous: logical replication or DMS full load + CDC |
| Oracle data warehouse to Redshift | Heterogeneous: SCT (with data extraction agents) + DMS |
| Oracle OLTP to Aurora PostgreSQL to cut licence costs | Heterogeneous: SCT/DMS Schema Conversion + DMS full load + CDC |
| SQL Server app with heavy T-SQL, minimal app change desired | Heterogeneous: Aurora PostgreSQL with Babelfish |
| MongoDB to DocumentDB | DMS (heterogeneous, different engine) |
| Self-managed Cassandra to Keyspaces | Migration tooling for Cassandra to Keyspaces (DMS or dedicated scripts) |
| RDS MySQL to Aurora MySQL | Homogeneous: Aurora read replica, snapshot restore |

## 8. Best Practices

- **Assess first**: use SCT assessment reports and DMS premigration assessments.
- **Right-size** the DMS replication instance (or use DMS Serverless) based on data volume and transaction rate.
- **Use CDC** to reduce downtime; monitor **replication lag** with CloudWatch.
- **Enable validation** on DMS tasks to confirm data integrity.
- **Load large tables in parallel** and use appropriate table mappings and filters.
- **Disable or defer** foreign keys, triggers, and secondary indexes during full load, and enable them before cutover.
- **Secure** the migration: encryption in transit and at rest, IAM least privilege, private networking (VPN / Direct Connect / VPC endpoints).
- **Test performance** on the target using a realistic workload before production cutover.
- **Plan rollback**, such as reverse replication.
- **Document** and rehearse the cutover runbook.

---

## 9. Summary

- AWS offers **purpose-built engines**: relational (RDS, Aurora), key-value (DynamoDB), document (DocumentDB), in-memory (ElastiCache, MemoryDB), graph (Neptune), time series (Timestream), and analytics (Redshift).
- **Homogeneous migrations** move between the **same engine**, need little or no schema conversion, and suit **lift-and-shift and replatforming** with native tools or DMS.
- **Heterogeneous migrations** move between **different engines**, require **SCT / DMS Schema Conversion plus DMS**, and suit **modernization, licence cost reduction, and re-architecture**.
- Select the engine by **data model, scale, latency, and compatibility needs**, and the migration approach by **source/target engine match, downtime tolerance, and conversion complexity**.
