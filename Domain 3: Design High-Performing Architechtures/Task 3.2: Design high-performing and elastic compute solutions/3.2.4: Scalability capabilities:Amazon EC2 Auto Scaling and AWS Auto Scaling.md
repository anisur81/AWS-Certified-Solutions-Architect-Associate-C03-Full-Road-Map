# Scalability capabilities:Amazon EC2 Auto Scaling and AWS Auto Scaling
---

## 1. Why Scalability Matters

Scalability is the ability of a workload to handle growing or shrinking demand by adding or removing capacity. In AWS this is mainly achieved through **horizontal scaling** (more or fewer instances or replicas) rather than **vertical scaling** (a bigger or smaller instance). Scaling automatically gives you three things:

- **Availability:** enough healthy capacity to serve users during spikes, and replacement of failed instances.
- **Cost optimization:** capacity shrinks when demand falls, so you do not pay for idle resources.
- **Operational simplicity:** no manual provisioning for predictable or unpredictable load.

AWS offers two closely related services for this:

| Service | Scope | Main purpose |
|---|---|---|
| **Amazon EC2 Auto Scaling** | EC2 instances only | Launch, terminate and maintain a fleet of instances in an Auto Scaling group (ASG) |
| **AWS Auto Scaling** | Multiple services, through *scaling plans* | One place to configure scaling for several resource types, with built-in scaling strategies |

Note that AWS Auto Scaling does not replace EC2 Auto Scaling. It builds on it (and on Application Auto Scaling) to manage scaling across services.

## 2. Amazon EC2 Auto Scaling

### 2.1 What it does

Amazon EC2 Auto Scaling automatically launches or terminates EC2 instances based on user-defined scaling policies, scheduled actions and health checks. Instances are organized into an **Auto Scaling group**, which is treated as a logical unit for scaling and management.

### 2.2 Core components

**Auto Scaling group (ASG).** The collection of EC2 instances. You define three capacity settings:

- **Minimum size:** the group never goes below this number of instances.
- **Maximum size:** the group never exceeds this number (a cost and safety ceiling).
- **Desired capacity:** the number of instances the group tries to maintain right now. Scaling actions change this value within the min and max limits.

**Launch template.** Specifies *what* to launch: AMI, instance type, key pair, security groups, storage, user data, IAM instance profile and metadata options. Launch templates are the recommended approach (they support versioning and newer EC2 features). Older launch configurations are legacy.

**Scaling options.** Rules that decide *when* and *by how much* to change the desired capacity.

**Health checks.** The group replaces instances that fail EC2 status checks. You can also enable Elastic Load Balancing (ELB) health checks so that instances failing load balancer checks are replaced.

### 2.3 Multi-AZ and instance purchasing flexibility

- **Multiple Availability Zones:** spreading the group over several AZs gives fault tolerance. If an AZ becomes unhealthy, the group launches instances in the remaining AZs and rebalances when the AZ recovers.
- **Mixed instances policy:** a single group can use multiple instance types and combine On-Demand and Spot capacity, for example a stable On-Demand base with Spot instances for burst capacity. Attribute-based instance type selection lets you describe requirements (vCPU, memory) instead of listing types.
- **Load balancer integration:** attaching the group to an Application Load Balancer, Network Load Balancer or Gateway Load Balancer target group registers new instances automatically and deregisters terminating ones.

### 2.4 Scaling options in EC2 Auto Scaling

#### a) Manual scaling
You change the desired capacity (or min/max) yourself through the console, CLI or API.
**Use case:** testing, one-off adjustments, emergency intervention.

#### b) Maintain a fixed number of instances
Set min, max and desired to the same value (or a narrow range). The group simply replaces unhealthy instances.
**Use case:** a legacy single-instance application that needs self-healing but cannot scale out, such as a fixed-size bastion fleet or license-bound software.

#### c) Scheduled scaling
You create scheduled actions that change min, max or desired capacity at specific times, either one time or recurring (cron expression).
**Use case:** known, predictable events: a business-hours workload that needs more capacity from 8 AM to 6 PM, a monthly billing run, or a planned marketing launch.

#### d) Dynamic scaling
Responds to *live* changes in demand using Amazon CloudWatch metrics. There are three policy types:

**1. Target tracking scaling (recommended starting point).**
You choose a metric and a target value, and EC2 Auto Scaling creates and manages the CloudWatch alarms for you, adding or removing capacity to keep the metric near the target. It works like a thermostat.

Predefined metrics:

- `ASGAverageCPUUtilization`
- `ASGAverageNetworkIn`
- `ASGAverageNetworkOut`
- `ALBRequestCountPerTarget`

You can also use **custom metrics** from CloudWatch (for example, queue depth per instance).

*Use cases:* web or API tier targeting 50% average CPU; a fleet behind an ALB targeting 1,000 requests per target; any workload where demand correlates with a single metric. It is the simplest policy and handles scale-in conservatively (it scales in only when metrics are below the target by a safe margin).

**2. Step scaling.**
You create CloudWatch alarms and define **step adjustments**: different scaling amounts depending on how far the metric breaches the alarm threshold. For example, add 1 instance if CPU is 60-70%, add 3 if it is 70-85%, and add 5 if it is above 85%.

*Use cases:* workloads that need an aggressive response to large spikes, or when you want fine control over the size of each adjustment. Step scaling supports a `MinAdjustmentMagnitude` and an instance warmup so that new instances are not double counted.

**3. Simple scaling.**
A single alarm triggers a single adjustment, followed by a **cooldown** period during which further scaling is blocked. It is the older approach, and AWS generally recommends target tracking or step scaling instead because they continue to respond while previous actions are still in progress.

*Use case:* legacy configurations or very simple needs.

**Key tuning concepts**

| Concept | Meaning |
|---|---|
| **Instance warmup** | Time (in seconds) for a new instance to become stable and start contributing to metrics. Warming instances are not counted in aggregated metrics, which prevents over-scaling. A *default instance warmup* can be set for the whole group. |
| **Cooldown** | A wait period after a scaling activity (mainly relevant to simple scaling) to let the group stabilize. |
| **Scale-in protection** | Prevents selected instances from being terminated during scale in. |
| **Termination policies** | Decide which instance to terminate first (for example, oldest launch template, closest to next billing hour, or default AZ-balancing behavior). |
| **Enabled / disabled policies** | A policy can be disabled temporarily without being deleted. |

You can combine multiple policies. When several policies request different actions at once, the group follows the policy that provides the **largest capacity** for scale out, which protects availability.

#### e) Predictive scaling
Predictive scaling uses machine learning on historical CloudWatch data to forecast load and schedule capacity **ahead of time**. It analyzes recurring daily and weekly patterns and generates scheduled scaling actions, so instances are ready *before* the traffic arrives, rather than reacting after the metric has already risen.

Key points:

- Predefined metrics include CPU utilization, network in/out and ALB request count per target, and you can supply custom metrics.
- A **ForecastOnly** mode lets you evaluate forecasts without applying any scaling action, which is a safe way to test before enabling **ForecastAndScale**.
- It works best for workloads with **cyclical, recurring** patterns and needs historical data to produce a forecast.
- It is typically used **together with** dynamic scaling: predictive scaling provides the baseline capacity, and dynamic scaling handles unexpected variation above the forecast.

*Use cases:* applications with regular daily or weekly peaks, applications with long instance initialization times (for example, heavy boot scripts or large application warmup), and batch workloads that start on a regular schedule.

### 2.5 Advanced EC2 Auto Scaling features

- **Lifecycle hooks:** pause an instance in a `Pending:Wait` or `Terminating:Wait` state so you can run custom actions, such as installing software before the instance enters service, or draining connections and uploading logs before termination. Integrates with EventBridge, SNS, or SQS.
- **Warm pools:** keep pre-initialized instances (stopped, running or hibernated) ready, which reduces scale-out latency for applications with long startup times and lowers cost compared with running them fully.
- **Instance refresh:** roll out a new AMI or launch template across the group gradually, with configurable minimum healthy percentage and checkpoints.
- **Capacity Rebalancing:** proactively replaces Spot instances that are at elevated risk of interruption.
- **Instance maintenance policy:** controls whether replacement launches before or after termination, to balance availability and cost.
- **Notifications and monitoring:** Amazon SNS notifications for launch and terminate events, plus group metrics (such as `GroupDesiredCapacity`, `GroupInServiceInstances`, `GroupMinSize`, `GroupMaxSize`) in CloudWatch.

## 3. AWS Auto Scaling (Scaling Plans)

### 3.1 What it is

AWS Auto Scaling provides a single interface to configure automatic scaling for multiple scalable resources that belong to the same application. You use a **scaling plan** to configure scaling in a matter of minutes. Resources can be grouped using **tags** (for example, `Environment=production`) or **CloudFormation stacks**, and AWS Auto Scaling then discovers the scalable resources automatically.

### 3.2 Supported resources

Scaling plans can scale:

- **Amazon EC2 Auto Scaling groups**: launch and terminate instances
- **Amazon ECS services**: adjust the desired task count
- **Spot Fleet requests**: change the target capacity
- **Amazon DynamoDB**: provisioned read/write capacity for tables and global secondary indexes
- **Amazon Aurora**: number of Aurora Replicas in a DB cluster

(AWS notes that supported resources can change over time; check the current documentation. Services such as Lambda or EBS volumes are not managed through scaling plans.)

### 3.3 Features and benefits

- **Resource discovery:** automatically finds scalable resources in your application by tag or stack.
- **Built-in scaling strategies:** pick a strategy that optimizes for availability, cost, or a balance:
  - **Optimize for availability:** keeps utilization lower (target around 40%) to leave headroom.
  - **Balance availability and cost:** targets about 50% utilization.
  - **Optimize for cost:** runs resources at higher utilization (about 70%) to reduce spend.
  - **Custom:** you set the metric and target value yourself.
- **Dynamic scaling:** creates **target tracking scaling policies** for each resource in the plan, adjusting capacity in response to live changes.
- **Predictive scaling:** for Auto Scaling groups, uses a load forecast to generate scheduled scaling actions so capacity is available before demand. The console shows graphs of historical load, the forecast and the scaling actions taken.
- **Unified experience:** one console and one plan for several services, instead of configuring each separately.
- **No additional charge** for AWS Auto Scaling itself; you pay for CloudWatch and the underlying resources you use.

### 3.4 How scaling plans work

1. **Define the application:** select resources via tags or a CloudFormation stack.
2. **Choose a scaling strategy:** availability, balanced, cost, or custom, and decide whether to enable dynamic and/or predictive scaling.
3. **AWS Auto Scaling configures scaling:** it creates target tracking policies and, for predictive scaling, forecasts load and schedules the scaling actions (updating the minimum capacity ahead of the expected peak).
4. **Monitor and adjust:** review capacity, forecasts and scaling history, and change the strategy if needed.

Under the hood, scaling plans rely on **Amazon EC2 Auto Scaling** (for ASGs) and **Application Auto Scaling** (for the other resource types).

### 3.5 Important documentation note

The AWS documentation states that if you use scaling plans **only for predictive scaling**, AWS strongly recommends setting **predictive scaling policies directly on your Auto Scaling groups** instead, and provides a guide for migrating from scaling plans to EC2 Auto Scaling predictive scaling policies. When designing new solutions, prefer configuring scaling directly on each service (EC2 Auto Scaling policies, or Application Auto Scaling for ECS, DynamoDB, Aurora and others) unless you specifically want the unified plan experience.

## 4. EC2 Auto Scaling vs. AWS Auto Scaling

| Aspect | Amazon EC2 Auto Scaling | AWS Auto Scaling (scaling plans) |
|---|---|---|
| Resources | EC2 instances in ASGs | ASGs, ECS services, Spot Fleet, DynamoDB, Aurora |
| Configuration level | Per group, fine-grained | Per application, strategy-based |
| Policy types | Target tracking, step, simple, scheduled, predictive | Target tracking (dynamic) and predictive |
| Control | High (warmup, cooldown, lifecycle hooks, warm pools, instance refresh) | Simplified, recommendation-driven |
| Best when | You need detailed control of the instance fleet | You want fast, consistent setup across several services |

## 5. Choosing the Right Approach: Use Cases

| Scenario | Recommended capability | Why |
|---|---|---|
| Public web application with unpredictable traffic behind an ALB | EC2 Auto Scaling, **target tracking** on `ALBRequestCountPerTarget` | Simple, adapts automatically, keeps per-instance load constant |
| E-commerce site with daily and weekly traffic cycles | **Predictive scaling** + target tracking | Capacity ready before peaks; dynamic policy covers surprises |
| Office-hours internal application | **Scheduled scaling** | Demand is time-based and known in advance |
| Flash sale or viral spike where load can jump quickly | **Step scaling** with larger steps (plus warm pool) | Aggressive, proportional response and fast instance readiness |
| Queue-based worker fleet (SQS) | Target tracking on a **custom metric** (backlog per instance) | Scales with work waiting, not with CPU |
| Single-instance app needing self-healing | Min = max = desired = 1 with health checks | Automatic replacement without scaling |
| Cost-sensitive batch or stateless processing | **Mixed instances policy** with Spot + Capacity Rebalancing | Lower cost with resilience to interruptions |
| Application with slow boot and configuration time | **Warm pools**, lifecycle hooks, default instance warmup | Shortens time to serve traffic; avoids premature metric counting |
| Multi-tier application: EC2 web tier, DynamoDB table, Aurora replicas | **AWS Auto Scaling scaling plan** (by tag or stack) | One strategy across multiple resources |
| Rolling out a new AMI with zero downtime | **Instance refresh** | Gradual replacement with health protection |

## 6. Best Practices

1. **Start with target tracking.** It is the easiest policy to manage and works for most workloads. Add step or scheduled scaling only when needed.
2. **Use multiple AZs** and, where possible, multiple instance types, to improve availability and Spot capacity access.
3. **Set sensible min and max limits.** Min protects availability; max protects your budget.
4. **Choose a metric that scales with capacity.** The metric should rise when load rises and fall when instances are added (average CPU or requests per target are good; total request count is not).
5. **Configure instance warmup** accurately so new instances are not counted before they are ready, preventing over-scaling.
6. **Enable ELB health checks** when using a load balancer so unhealthy application instances are replaced, not just failed hardware.
7. **Use detailed (1-minute) monitoring** for faster scaling responses to rapid changes.
8. **Test predictive scaling in ForecastOnly mode** before allowing it to act.
9. **Combine strategies:** scheduled or predictive for the baseline, dynamic scaling for the unexpected.
10. **Design instances to be stateless.** Store session data and files outside the instance (ElastiCache, DynamoDB, S3, EFS) so instances can be terminated freely.
11. **Use scale-in protection and lifecycle hooks** for workloads that must finish work before termination.
12. **Monitor and review:** use CloudWatch metrics, scaling activity history and notifications to tune policies over time.

## 7. Quick Revision Summary

- **EC2 Auto Scaling** manages groups of EC2 instances with **min / desired / max** capacity, launch templates, health checks and multi-AZ placement.
- **Scaling options:** manual, fixed-size maintenance, **scheduled**, **dynamic** (target tracking, step, simple) and **predictive**.
- **Target tracking** = thermostat style, recommended default; **step scaling** = tiered response to alarm breaches; **simple scaling** = one action plus cooldown (legacy).
- **Predictive scaling** forecasts cyclical load with machine learning and scales ahead of time; use **ForecastOnly** to test.
- **Warm pools, lifecycle hooks, instance refresh and Capacity Rebalancing** improve startup speed, control and resilience.
- **AWS Auto Scaling** uses **scaling plans** to configure scaling across ASGs, ECS, Spot Fleet, DynamoDB and Aurora, with strategies to optimize for availability, cost or balance.
- For predictive-only needs, AWS recommends **predictive scaling policies directly on the ASG** rather than scaling plans.
