# Edge Networking Services and Their Use Cases

**Exam context:** AWS Certified Solutions Architect – Associate (SAA-C03), Domain 3: High-Performing Architectures, Task 3.4 (high-performing and scalable network architectures).
**Sources:** AWS documentation for Amazon CloudFront, AWS Global Accelerator, Lambda@Edge and CloudFront Functions, AWS WAF and AWS Shield (docs.aws.amazon.com).

---

## 1. What "edge networking" means

AWS runs a global network of **edge locations** and **Regional Edge Caches** that sit close to end users, far from the Regions where your workloads live. Edge networking services use this footprint to:

- **Reduce latency** by serving or terminating traffic near the viewer.
- **Offload origins** by caching and absorbing traffic at the edge.
- **Improve availability** by routing around unhealthy endpoints.
- **Improve security** by filtering malicious traffic before it reaches your VPC.

The two flagship services for this exam topic are **Amazon CloudFront** (content delivery) and **AWS Global Accelerator** (network-layer acceleration). Related services you should know are Amazon Route 53, Lambda@Edge, CloudFront Functions, AWS WAF and AWS Shield.

## 2. Amazon CloudFront

### 2.1 Overview

CloudFront is a **content delivery network (CDN)**. You create a **distribution** that points to one or more **origins**. When a viewer requests content, CloudFront routes the request to a nearby edge location. If the object is in the cache (a **cache hit**), it is returned immediately. If not (a **cache miss**), CloudFront fetches it from the origin, returns it, and caches it for later requests.

Between the edge locations and the origin there are **Regional Edge Caches**, a larger middle caching tier. They keep objects longer than individual edge locations, which reduces the number of requests reaching the origin.

### 2.2 Supported origins

- Amazon S3 buckets (the most common static-content origin)
- Elastic Load Balancing (Application Load Balancer, and Network Load Balancer through a VPC origin)
- Amazon EC2 instances or any custom HTTP(S) origin, including on-premises servers
- Amazon API Gateway
- AWS Lambda function URLs
- AWS Elemental MediaStore containers and MediaPackage channels
- **Origin groups** for failover: a primary and a secondary origin, with automatic failover on specified HTTP status codes or connection failures

Data transfer from AWS origins (S3, ELB, API Gateway and similar) to CloudFront is free of charge.

### 2.3 Key features

| Feature | What it does |
|---|---|
| **Caching and cache policies** | Control TTLs and which headers, cookies and query strings form the cache key. A better cache hit ratio means lower latency and cost. |
| **Origin Access Control (OAC)** | Lets CloudFront access a private S3 bucket so users cannot bypass the CDN. OAC replaces the older Origin Access Identity (OAI). |
| **Signed URLs and signed cookies** | Restrict content to authorized users (paid content, private downloads). Signed URLs suit single files. Signed cookies suit many files. |
| **HTTPS and custom domains** | Use AWS Certificate Manager (ACM) certificates. For CloudFront, the certificate must be in **us-east-1**. |
| **Field-level encryption** | Encrypts specific sensitive form fields at the edge so only designated back-end services can decrypt them. |
| **Geo restriction** | Allow or block countries (geographic restrictions). |
| **Origin Shield** | An additional centralized caching layer that further reduces origin load. |
| **Price classes** | Limit which edge locations are used to reduce cost. |
| **Real-time and standard logs** | Monitor requests and feed analytics pipelines. |
| **Continuous deployment** | Test configuration changes on a portion of live traffic. |

### 2.4 Running code at the edge

- **CloudFront Functions:** very lightweight JavaScript functions that run at the edge locations. They are suited to high-volume, sub-millisecond tasks such as URL rewrites and redirects, header manipulation, cache key normalization and simple request authorization (for example JWT validation).
- **Lambda@Edge:** more powerful functions (Node.js or Python) that run at Regional Edge Caches. They are suited to heavier logic such as calling external services, longer processing, or accessing the request body.

Both can be triggered on viewer request, viewer response, origin request and origin response events (Lambda@Edge supports all four; CloudFront Functions support the viewer events only).

### 2.5 Appropriate use cases

1. **Static website and asset acceleration.** Serve images, CSS, JavaScript and downloads from S3 with CloudFront in front. This is the classic pattern and the most frequently tested.
2. **Dynamic content acceleration.** CloudFront can also help with non-cacheable content (APIs, personalized pages). Connections are terminated at the nearby edge and requests travel to the origin over the AWS backbone using persistent connections, which is faster than a client going over the public internet.
3. **Video streaming.** On-demand and live streaming (HLS, DASH, CMAF) in combination with AWS Elemental MediaPackage or MediaStore.
4. **Software distribution.** Large file downloads such as installers, game patches and firmware updates.
5. **Securing S3 content.** Keep the bucket private and use OAC plus signed URLs/cookies.
6. **Protecting web applications.** Attach AWS WAF to the distribution and benefit from AWS Shield Standard (included at no extra cost) against network and transport layer DDoS attacks.
7. **Edge customization.** A/B testing, redirects, geo-based content, header injection and authentication with Functions or Lambda@Edge.
8. **Origin failover.** Use origin groups to fail over from a primary to a secondary origin (for example, S3 buckets in two Regions).
9. **Global API delivery.** Place CloudFront in front of API Gateway or an ALB to reduce latency and absorb traffic spikes.
10. **SaaS and multi-tenant applications.** Multi-tenant distributions (CloudFront SaaS Manager) let SaaS providers manage many customer domains with shared configuration.

### 2.6 When CloudFront is *not* the best fit

- Non-HTTP/HTTPS protocols such as arbitrary TCP or UDP traffic (use Global Accelerator).
- Applications that require **static IP addresses** for clients to allow-list (CloudFront IPs change; use Global Accelerator).
- Fast, deterministic **regional failover** with no dependency on DNS caching (use Global Accelerator).

## 3. AWS Global Accelerator

### 3.1 Overview

Global Accelerator improves the **availability and performance** of applications for local and global users. It gives you **two static anycast IPv4 addresses** (four addresses with dual-stack: two IPv4 and two IPv6) that act as fixed entry points. Traffic enters the AWS global network at the **edge location closest to the user** and then travels over the AWS backbone to the optimal healthy endpoint, instead of crossing many internet hops.

Important facts:

- It operates at **Layer 4 (TCP and UDP)**, so it is protocol-agnostic and does not cache content.
- The static IPs stay with your accelerator for as long as it exists, even if disabled. They are released when the accelerator is deleted.
- You can **bring your own IP addresses (BYOIP)** for standard accelerators.
- It is a global service, but you must use the **US West (Oregon) Region (us-west-2)** to create and manage accelerators through the API or CLI.
- It reacts quickly to health or configuration changes and shifts traffic to healthy endpoints, without waiting for DNS TTLs to expire.

### 3.2 Core components

| Component | Description |
|---|---|
| **Accelerator** | The top-level resource: either *standard* or *custom routing*. |
| **Static IP addresses** | Anycast addresses assigned to the accelerator. |
| **DNS name** | Each accelerator also gets a DNS name that maps to the static IPs. |
| **Listener** | Processes inbound connections on the ports and protocol (TCP, UDP or both) you specify. |
| **Endpoint group** | One per AWS Region. Has a **traffic dial** (0–100%) to control how much traffic goes to the Region, plus health check settings. |
| **Endpoint** | The resource receiving traffic: Application Load Balancer, Network Load Balancer, EC2 instance, or Elastic IP address. Endpoints can have weights. |

### 3.3 Accelerator types

- **Standard accelerator:** routes traffic to the optimal healthy endpoint based on health, client location and the policies you configure. It supports ALB, NLB, EC2 and Elastic IP endpoints in one or more Regions.
- **Custom routing accelerator:** lets application logic map specific users or sessions **deterministically to a particular EC2 instance and port** inside VPC subnets. It is used for cases where your application decides which server handles which user.

### 3.4 Appropriate use cases

1. **Global applications needing static entry points.** Clients or firewalls need only two fixed IPs to allow-list, no matter how many back-end endpoints change.
2. **Non-HTTP workloads.** Gaming (UDP), IoT, VoIP and other TCP/UDP traffic that CloudFront cannot cache or handle.
3. **Multi-Region active-active or active-passive architectures.** Distribute traffic across Regions and fail over within seconds when a Region or endpoint becomes unhealthy.
4. **Blue/green and gradual migrations.** Use the traffic dial and endpoint weights to shift traffic gradually between Regions or stacks.
5. **Performance improvement for dynamic, latency-sensitive apps.** Moving user traffic onto the AWS backbone close to the user reduces jitter and packet loss.
6. **Gaming and real-time session routing.** Custom routing accelerators assign players to specific game servers.
7. **Preserving client IP.** Client IP address preservation is supported for several endpoint types (ALB and EC2 endpoints, for example), which helps with logging and security rules.
8. **Replacing regional static IPs.** A single global static IP set can stand in front of regional load balancers whose addresses would otherwise vary per Region.

## 4. CloudFront vs. Global Accelerator

| Aspect | Amazon CloudFront | AWS Global Accelerator |
|---|---|---|
| **Primary purpose** | Content delivery with caching | Network-layer routing and acceleration |
| **OSI layer / protocols** | Layer 7: HTTP, HTTPS, WebSocket | Layer 4: TCP and UDP |
| **Caching** | Yes (edge and regional caches) | No |
| **Client entry point** | DNS name (IPs vary) | Two static anycast IPs |
| **Failover** | Origin groups (per request/status code) | Health checks with fast endpoint/Region failover, traffic dial |
| **Typical origins/endpoints** | S3, ALB, EC2, API Gateway, custom origin | ALB, NLB, EC2, Elastic IP |
| **Edge compute** | CloudFront Functions, Lambda@Edge | None |
| **Best for** | Static and streaming content, web/API acceleration | Gaming, VoIP, IoT, static-IP requirements, multi-Region failover |

**Rule of thumb for the exam:**

- *Cacheable HTTP(S) content, S3 delivery, video, signed access* → **CloudFront**.
- *Need static IPs, TCP/UDP, instant regional failover, non-HTTP* → **Global Accelerator**.

## 5. Related edge and global services

- **Amazon Route 53:** DNS with latency-based, geolocation, geoproximity, weighted and failover routing policies. Unlike Global Accelerator, failover and routing depend on DNS resolution and TTLs, and clients may cache old answers.
- **AWS WAF:** web application firewall that integrates with CloudFront (and ALB, API Gateway, AppSync). It blocks SQL injection, XSS, bad bots and rate-based abuse.
- **AWS Shield:** Standard (automatic, free) protects against common network/transport DDoS. Advanced adds enhanced detection, response team support and cost protection, and works with CloudFront, Global Accelerator, Route 53, ALB and Elastic IPs.
- **AWS Wavelength, Local Zones and Outposts:** extend AWS infrastructure to the telco edge, metro areas or on-premises for ultra-low latency compute (distinct from the content-delivery edge, but part of the broader edge picture).
- **Amazon S3 Transfer Acceleration:** speeds up uploads to a bucket over long distances by routing through the nearest edge location, a good fit for global uploads rather than downloads.

## 6. Design best practices

1. **Maximize cache hit ratio.** Keep the cache key minimal (forward only the headers, cookies and query strings you need) and set sensible TTLs.
2. **Lock down the origin.** Use OAC for S3. For ALB or custom origins, require a secret custom header or use VPC origins/the CloudFront managed prefix list in security groups.
3. **Enforce HTTPS.** Redirect HTTP to HTTPS and use modern TLS policies.
4. **Layer protection.** Combine CloudFront + WAF + Shield for internet-facing apps.
5. **Choose the right price class** if users are concentrated in specific geographies.
6. **Use origin failover** for critical static content.
7. **Combine services when appropriate.** For example, CloudFront for the web front end and Global Accelerator for a separate TCP/UDP service. Do not put them in series for the same HTTP traffic without a clear reason.
8. **Monitor.** Use CloudWatch metrics, CloudFront logs, and Global Accelerator flow logs and health checks.

## 7. Scenario cheat sheet

| Scenario | Best answer |
|---|---|
| Website with images stored in S3; users worldwide complain of slow loading | CloudFront in front of S3 |
| Only subscribed users should download video files | CloudFront with signed URLs/cookies, S3 with OAC |
| Customer firewall can only allow-list a couple of IP addresses for a global app on ALBs | Global Accelerator |
| Multiplayer UDP game with players worldwide and servers in several Regions | Global Accelerator (custom routing if players must reach specific servers) |
| Need to fail over to another Region within seconds, without waiting for DNS TTL | Global Accelerator |
| Add security headers or redirect URLs with minimal latency and cost | CloudFront Functions |
| Complex request logic requiring network calls at the edge | Lambda@Edge |
| Block SQL injection on a CloudFront-served site | AWS WAF attached to the distribution |
| Global users upload large files to one S3 bucket | S3 Transfer Acceleration |
| Primary S3 bucket fails; static site must keep serving | CloudFront origin group with a secondary bucket |

## 8. Quick revision points

- CloudFront = CDN, **caching**, HTTP/HTTPS, many origin types, edge compute, signed URLs, OAC.
- Global Accelerator = **no caching**, TCP/UDP, **two static anycast IPs**, AWS backbone, endpoint health checks, traffic dials.
- ACM certificates for CloudFront must be in **us-east-1**.
- Global Accelerator control-plane calls use **us-west-2**.
- CloudFront Functions (edge locations, lightweight, viewer events) vs. Lambda@Edge (Regional Edge Caches, more power, all four event types).
- Shield Standard is free and automatic. WAF is a paid add-on you attach.
- Route 53 routes via DNS; Global Accelerator routes via anycast IPs and is not subject to DNS caching.
