# How to design network architecture (subnet tiers, routing, IP addressing)

## VPC Foundations & IP Addressing Strategy

A Virtual Private Cloud (VPC) is an isolated virtual network dedicated to your AWS account. Designing your IP addressing scheme 
thoughtfully prevents overlapping address spaces, facilitates seamless hybrid cloud integration, and simplifies routing.

### CIDR Blocks and IP Addressing

#### CIDR Selection Best Practices

Use Private IPv4 Ranges:

10.0.0.0/8 (16,777,216 addresses) — Standard for large enterprises with complex internal networks.

172.16.0.0/12 (1,048,576 addresses) — Commonly used for medium-to-large cloud deployments.

192.168.0.0/16 (65,536 addresses) — Best suited for small deployments or isolated environments.

#### Sizing Your VPC:

Standard VPC sizes range between /16 (65,536 IPs) and /24 (256 IPs). AWS allows VPC sizes from /28 to /16.

Avoid over-constraining CIDRs; allocate sufficient headroom for containerized workloads (e.g., Amazon EKS with VPC CNI assigns native pod IPs) and scale-out events.

#### Preventing Overlaps:

Allocate distinct CIDR blocks to each VPC across regions, environments (Development, Staging, Production), and on-premises data centers to facilitate VPC Peering and AWS Transit Gateway routing without Network Address Translation (NAT) collisions.

#### Secondary CIDRs and IPv6 Design

Secondary IPv4 CIDR Blocks: If primary address pools become constrained, attach secondary IPv4 CIDR blocks (including non-routable CGNAT ranges like 100.64.0.0/10) to existing VPCs for container networking or internal resources.

IPv6 Dual-Stack Architecture:

AWS allows assigning a /56 IPv6 CIDR block to a VPC.

Subnets receive /64 IPv6 prefixes.

IPv6 uses globally unique unicast addresses (GUA), eliminating the need for NAT devices (utilizing Egress-Only Internet Gateways instead for outbound-only access).


### Why CIDR planning matters

Proper IP address planning helps you:

- Divide a network into smaller segments.
- Avoid overlapping network ranges.
- Connect VPCs through peering or transit networks.
- Establish connectivity with on-premises networks.
- Organize resources according to security requirements.

**Security consideration** Overlapping CIDR ranges can complicate routing and connectivity between networks. A well-planned IP addressing strategy reduces these problems.

# Understanding Public and Private Subnets

Subnet design is one of the most important concepts in secure VPC architecture.

## What is a Subnet?

A subnet is a segment of a VPC's IP address range.

Subnets help organize resources into separate network segments based on their purpose.

For example, a company might create separate subnets for:

- Public-facing web applications.
- Internal application servers.
- Databases.
- Management and administration systems.

Subnet separation supports network organization, but **a subnet is not, by itself, a complete security boundary**.

## Public Subnet

A public subnet is a subnet whose associated route table has a route directing internet-bound IPv4 traffic to an Internet Gateway.

Resources also need suitable addressing and security configuration to communicate directly with the internet.

### Typical resources

- Public-facing load balancers.
- Internet-facing web servers, when required.
- Network appliances that need public connectivity.


#### Subnet Tiering and Multi-AZ Layout

High availability requires distributing resources across multiple Availability Zones (AZs) within an AWS Region. A structured subnet layout isolates components according to their accessibility, security posture, and internet dependency.

The 3-Tier VPC Architecture

```
+-----------------------------------+
                       |         Internet Gateway          |
                       +-----------------+-----------------+
                                         |
    +------------------------------------+------------------------------------+
    | AZ-a                               | AZ-b                               |
    |                                    |                                    |
    |  +------------------------------+  |  +------------------------------+  |
    |  |  Public Subnet (Web / ALB)   |  |  |  Public Subnet (Web / ALB)   |  |
    |  |  CIDR: 10.0.1.0/24           |  |  |  CIDR: 10.0.2.0/24           |  |
    |  |  [ NAT Gateway A ]           |  |  |  [ NAT Gateway B ]           |  |
    |  +--------------+---------------+  |  +--------------+---------------+  |
    |                 |                  |                 |                  |
    |  +--------------v---------------+  |  +--------------v---------------+  |
    |  |  Private Subnet (App Tier)   |  |  |  Private Subnet (App Tier)   |  |
    |  |  CIDR: 10.0.10.0/24          |  |  |  CIDR: 10.0.20.0/24          |  |
    |  +--------------+---------------+  |  +--------------+---------------+  |
    |                 |                  |                 |                  |
    |  +--------------v---------------+  |  +--------------v---------------+  |
    |  | Isolated Subnet (Database)   |  |  | Isolated Subnet (Database)   |  |
    |  | CIDR: 10.0.100.0/24          |  |  | CIDR: 10.0.200.0/24          |  |
    |  +------------------------------+  |  +------------------------------+  |
    +------------------------------------+------------------------------------+

    ```

### Security considerations

Public-facing resources are more exposed to internet-originated traffic.

To reduce risk:

- Expose only the services that must be publicly accessible.
- Restrict administrative access.
- Use security groups to control inbound connections.
- Monitor network traffic.
- Avoid placing databases and other sensitive backend systems in directly internet-accessible configurations.

**Important:** A public subnet does not mean every resource in that subnet is automatically accessible from the internet.

## Private Subnet

A private subnet generally has no direct route to an Internet Gateway for internet-bound traffic.

It is commonly used for resources that do not need direct inbound internet connectivity.

### Typical resources

- Application servers.
- Database servers.
- Internal APIs.
- Background processing services.
- Internal business applications.

A private subnet can still have outbound connectivity through a NAT Gateway or other network path, depending on its routing configuration.

### Security benefits

- Reduces direct internet exposure.
- Separates backend systems from public-facing components.
- Supports layered access controls.
- Helps limit the potential impact of a compromised public-facing system.

### Important distinction

**Private does not mean completely isolated.**

A resource in a private subnet may still communicate with other VPC resources, connected networks, or external destinations through configured routes and permitted security rules.

## Public vs. Private Subnets

| Feature | Public subnet | Private subnet |
|---|---|---|
| Typical purpose | Public-facing services | Internal workloads |
| Route to Internet Gateway | Usually present for internet-bound IPv4 traffic | Usually absent for direct internet access |
| Direct inbound internet access | Possible when addressing, routing, and security permit | Generally not available through a direct internet route |
| Outbound internet access | Possible with suitable routing and security | Possible through NAT or other configured paths |
| Common resources | Public load balancers | Application servers and databases |
| Security objective | Minimize exposure | Limit direct external reachability |

### Example architecture

Consider an online shopping platform:

- **Public tier:** A load balancer receives customer requests.
- **Private application tier:** Application servers process orders.
- **Private database tier:** Database servers store customer and order records.

Customers connect to the public endpoint. The application tier communicates with the database tier through specifically authorized connections.

This design separates internet-facing access from sensitive internal processing.

# Route Tables and Network Traffic Flow

## What is a Route Table?

A route table contains rules that determine where network traffic is directed.

Each route includes a destination network and a target.

A subnet uses an associated route table to determine how its outbound traffic is routed.

### Common route targets

- Local VPC routing.
- Internet Gateway.
- NAT Gateway.
- Virtual Private Gateway.
- Transit Gateway.
- VPC endpoint, depending on endpoint type.

## Why Are Route Tables Important for Security?

Security groups determine which traffic is permitted at a resource's network interface, while route tables determine where traffic can be directed.

Both must be considered when evaluating network reachability.

### Example: Public subnet

A public subnet might have:

- A local route for communication within the VPC.
- A default IPv4 route to an Internet Gateway.

### Example: Private application subnet

A private application subnet might have:

- A local route for internal VPC communication.
- A default IPv4 route to a NAT Gateway for outbound internet connectivity.

### Example: Isolated database subnet

A database subnet might have only the local VPC route and any additional routes strictly required by the application architecture.

It would not need a default internet route if it has no internet connectivity requirement.

### Security best practice

**Use the minimum routes necessary to support the workload.**

Unnecessary routes can create connectivity paths that increase exposure or make network behavior harder to understand.

---
### Subnet Characteristics

| Subnet Tier | Inbound Access | Outbound Access | Primary Workloads |
| :--- | :--- | :--- | :--- |
| **Public Subnet** | Direct via IGW | Direct via IGW | Application Load Balancers (ALB), Bastion Hosts, NAT Gateways |
| **Private Subnet (App)** | Restricted via ALB / Internal Route | Indirect via NAT Gateway | Application Servers, Container Instances, Internal APIs |
| **Isolated Subnet (Data)** | Restricted via App Tier only | No Internet Access | Amazon RDS, DynamoDB VPC Endpoints, Elasticache, HSMs |

### AWS Reserved IP Addresses

For any assigned subnet CIDR block (e.g., `/24` providing 256 addresses), AWS reserves **5 IP addresses** for internal operations:
- `.0`: Network address.
- `.1`: AWS VPC Router address.
- `.2`: AWS DNS (AmazonProvidedDNS) server address.
- `.3`: Reserved by AWS for future use.
- `.255`: Network broadcast address (VPC does not support standard broadcast).

## 3. Routing Architecture and Traffic Control

Routing controls how network packets transit between subnets, the internet, and remote networks. Every subnet must be associated with a Route Table.

### Route Table Configurations

#### Public Subnet Route Table
Directs all external traffic (`0.0.0.0/0`) to the Internet Gateway (IGW).

```text
Destination     Target
-----------------------------------------
10.0.0.0/16     local
0.0.0.0/0       igw-0123456789abcdef0
```

#### Private Subnet Route Table (App Tier)
Directs local VPC traffic locally and external outbound requests to a managed NAT Gateway located in a public subnet.

```text
Destination     Target
-----------------------------------------
10.0.0.0/16     local
0.0.0.0/0       nat-0123456789abcdef0
```

#### Isolated Subnet Route Table (DB Tier)
Restricts routing strictly to internal ranges with no target set for `0.0.0.0/0`.

```text
Destination     Target
-----------------------------------------
10.0.0.0/16     local
```

### Internet Connectivity Components

- **Internet Gateway (IGW):** Horizontally scaled, redundant, highly available component allowing bidirectional communication between instances in public subnets and the internet.
- **NAT Gateway:** Managed Service providing IPv4 outbound internet access for private subnets while blocking unsolicited inbound connections. Deploy one NAT Gateway per Availability Zone to avoid cross-AZ latency and cross-AZ data transfer costs.
- **Egress-Only Internet Gateway (EOIGW):** Stateful gateway providing outbound-only IPv6 traffic routing for private workloads.

## 4. Network Security and Isolation

Security in AWS network architecture operates via a defense-in-depth model utilizing Security Groups, Network Access Control Lists (NACLs), and specialized gateways.

```
       [ External / Public Traffic ]
                    |
                    v
    +----------------------------------+
    |  Network ACL (Subnet Boundary)   | <-- Stateless Layer (Subnet level)
    +----------------+-----------------+
                     |
                     v
    +----------------------------------+
    | Security Group (Instance level)  | <-- Stateful Layer (ENI level)
    +----------------+-----------------+
                     |
                     v
             [ EC2 / Container ]
```

### Security Groups vs. Network ACLs

| Feature | Security Groups (SG) | Network ACLs (NACL) |
| :--- | :--- | :--- |
| **Operating Layer** | Elastic Network Interface (ENI) level | Subnet boundary level |
| **State** | **Stateful** (Return traffic automatically allowed) | **Stateless** (Inbound and outbound rules evaluated separately) |
| **Rule Types** | Allow rules only | Allow and Deny rules |
| **Evaluation** | All rules evaluated before granting access | Rules processed in strict numerical order |

### VPC Endpoints (AWS PrivateLink)

To connect to AWS services (e.g., S3, DynamoDB, Systems Manager) without traversing the public internet, use VPC Endpoints:

1. **Gateway Endpoints:**
   - Free targets declared in route tables.
   - Supported services: **Amazon S3** and **Amazon DynamoDB**.
2. **Interface Endpoints (PrivateLink):**
   - Elastic Network Interfaces (ENIs) with private IPs placed inside your subnets.
   - Used for services such as SNS, SQS, EC2 Messages, Systems Manager, and custom private microservices.

## 5. Multi-VPC and Hybrid Cloud Architecture

As organizations expand, single-VPC architectures transition to multi-VPC topologies governed by centralized routing control.

### VPC Peering vs. AWS Transit Gateway

```
VPC Peering (Mesh)                    AWS Transit Gateway (Hub-and-Spoke)

  [VPC A] <-----> [VPC B]                   [VPC A]       [VPC B]
     ^             ^                           \             /
     |             |                            v           v
     v             v                          +---------------+
  [VPC C] <-----> [VPC D]                     | Transit Gateway|
                                              +-------+-------+
                                                      |
                                                      v
                                               [ On-Premises ]
```

- **VPC Peering:**
  - One-to-one networking connection between two VPCs.
  - Non-transitive routing (VPC A peering with B, and B with C, does NOT allow A to communicate with C).
  - Cost-effective for low VPC counts (no hourly connection fee, only standard data transfer charges).
- **AWS Transit Gateway (TGW):**
  - Central regional router acting as a network hub.
  - Supports transitive routing between thousands of VPCs, AWS Direct Connect, and VPN connections.
  - Simplifies routing management using central route tables.

### Hybrid Connectivity

- **AWS Site-to-Site VPN:** IPsec VPN tunnels established over the public internet between on-premises customer gateways and AWS Transit Gateway or Virtual Private Gateway (VGW).
- **AWS Direct Connect (DX):** Dedicated physical fiber connection from on-premises data centers directly to AWS, delivering lower latency, higher bandwidth, and consistent network performance.
