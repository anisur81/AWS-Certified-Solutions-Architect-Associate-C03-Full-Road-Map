
# Container Orchestration on AWS – Amazon ECS and Amazon EKS

## 1. Introduction to Container Orchestration

Container orchestration automates the deployment, scheduling, scaling, networking, and lifecycle management of containerized applications across a cluster of compute resources.

A container packages an application with its runtime, libraries, and dependencies. Orchestration becomes important when an application has multiple containers, needs to scale, or must remain available when individual containers or compute resources fail.

### Why use container orchestration?

- **Deployment:** deploy and update containerized applications consistently.
- **Scheduling:** place containers on suitable compute resources.
- **Scaling:** increase or decrease application capacity as demand changes.
- **Self-healing:** replace failed tasks or Pods.
- **Networking and service discovery:** enable communication between application components.
- **Availability:** distribute workloads across infrastructure and Availability Zones.
- **Resource management:** allocate CPU and memory to workloads.

## 2. AWS Container Orchestration Services

AWS provides two major orchestration services:

| Service | Orchestration technology | Best understood as |
|---|---|---|
| Amazon ECS | AWS-native orchestration | AWS-managed container orchestration |
| Amazon EKS | Kubernetes | Managed Kubernetes on AWS |

Both services can run containers on Amazon EC2 or AWS Fargate. The orchestration service and the compute capacity are separate concepts: ECS or EKS manages workloads, while EC2 or Fargate provides the compute environment.

## 3. Amazon Elastic Container Service (Amazon ECS)

Amazon ECS is a fully managed AWS container orchestration service. It helps deploy, manage, and scale containerized applications without requiring you to operate your own Kubernetes control plane.

### 3.1 Main ECS components

| Component | Purpose |
|---|---|
| **Cluster** | Logical grouping of tasks and services, with associated compute capacity. |
| **Task definition** | Blueprint describing one or more containers, images, CPU/memory, ports, environment variables, volumes, and IAM roles. |
| **Task** | A running instance of a task definition. |
| **Service** | Maintains a desired number of running tasks and replaces failed tasks. |
| **Container image** | Packaged application artifact, commonly stored in Amazon ECR. |
| **Capacity provider** | Connects workloads to compute capacity and helps manage scaling. |

### 3.2 ECS architecture / deployment flow

```text
Developer
   |
   v
Build container image (Docker)
   |
   v
Amazon ECR (image registry)
   |
   v
ECS Task Definition (application blueprint)
   |
   v
ECS Cluster
   |
   +------ ECS Service (maintains desired task count)
   |             |
   |             v
   |        ECS Tasks
   |        (containers)
   |
   +------ Compute capacity
                 |
          +------+------+
          |             |
       AWS Fargate   Amazon EC2 /
                     ECS Managed
                     Instances
```

### 3.3 ECS compute options

- **AWS Fargate:** serverless container compute. AWS provisions and manages the underlying infrastructure; you specify task CPU and memory. You do not manage EC2 instances.
- **Amazon EC2:** you select and manage the EC2 instances that provide container capacity. This offers greater infrastructure control.
- **Amazon ECS Managed Instances:** AWS manages the lifecycle of the underlying EC2 instances while providing access to EC2 instance choices and capabilities.

ECS capacity providers can manage or connect capacity for Fargate, Fargate Spot, EC2 Auto Scaling groups, and ECS Managed Instances. Fargate Spot is intended for interruption-tolerant workloads and can be interrupted with a warning.

### 3.4 ECS service features

- Maintains the configured desired number of tasks.
- Replaces stopped or unhealthy tasks.
- Supports service auto scaling.
- Integrates with Elastic Load Balancing to distribute application traffic.
- Integrates with IAM, Amazon VPC, Amazon ECR, CloudWatch, and other AWS services.

**Example:** A web application runs three ECS tasks behind an Application Load Balancer. If one task fails, the ECS service scheduler starts a replacement to maintain the desired count.

## 4. Amazon Elastic Kubernetes Service (Amazon EKS)

Amazon EKS is a managed Kubernetes service. Kubernetes is an open-source container orchestration platform. EKS runs and manages the Kubernetes control plane, while you choose how to provide compute capacity for application workloads.

EKS is useful when an organization needs Kubernetes APIs, ecosystem tools, portability, or Kubernetes-based operating practices.

### 4.1 Main Kubernetes / EKS components

| Component | Purpose |
|---|---|
| **EKS cluster** | Kubernetes environment containing the control plane and registered compute resources. |
| **Control plane** | Runs Kubernetes management components, including the API server and cluster state store. AWS manages its availability. |
| **Node** | Compute machine that runs application Pods. |
| **Pod** | Smallest deployable Kubernetes unit; contains one or more closely related containers. |
| **Deployment** | Defines the desired state and manages replicated Pods and rolling updates. |
| **Service** | Provides a stable network endpoint for accessing a set of Pods. |
| **Namespace** | Logical separation of Kubernetes resources within a cluster. |

### 4.2 EKS architecture

```text
Developer / kubectl / CI-CD
          |
          v
     EKS API Server
          |
          v
   AWS-managed Control Plane
          |
          v
   Kubernetes Scheduler
          |
          v
      Worker Nodes
   (EC2 / Fargate / Auto Mode)
          |
          v
         Pods
          |
          v
      Containers
```

The EKS control plane is distributed across multiple Availability Zones. Application Pods run on compute capacity associated with the cluster; the control plane and worker compute are distinct.

### 4.3 EKS compute options

- **EKS Managed Node Groups:** AWS manages provisioning and lifecycle operations for groups of EC2 worker nodes, including updates and scaling workflows. You remain responsible for workload and relevant node configuration.
- **Self-managed nodes:** you manage the EC2 instances, scaling, updates, and maintenance.
- **AWS Fargate:** runs selected Kubernetes Pods without requiring you to manage worker EC2 instances. Fargate profiles determine which Pods run on Fargate.
- **EKS Auto Mode:** extends AWS management to compute and key cluster infrastructure operations, including provisioning, scaling, and maintenance.
- **EKS Hybrid Nodes:** allows supported on-premises or edge infrastructure to act as nodes in an EKS cluster.

### 4.4 EKS capabilities

- Kubernetes-native deployment and scheduling.
- Horizontal scaling of application workloads.
- Rolling updates and rollback through Kubernetes controllers.
- Service discovery and networking through Kubernetes Services and related components.
- Integration with IAM for AWS access, VPC networking, ECR, Elastic Load Balancing, CloudWatch, and other AWS services.

**Example:** A microservices application uses separate Kubernetes Deployments for its frontend, API, and background workers. Kubernetes schedules Pods across nodes and maintains the desired replica count.

## 5. Amazon ECS vs. Amazon EKS

| Comparison | Amazon ECS | Amazon EKS |
|---|---|---|
| Orchestrator | AWS-native ECS | Kubernetes |
| Learning curve | Generally simpler for AWS-focused teams | Requires Kubernetes knowledge |
| Workload unit | Task / container | Pod / container |
| Workload controller | ECS Service | Kubernetes Deployment, StatefulSet, etc. |
| Compute | EC2, Fargate, ECS Managed Instances | EC2 nodes, Fargate, Auto Mode, Hybrid Nodes |
| Portability | More AWS-specific | Kubernetes ecosystem supports portability |
| Best fit | AWS-native applications and simpler operations | Kubernetes-standard platforms and complex Kubernetes workloads |

### When should you choose ECS?

Choose ECS when:
- You want a straightforward AWS-native orchestration service.
- Your workloads are primarily hosted on AWS.
- You prefer less Kubernetes operational complexity.
- You want to run containers on Fargate or EC2 with AWS integrations.

### When should you choose EKS?

Choose EKS when:
- Your organization already uses Kubernetes.
- You need Kubernetes APIs, controllers, and ecosystem tools.
- You want Kubernetes-compatible deployment patterns across environments.
- Your platform engineering teams have the skills to operate Kubernetes workloads.

Neither service is universally better. Select based on workload requirements, team expertise, operational complexity, portability, and cost.

## 6. Security, Monitoring, and Best Practices

### Security
- Apply least-privilege IAM permissions.
- Use IAM task roles for ECS applications and appropriate IAM-to-Kubernetes workload identity mechanisms for EKS.
- Store secrets in AWS Secrets Manager or AWS Systems Manager Parameter Store rather than embedding them in images.
- Scan and protect container images in Amazon ECR.
- Use private subnets where appropriate and restrict inbound network access.
- Patch container images, nodes, and dependencies.
- Apply Kubernetes RBAC and network policies where appropriate in EKS.

### Monitoring and operations
- Use Amazon CloudWatch for logs, metrics, and alarms.
- Use Container Insights where appropriate for container-level observability.
- Use AWS CloudTrail to record relevant AWS API activity.
- Define health checks, resource requests/limits, scaling policies, and deployment strategies.
- Test recovery, upgrades, and rollback procedures.

### Cost considerations
- ECS and EKS orchestration do not mean that compute and supporting resources are free.
- EC2, Fargate, storage, load balancers, data transfer, logging, and other resources can incur charges.
- EKS has a cluster management charge; application compute and other AWS resources are billed separately. Check current regional pricing before deployment.
- Right-size CPU and memory, scale workloads appropriately, and consider Spot capacity only for interruption-tolerant workloads.

## 7. SAA-C03 Exam Tips

- **ECS = AWS-native container orchestration.**
- **EKS = managed Kubernetes service.**
- **Fargate = serverless compute for containers; it can be used with both ECS and EKS.**
- **EC2 = customer-managed compute capacity** when you choose self-managed EC2 options.
- **ECS task definition = blueprint; task = running instance; service = maintains desired task count.**
- **Kubernetes Pod = smallest deployable unit; Deployment = manages replicated Pods; Service = stable network access to Pods.**
- Do not confuse the orchestration layer (ECS/EKS) with the compute layer (EC2/Fargate).
- For a simple AWS-native container workload with minimal Kubernetes overhead, consider ECS with Fargate.
- For Kubernetes compatibility and Kubernetes-native tooling, consider EKS.
