 
# How to Migrate Applications into Containers on AWS

## 1. Introduction

Application containerization is the process of packaging an application, its runtime, libraries, dependencies, and configuration into a standardized container image.

Containers provide portability, consistency, scalability, resource efficiency, and faster application deployment.

AWS supports containerized applications through:

- **Amazon ECS:** Fully managed container orchestration.
- **Amazon EKS:** Managed Kubernetes service.
- **AWS Fargate:** Serverless compute for containers.
- **Amazon ECR:** Container image registry.
- **AWS App2Container:** Application containerization and migration tool for supported Java and .NET workloads.

## 2. Benefits of Application Containerization

- **Portability:** Run applications consistently across environments.
- **Scalability:** Scale application containers based on demand.
- **Resource efficiency:** Share the host operating system kernel.
- **Faster deployment:** Standardize application packaging and delivery.
- **Isolation:** Separate application processes and dependencies.
- **Automation:** Integrate container builds with CI/CD pipelines.
- **Modernization:** Gradually transition legacy applications toward cloud-native architectures.

## 3. Application Migration Strategies

Before containerization, assess the existing application and select an appropriate AWS migration strategy.

AWS identifies seven migration strategies (7 Rs):

| Strategy   | Description                                                                 |
| ---------- | --------------------------------------------------------------------------- |
| Rehost     | Move applications without major modifications.                              |
| Replatform | Make limited changes to run applications on containers or managed services. |
| Refactor   | Redesign applications to use cloud-native capabilities.                     |
| Repurchase | Replace existing applications with SaaS or another product.                 |
| Relocate   | Move infrastructure to another cloud environment.                           |
| Retain     | Keep applications in the existing environment.                              |
| Retire     | Decommission applications that are no longer required.                      |

**Note:** Replatforming is commonly used when migrating virtual-machine-based applications into containers.

## 4. Application Assessment Before Containerization

Assess the application before selecting a containerization approach.

### Important assessment areas

1. **Application dependencies:** Identify libraries, frameworks, runtime versions, and external services.
2. **Operating system:** Check OS compatibility and system-level dependencies.
3. **Application architecture:** Identify monolithic applications, microservices, and distributed components.
4. **Data storage:** Identify databases, file systems, caches, and persistent storage.
5. **Network dependencies:** Identify ports, protocols, upstream and downstream connections.
6. **Security:** Evaluate vulnerabilities, authentication, authorization, and compliance requirements.
7. **Logging and monitoring:** Determine how application logs and metrics will be collected.
8. **Deployment process:** Review existing CI/CD pipelines and release procedures.

### Good candidates for containerization

- Stateless applications.
- Applications with clearly defined dependencies.
- Applications packaged as deployable binaries.
- Applications using supported runtime environments.
- Applications already using automated CI/CD pipelines.

Stateless applications are generally easier to migrate because persistent information is stored outside the container.

## 6. Step-by-Step Application Containerization Process

### Step 1: Assess the Existing Application

- Inventory application servers.
- Identify application runtime and dependencies.
- Review application configuration.
- Identify database and external service dependencies.
- Determine containerization feasibility.
- Select the target AWS container platform.

### Step 2: Prepare the Containerization Environment

Install and configure:

- Docker Engine.
- AWS CLI.
- Required containerization tools.
- AWS IAM permissions.
- Network connectivity to AWS services.

For AWS App2Container, use an application server or a separate worker machine depending on infrastructure requirements.

### Step 3: Analyze Application Dependencies

Identify:

- Application processes.
- Runtime dependencies.
- Network ports.
- Configuration files.
- Application artifacts.
- Required libraries.

AWS App2Container can inventory supported applications and analyze their runtime dependencies without requiring application source code.

### Step 4: Create the Container Image

Create a Dockerfile containing:

- Base image.
- Application runtime.
- Application artifacts.
- Required dependencies.
- Environment configuration.
- Startup command.

Example Dockerfile:

```
FROM eclipse-temurin:17-jre

WORKDIR /app

COPY target/application.jar app.jar

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]
```

Build the container image:

```
docker build -t my-application:v1 .
```

Run the container locally:

```
docker run -d -p 8080:8080 my-application:v1
```

Test application functionality before migrating it to AWS.

### Step 5: Push the Image to Amazon ECR

Create an ECR repository:

```
aws ecr create-repository \
  --repository-name my-application
```

Authenticate Docker with ECR:

```
aws ecr get-login-password --region REGION \
| docker login --username AWS --password-stdin ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com
```

Tag the image:

```
docker tag my-application:v1 \
ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/my-application:v1
```

Push the image:

```
docker push ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/my-application:v1
```

### Step 6: Deploy Containers on AWS

Choose the appropriate hosting platform.

**Option A: Amazon ECS**

- Create an ECS cluster.
- Define an ECS task definition.
- Configure CPU and memory.
- Configure IAM task roles.
- Create an ECS service.
- Configure Application Load Balancer if required.

**Option B: Amazon EKS**

- Create an EKS cluster.
- Configure worker nodes.
- Configure Kubernetes deployments.
- Create Kubernetes services.
- Configure ingress and load balancing.
- Deploy application containers.

**Option C: AWS Fargate**

Use Fargate with Amazon ECS or supported EKS configurations to run containers without managing the underlying compute instances.

### Step 7: Migrate Application Data

Containers should not be treated as permanent storage.

Use appropriate external storage services:

- Amazon RDS or Aurora for relational databases.
- Amazon DynamoDB for NoSQL workloads.
- Amazon EFS for shared file storage.
- Amazon S3 for object storage.
- Amazon ElastiCache for caching.

Use AWS DMS where appropriate for database migration and ongoing change data capture.

### Step 8: Configure Security and Monitoring

Implement:

- IAM least-privilege permissions.
- Private networking and security groups.
- Secrets Manager for sensitive credentials.
- TLS encryption.
- ECR image vulnerability scanning.
- Container image versioning.
- CloudWatch logs and metrics.
- Container runtime security.
- Network access restrictions.

### Step 9: Automate CI/CD

Create a pipeline to automate:

1. Source code checkout.
2. Application build.
3. Unit and integration tests.
4. Security scanning.
5. Docker image creation.
6. Image publishing to ECR.
7. Deployment to ECS or EKS.
8. Post-deployment validation.

### Step 10: Validate and Cut Over

Perform:

- Functional testing.
- Integration testing.
- Performance testing.
- Security testing.
- Load testing.
- Availability testing.
- Database consistency checks.
- Backup and recovery testing.

After successful validation, switch application traffic to the new containerized environment using a controlled cutover strategy.

Maintain a rollback plan until the migration is confirmed successful.
