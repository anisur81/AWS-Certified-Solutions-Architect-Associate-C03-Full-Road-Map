# When to Use Read Replicas & Workflow Orchestration (AWS Step Functions)

## 1. When to Use Read Replicas (Amazon RDS)

### 1.1 What Is a Read Replica?

An Amazon RDS Read Replica is a read-only copy of a primary database instance. It helps improve database performance by distributing read-heavy workloads across multiple database instances.

Amazon RDS uses **asynchronous replication** to copy changes from the primary database to its read replicas.

**Key characteristics:**

- Read replicas accept read-only database queries.
- The primary database handles read and write operations.
- Replication happens asynchronously.
- Applications can connect directly to read replicas.
- Multiple read replicas can distribute read traffic.
- A read replica can be promoted to a standalone database for disaster recovery.

### 1.2 Read Replica Architecture

```
              Application
                   |
          +--------+--------+
          |                 |
     Write Requests     Read Requests
          |                 |
          v                 v
    +-------------+    +-------------+
    | Primary RDS |--->| Read Replica|
    | Read/Write  |Async| Read Only  |
    +-------------+    +-------------+
          |                 |
          |                 |
          v                 v
       Write DB          Read DB
```

For larger workloads, multiple read replicas can distribute read traffic.

```
                 Application
                      |
             Database Routing
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
      Primary RDS  Replica 1  Replica 2
      Read/Write   Read Only  Read Only
          |
          +---- Asynchronous Replication ---->
```

### 1.3 When Should You Use Read Replicas?

**1. Read-heavy workloads**

Use read replicas when applications generate many SELECT queries and the primary database experiences high CPU, memory, or I/O utilization.

Examples:

- E-commerce product searches.
- Online banking account statements.
- Large web applications.
- Customer dashboards.

**2. Database performance improvement**

When read requests affect the performance of write transactions, move suitable read queries to replicas.

This reduces the workload on the primary database.

**3. Reporting and analytics**

Use read replicas for:

- Business intelligence reporting.
- Management dashboards.
- Historical data analysis.
- Reporting applications.
- Data warehouse workloads.

This prevents expensive reporting queries from affecting production transactions.

**4. Disaster recovery (DR)**

A read replica can be promoted to become a standalone database if the primary database fails.

This can help reduce recovery time, depending on the database engine, replication status, and recovery procedure.

**5. Cross-Region read access**

Use cross-Region read replicas when applications in another AWS Region need access to replicated database data.

Benefits:

- Improve read performance for geographically distributed users.
- Support regional disaster recovery strategies.
- Maintain a separate copy of database data in another Region.

### 1.4 Read Replica vs Multi-AZ Deployment

| Feature          | Read Replica                                | Multi-AZ                              |
| ---------------- | ------------------------------------------- | ------------------------------------- |
| Main purpose     | Read scaling                                | High availability                     |
| Replication      | Asynchronous                                | Synchronous for Multi-AZ DB instances |
| Read traffic     | Supports read queries                       | Standby doesn't serve read traffic    |
| Write operations | Primary only                                | Primary only                          |
| Failover         | Manual promotion for standard read replicas | Automatic failover                    |
| DR use           | Yes                                         | High availability within deployment   |
| Scaling          | Horizontal read scaling                     | Availability improvement              |

**Important:** Read replicas and Multi-AZ deployments solve different problems. Read replicas primarily improve read scalability, while Multi-AZ improves availability.

### 1.5 Important Considerations

- **Replication lag:** A read replica might not immediately contain the latest primary database changes.
- **Stale data:** Applications requiring immediate consistency should read from the primary database.
- **Read-only limitation:** Standard read replicas cannot handle write operations.
- **Cost:** Each read replica has its own compute and storage costs.
- **Monitoring:** Monitor the `ReplicaLag` CloudWatch metric.
- **Manual scaling:** Standard RDS read replicas must be created and removed manually; RDS doesn't automatically scale their number based on read demand.

### 1.6 When NOT to Use Read Replicas

Avoid using read replicas when:

- Your application is primarily write-heavy.
- You require immediate consistency for every read.
- Your primary database doesn't experience read-related performance problems.
- Additional database infrastructure costs outweigh the performance benefits.

## 2. Workflow Orchestration (AWS Step Functions)

### 2.1 What Is Workflow Orchestration?

Workflow orchestration is the process of coordinating multiple tasks, services, and operations in a specific sequence to complete a business process.

**AWS Step Functions** is a fully managed AWS service that helps coordinate distributed applications and microservices using visual workflows called state machines.

It integrates with AWS services such as:

- AWS Lambda
- Amazon ECS
- Amazon SQS
- Amazon SNS
- Amazon DynamoDB
- Amazon EventBridge
- AWS Glue

**Main benefits:**

- Automates multi-step workflows.
- Coordinates multiple AWS services.
- Provides built-in error handling and retry mechanisms.
- Supports parallel processing.
- Provides workflow execution history and monitoring.
- Reduces orchestration logic in application code.

### 2.2 AWS Step Functions Architecture

```
             User / Application
                     |
                     v
              Start Execution
                     |
                     v
             AWS Step Functions
                State Machine
                     |
          +----------+----------+
          |          |          |
          v          v          v
       Lambda      DynamoDB     SQS
       Task        Task         Task
          |          |          |
          +----------+----------+
                     |
                     v
               Workflow Result
                     |
                     v
               Success / Failure
```

Step Functions manages the execution flow between tasks.

### 2.3 Important Components

| Component      | Description                                                   |
| -------------- | ------------------------------------------------------------- |
| State Machine  | Defines the complete workflow                                 |
| State          | Represents an individual workflow step                        |
| Task State     | Performs an operation using an AWS service or external worker |
| Choice State   | Implements conditional decisions                              |
| Parallel State | Runs multiple branches concurrently                           |
| Map State      | Processes multiple items                                      |
| Wait State     | Pauses workflow execution                                     |
| Pass State     | Passes input to output without performing a task              |
| Succeed State  | Ends workflow successfully                                    |
| Fail State     | Ends workflow with failure                                    |

Workflows are defined using **Amazon States Language (ASL)**, a JSON-based language.

You can also use Workflow Studio to design workflows visually.

### 2.4 When Should You Use AWS Step Functions?

**1. Multi-step application workflows**

Use Step Functions when an application requires multiple operations to execute in a specific sequence.

Example:

- Register a customer.
- Validate customer information.
- Process payment.
- Update the database.
- Send a confirmation notification.

**2. Microservices orchestration**

Use Step Functions to coordinate multiple microservices without implementing all workflow coordination logic inside application code.

Example:

- Customer service.
- Payment service.
- Inventory service.
- Notification service.

**3. Error handling and automatic retries**

Use Step Functions when workflows need reliable error handling.

Features include:

- Retry failed tasks.
- Catch errors.
- Define fallback operations.
- Handle temporary service failures.

**4. Parallel processing**

Use Parallel states when multiple independent operations can execute simultaneously.

Example:

- Process customer information.
- Verify payment.
- Check inventory.

These operations can run in parallel before the workflow continues.

**5. Long-running business processes**

Use Standard Workflows for processes that may take hours, days, or months.

Examples:

- Insurance claim processing.
- Financial approval workflows.
- Order fulfillment.
- Employee onboarding.

**6. Event-driven automation**

Step Functions can start workflows through integrations with services such as Amazon EventBridge and API Gateway.

Examples:

- Automated file processing.
- Data transformation.
- Application event processing.
- Infrastructure automation.

### 2.5 Standard vs Express Workflows

AWS Step Functions provides two workflow types.

| Feature            | Standard Workflow               | Express Workflow                               |
| ------------------ | ------------------------------- | ---------------------------------------------- |
| Execution duration | Up to 1 year                    | Up to 5 minutes                                |
| Execution model    | Exactly-once by default         | At-least-once or asynchronous at-most-once     |
| Workload           | Long-running workflows          | High-volume workloads                          |
| Execution rate     | Up to 2,000/sec (default quota) | Up to 100,000/sec (default quota)              |
| Pricing            | State transitions               | Number and duration of executions, plus memory |
| Best use case      | Payment and approval processes  | IoT and event processing                       |

**Important:**

- Standard Workflows are suitable for long-running, auditable processes.
- Express Workflows are suitable for short-duration, high-volume processing.
- Express workflows can execute tasks more than once. Design tasks to be idempotent when necessary.
- Workflow type cannot be changed after creating a state machine.

### 2.6 Practical Example: E-commerce Order Processing

**Business requirement:** Automate the complete order-processing workflow.

```
          Customer Places Order
                   |
                   v
          AWS Step Functions
                   |
                   v
          Validate Order (Lambda)
                   |
                   v
           Check Inventory
                   |
                   v
          +----------------+
          | Inventory      |
          | Available?     |
          +----------------+
             /         \
           Yes          No
            |            |
            v            v
       Process       Cancel Order
       Payment           |
            |            v
            v          Notify
       Update DB      Customer
            |
            v
       Send Notification
            |
            v
          Success
```

**Workflow execution:**

1. Customer places an order.
2. Step Functions starts the workflow.
3. Lambda validates customer and order information.
4. Inventory service checks product availability.
5. Choice state determines whether inventory is available.
6. Payment service processes the payment.
7. DynamoDB or another database stores the order details.
8. Notification service sends confirmation.
9. Workflow completes successfully.

If payment fails, Step Functions can catch the error and execute a suitable failure-handling path.

### 2.7 Important Best Practices

- Use IAM least-privilege permissions for state machines.
- Implement Retry and Catch for appropriate errors.
- Configure task timeouts to prevent stuck executions.
- Use Standard workflows for long-running business processes.
- Use Express workflows for high-volume, short-duration processing.
- Make retryable operations idempotent.
- Avoid passing large payloads between states; use Amazon S3 for large data.
- Monitor workflow execution using Amazon CloudWatch.
- Use nested workflows to reuse common workflow logic.

## 3. Quick Comparison: When to Use Which Service?

| Requirement                            | Recommended AWS Service                 |
| -------------------------------------- | --------------------------------------- |
| Scale database read traffic            | RDS Read Replicas                       |
| Improve database high availability     | RDS Multi-AZ                            |
| Disaster recovery for RDS              | Read Replica / Cross-Region DR strategy |
| Coordinate multiple AWS services       | AWS Step Functions                      |
| Automate multi-step business processes | AWS Step Functions                      |
| Execute tasks in parallel              | Step Functions Parallel State           |
| Process high-volume events             | Step Functions Express                  |
| Manage long-running workflows          | Step Functions Standard                 |

## 4. AWS SAA-C03 Exam Tips

### Read Replicas

- Remember: Read replicas are primarily designed for read scaling.
- Understand asynchronous replication and replication lag.
- Read replicas can be promoted for disaster recovery.
- Multi-AZ is primarily for high availability.
- Standby instances in a standard Multi-AZ DB instance deployment do not serve read traffic.
- Cross-Region read replicas support geographically distributed read access and DR strategies.

### AWS Step Functions

- Remember: Step Functions orchestrates multiple AWS services.
- Standard = long-running workflows.
- Express = high-volume, short-duration workflows.
- Choice = conditional execution.
- Parallel = concurrent execution.
- Map = process multiple items.
- Retry = retry failed tasks.
- Catch = handle errors.
- Workflow Studio = visual workflow designer.

### Common Exam Scenarios

| Exam Scenario                                      | Correct Choice          |
| -------------------------------------------------- | ----------------------- |
| Production database overloaded by SELECT queries   | Read Replica            |
| Reporting queries affecting production performance | Read Replica            |
| Database automatic failover requirement            | Multi-AZ                |
| Multi-step payment processing                      | Step Functions Standard |
| High-volume event processing                       | Step Functions Express  |
| Multiple independent tasks running simultaneously  | Parallel State          |
| Conditional workflow execution                     | Choice State            |
