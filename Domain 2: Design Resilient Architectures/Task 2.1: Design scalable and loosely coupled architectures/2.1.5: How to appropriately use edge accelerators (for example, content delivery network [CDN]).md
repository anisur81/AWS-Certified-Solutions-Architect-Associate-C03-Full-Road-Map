
# How to Appropriately Use Edge Accelerators (e.g., Content Delivery Network – CDN)

**Edge accelerators** improve application performance by delivering content and routing user requests through infrastructure located closer to end users.

An Edge Location is a geographically distributed point of presence where content can be cached or requests can be processed closer to users.

AWS provides services such as:

- **Amazon CloudFront:** Content Delivery Network (CDN).
- **AWS Global Accelerator:** Improves application availability and network performance.
- **CloudFront Functions and Lambda@Edge:** Execute application logic closer to users.

Using edge acceleration appropriately reduces latency, improves availability, reduces origin infrastructure load, and can optimize data transfer costs.

## 2. Amazon CloudFront (CDN)

Amazon CloudFront is a globally distributed CDN that delivers static, dynamic, streaming, and interactive content through AWS edge locations.

### How CloudFront Works

1. A user requests content from a website or application.
2. DNS routing directs the request to an appropriate CloudFront edge location.
3. CloudFront checks whether the requested content exists in its cache.
4. If cached (Cache Hit), CloudFront delivers the content directly.
5. If not cached (Cache Miss), CloudFront retrieves content from the configured origin.
6. CloudFront caches eligible content according to its caching policies.
7. Subsequent requests can be served from the edge cache.

### Supported Origins

- Amazon S3
- Amazon EC2
- Elastic Load Balancing (ELB)
- Application servers
- On-premises web servers
- Other publicly accessible HTTP servers

## 3. When to Use Edge Accelerators

### A. Static Content Delivery

Use CloudFront to distribute frequently accessed static files, such as:

- Images and videos
- JavaScript and CSS files
- HTML pages
- Software downloads
- Public documents

**Benefit:** Reduces latency and decreases requests reaching origin servers.

### B. Dynamic Content Acceleration

CloudFront can accelerate dynamic content, including API requests and application responses, using optimized network connections.

**Use cases:**
- E-commerce applications
- Banking applications
- Global web applications
- Dynamic API responses

**Benefit:** Improves request delivery performance, even when content cannot be cached.

### C. Video Streaming

Use CloudFront for:

- Video on Demand (VOD)
- Live video streaming
- Media distribution
- Large file downloads

**Benefit:** Delivers media efficiently to geographically distributed users.

### D. Global Application Traffic Acceleration

Use AWS Global Accelerator when applications require improved availability and consistent network performance for global users.

It provides static anycast IP addresses and routes traffic through the AWS global network to healthy application endpoints.

**Use cases:**
- Online gaming
- VoIP applications
- IoT applications
- Global TCP/UDP workloads

**Important:** CloudFront is primarily designed for content delivery and caching, whereas Global Accelerator focuses on application traffic routing and availability.

## 4. AWS Edge Acceleration Services Comparison

| Service | Primary Purpose | Best Use Case |
|---|---|---|
| Amazon CloudFront | CDN and content caching | Websites, APIs and media |
| AWS Global Accelerator | Global traffic acceleration | Gaming, IoT and TCP/UDP |
| CloudFront Functions | Lightweight edge processing | URL rewrites and redirects |
| Lambda@Edge | Advanced edge processing | Request customization and authorization |

## 5. Best Practices for Using CloudFront

### A. Configure Effective Caching

- Identify frequently accessed content.
- Configure appropriate cache policies.
- Set suitable Time to Live (TTL) values.
- Use versioned filenames for static assets.
- Avoid caching sensitive or personalized responses.

### B. Secure Content Delivery

- Enable HTTPS using SSL/TLS certificates.
- Use Origin Access Control (OAC) for private S3 origins.
- Apply AWS WAF rules where appropriate.
- Use signed URLs or signed cookies for private content.
- Restrict direct access to origin infrastructure.

### C. Optimize Performance

- Enable compression where appropriate.
- Minimize unnecessary origin requests.
- Use suitable cache keys.
- Consider Origin Shield for high-volume workloads.
- Monitor cache hit ratio and origin latency.

### D. Control Costs

- Monitor data transfer and request charges.
- Select an appropriate CloudFront pricing option.
- Optimize cache hit ratios.
- Avoid unnecessary cache invalidations.
- Evaluate Origin Shield costs against origin-load savings.

### E. Monitor and Troubleshoot

Use:
- CloudFront access logs
- Amazon CloudWatch
- CloudFront metrics
- AWS CloudTrail
- AWS Cost Explorer

Monitor cache hit ratio, request count, error rates, latency and origin response time.

## 6. Practical Architecture Example

### Global Website Using S3 and CloudFront

```text
              Global Users
                   |
                   v
             Amazon CloudFront
               (Edge Locations)
                   |
             Cache Hit / Miss
                   |
          +--------+--------+
          |                 |
       Cache Hit         Cache Miss
          |                 |
          v                 v
      Cached Content    Amazon S3
                            |
                     Original Content
```

### Implementation Steps

1. Create an Amazon S3 bucket.
2. Upload static website files.
3. Create a CloudFront distribution.
4. Configure the S3 bucket as the origin.
5. Configure Origin Access Control (OAC).
6. Restrict public access to the S3 bucket.
7. Configure HTTPS and a suitable cache policy.
8. Access the content using the CloudFront distribution domain.
9. Verify cache behavior using response headers.
10. Monitor performance using CloudFront metrics.

## 7. Common Mistakes to Avoid

- Caching private or user-specific data unintentionally.
- Leaving the S3 origin publicly accessible.
- Setting excessively long TTL values for frequently changing content.
- Using CloudFront when Global Accelerator better fits the workload.
- Ignoring cache invalidation and versioning strategies.
- Failing to monitor origin requests and data transfer costs.
- Assuming every dynamic request can be cached safely.
