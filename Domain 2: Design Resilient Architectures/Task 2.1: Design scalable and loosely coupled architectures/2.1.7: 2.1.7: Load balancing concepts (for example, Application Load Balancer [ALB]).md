
# Load Balancing Concepts: Application Load Balancer (ALB)

> **AWS reference:** [What is an Application Load
> Balancer?](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html)\
> **Purpose:** Understand ALB concepts, components, routing, health
> checks, security, and common architecture patterns.\
> **Scope:** AWS Elastic Load Balancing -- Application Load Balancer.

## 1. What is Load Balancing?

Load balancing distributes incoming application traffic across multiple
backend targets. It helps improve application **availability,
scalability, and fault tolerance** by avoiding dependence on a single
server.

AWS Elastic Load Balancing (ELB) distributes traffic across registered
targets such as EC2 instances, containers, and IP addresses. It monitors
target health and normally routes requests to healthy targets. ELB
scales the load balancer as traffic changes.

AWS provides Application Load Balancers (ALB), Network Load Balancers
(NLB), Gateway Load Balancers (GWLB), and Classic Load Balancers (CLB).
Choose the type based on application and protocol requirements.

## 2. What is an Application Load Balancer?

An **Application Load Balancer operates at Layer 7 (Application Layer)
of the OSI model**. It understands HTTP/HTTPS request information and
can route requests using application-level content, such as host names,
URL paths, HTTP headers, query strings, and request methods.

Typical use cases: - Web applications and REST APIs. - Microservices and
containerized applications. - Multiple websites or services behind one
load balancer. - Path-based and host-based routing. - HTTP-to-HTTPS
redirects and user authentication.

ALB supports HTTP and HTTPS listeners and also supports WebSocket and
gRPC workloads. It is not a general-purpose TCP/UDP load balancer;
consider NLB when Layer 4 capabilities or static IP addresses are
required.

## 3. Core ALB Components

### 3.1 Load Balancer

The ALB is the client-facing entry point. It receives requests and
distributes them to targets in one or more enabled Availability Zones
(AZs). For production workloads, deploy the ALB across at least two AZs.

### 3.2 Listener

A listener checks for connection requests on a configured protocol and
port. ALB listeners support: - **HTTP**, commonly port 80. - **HTTPS**,
commonly port 443.

An HTTPS listener uses a certificate, commonly provisioned through AWS
Certificate Manager (ACM), to terminate TLS at the load balancer. A
listener must have a default rule and can have additional rules.

### 3.3 Listener Rules

Rules determine how requests are handled. A rule contains a priority,
conditions, and actions. ALB evaluates non-default rules in priority
order; the default rule is used when no other rule matches.

Common conditions: - **Host header:** `api.example.com` - **Path
pattern:** `/api/*` or `/images/*` - **HTTP header:** Match a specified
header. - **HTTP request method:** GET, POST, etc. - **Query string:**
Match query-string key/value pairs. - **Source IP:** Match a client
source IP range.

Common actions: - **Forward:** Send requests to a target group. -
**Redirect:** Redirect a request, such as HTTP to HTTPS. - **Fixed
response:** Return a configured response. - **Authentication:**
Authenticate through Amazon Cognito or an OIDC-compatible identity
provider on supported HTTPS listener rules.

### 3.4 Target Group

A target group is a logical collection of destinations to which the ALB
forwards requests. It also defines target-level settings, including the
traffic protocol, port, and health checks.

Supported target types include: - **Instance:** EC2 instances identified
by instance ID. - **IP:** Targets identified by private IP addresses,
including eligible resources outside the load balancer's VPC. -
**Lambda:** A Lambda function invoked as a target.

A target can be registered with more than one target group. A target
group is associated with one load balancer.

## 4. How ALB Routes a Request

Example architecture:

``` text
                 Internet / Client
                        |
                  HTTPS : 443
                        |
               Application Load Balancer
                        |
                 HTTPS Listener
                        |
              Listener Rules (priority)
                 /             \
       Host: shop.example.com   Path: /api/*
              |                      |
        Shop Target Group       API Target Group
          /       \               /       \
       EC2-A     EC2-B          EC2-C     EC2-D
```

Request flow: 1. A client sends an HTTP/HTTPS request to the ALB DNS
name or an application domain mapped to it. 2. The listener receives the
request on its configured port. 3. ALB evaluates listener rules in
priority order. 4. The matching rule performs its action, typically
forwarding to a target group. 5. The target group selects an eligible
healthy target. 6. The application processes the request and returns a
response.

ALB supports routing algorithms at the target-group level. **Round
robin** is the default; **least outstanding requests** is an
alternative. Select the algorithm based on workload behavior.

## 5. Health Checks

ALB periodically sends health-check requests to registered targets using
each target group's health-check configuration. Settings include: -
Protocol: HTTP or HTTPS. - Port: Traffic port or a configured port. -
Path: For example, `/health`. - Interval and timeout. - Healthy and
unhealthy thresholds. - Success-code matcher.

A target becomes healthy after the required successful checks and
unhealthy after the configured consecutive failures. ALB normally sends
traffic to healthy targets in enabled AZs.

**Important:** If every registered target in all enabled AZs is
unhealthy, ALB can fail open and route requests to all those targets.
Therefore, health checks are not a substitute for application resilience
and monitoring.

Use a health endpoint that checks whether the application can serve
requests. Avoid making it depend on every optional downstream service,
or temporary dependency issues may remove all application targets from
service.

## 6. Availability, Scaling, and Integrations

-   **Multi-AZ:** Configure ALB subnets in at least two AZs for
    production resilience.
-   **Auto Scaling:** Attach a target group to an EC2 Auto Scaling group
    so instances can register and deregister as capacity changes.
-   **ECS/EKS:** ALB can route to container workloads; integration and
    target registration depend on the service configuration.
-   **ACM:** Manage TLS certificates for HTTPS listeners.
-   **Route 53:** Map a custom DNS name to the ALB.
-   **AWS WAF:** Apply web request filtering rules.
-   **CloudWatch:** Monitor ALB and target-group metrics.
-   **Access logs:** Store request-level access logs in Amazon S3 for
    analysis.

## 7. Security and Best Practices

1.  Use HTTPS listeners and valid certificates; redirect HTTP to HTTPS
    where appropriate.
2.  Place the ALB in appropriate public or internal subnets based on
    application exposure.
3.  Restrict target security groups so application ports accept traffic
    only from the ALB security group.
4.  Permit health-check traffic from the ALB security group on the
    health-check port.
5.  Use AWS WAF for applicable web-application protections.
6.  Apply least-privilege IAM permissions to ALB administration.
7.  Enable access logs and monitor CloudWatch metrics and alarms.
8.  Configure realistic health-check paths, thresholds, and timeouts.
9.  Use multiple AZs and Auto Scaling where appropriate.
10. Review ALB capacity, target health, latency, HTTP errors, and
    request volume.

## 8. ALB vs. NLB --- Quick Comparison

  -----------------------------------------------------------------------
  Feature                 ALB                     NLB
  ----------------------- ----------------------- -----------------------
  OSI layer               Layer 7                 Layer 4

  Main protocols          HTTP, HTTPS             TCP, TLS, UDP and
                                                  related L4 options

  Routing                 Host/path/header and    Network-level
                          other HTTP conditions   connection routing

  Common use              Websites, APIs,         Low-latency or non-HTTP
                          microservices           traffic

  Static IP per AZ        Not its standard model  Supported
  -----------------------------------------------------------------------

Choose ALB when routing decisions depend on HTTP request content. Choose
NLB when you need Layer 4 load balancing, supported static IP addresses,
or protocols beyond ALB's HTTP-focused model.

## 9. SAA-C03 / Interview Quick Revision

-   ALB is a **Layer 7** load balancer.
-   A listener receives client connections on a configured protocol and
    port.
-   Listener rules use conditions and actions to route or handle
    requests.
-   A target group contains registered destinations and its own
    health-check configuration.
-   Host-based routing supports multiple domains through one ALB.
-   Path-based routing supports microservices behind one ALB.
-   HTTPS listeners can terminate TLS using certificates such as ACM
    certificates.
-   ALB supports instance, IP, and Lambda target types.
-   Round robin is the default target-group routing algorithm; least
    outstanding requests is an alternative.
-   For HTTP/HTTPS application routing, choose ALB; for Layer 4
    requirements, evaluate NLB.
