
# Event-Driven Architectures, Horizontal Scaling, and Vertical Scaling on AWS

## 1. Event-Driven Architecture (EDA)

An **event-driven architecture (EDA)** is a software design pattern in
which components communicate by producing, routing, and responding to
events. An event represents a meaningful change or occurrence, such as
an order being placed, a file being uploaded, a payment being completed,
or an EC2 instance changing state.

EDA reduces direct dependencies between application components. A
producer does not need to know which services consume its event. This
loose coupling supports independent development, deployment, scaling,
and failure isolation.

### Main components

1.  **Event producer:** Creates and publishes an event. Examples include
    an application, Amazon S3, or an AWS service.
2.  **Event router or broker:** Receives events, filters or routes them,
    and delivers them to destinations. Examples include Amazon
    EventBridge, Amazon SNS, and Amazon SQS.
3.  **Event consumer:** Processes an event and performs an action.
    Examples include AWS Lambda, an ECS task, or an application running
    on Amazon EKS.

### Typical AWS event flow

``` text
Customer places an order
          |
          v
   Order API / Service
          |
          v
   Amazon EventBridge
      /       |       \
     v        v        v
 Payment   Inventory  Notification
 Lambda     Service     Lambda
     |        |           |
     v        v           v
 Payment   Update stock  Send email
```

The order service publishes an `OrderPlaced` event. EventBridge routes
it to relevant consumers. Payment, inventory, and notification
processing can occur independently and, where appropriate, in parallel.

### Benefits

-   **Loose coupling:** Producers and consumers can change
    independently.
-   **Independent scaling:** Busy consumers can scale without scaling
    every component.
-   **Resilience:** Queues can buffer messages when consumers are
    temporarily unavailable.
-   **Extensibility:** New consumers can subscribe without changing the
    producer.
-   **Cost efficiency:** Event-triggered processing can reduce
    continuously running or polling workloads.
-   **Parallel processing:** Multiple consumers can process the same
    event for different business purposes.

### Design considerations and best practices

-   Design consumers to be **idempotent**, because messages may be
    delivered more than once.
-   Use retries and dead-letter queues (DLQs) to handle failed
    processing.
-   Define and version event schemas; avoid breaking existing consumers.
-   Use correlation IDs and structured logs to trace an event across
    services.
-   Monitor queue depth, message age, processing errors, throttling, and
    delivery failures.
-   Consider ordering requirements: standard queues and event delivery
    mechanisms do not always guarantee strict ordering. Use an
    ordering-capable option, such as SQS FIFO, when the application
    requires it.
-   Protect event sources and targets with least-privilege IAM policies
    and encryption.
-   Avoid using asynchronous events where an immediate synchronous
    response is essential.

## 2. Horizontal Scaling

**Horizontal scaling (scaling out or in)** means increasing or
decreasing capacity by adding or removing multiple compute resources,
such as EC2 instances, containers, or application tasks.

``` text
                 Load Balancer
                 /     |     \
                v      v      v
             EC2-1   EC2-2   EC2-3
```

Instead of making one server larger, the application distributes
workload across several instances.

### AWS implementation

-   **Amazon EC2 Auto Scaling:** Adds or removes EC2 instances based on
    demand or defined policies.
-   **Elastic Load Balancing (ELB):** Distributes incoming traffic
    across healthy targets.
-   **Amazon ECS / Amazon EKS:** Scales container tasks or pods; cluster
    capacity can also scale.
-   **AWS Lambda:** Scales function execution in response to incoming
    events, subject to concurrency limits and service quotas.
-   **Amazon DynamoDB:** Supports on-demand capacity and automatic
    scaling for suitable workloads.

### Advantages

-   Can provide greater aggregate capacity.
-   Improves availability when deployed across multiple Availability
    Zones.
-   Supports incremental capacity growth.
-   Allows independent scaling of application components.
-   Fits stateless web services, microservices, and distributed
    workloads.

### Challenges

-   Requires application design that supports distributed processing.
-   Session state should be externalized or handled appropriately.
-   Shared databases, caches, and network resources can become
    bottlenecks.
-   Adds distributed-system concerns such as retries, consistency, and
    observability.

## 3. Vertical Scaling

**Vertical scaling (scaling up or down)** means increasing or decreasing
the resources of a single compute resource, such as assigning an EC2
instance a larger instance type with more CPU, memory, or network
capacity.

``` text
       Before                  After
   +-----------+           +-------------+
   |  EC2      |   ---->   |   Larger    |
   |  small    |           |   EC2       |
   +-----------+           +-------------+
   Less CPU/RAM              More CPU/RAM
```

### AWS implementation

-   Change an EC2 instance to a larger or smaller instance type, subject
    to compatibility and operational requirements.
-   Select appropriately sized Amazon RDS DB instance classes.
-   Increase compute or memory capacity for workloads that cannot easily
    be distributed.
-   Plan for service-specific limits and possible downtime during
    resizing.

### Advantages

-   Often simpler than distributing an application across multiple
    servers.
-   Can improve performance for workloads that need larger CPU or memory
    capacity.
-   Useful for legacy or stateful applications that are difficult to
    distribute.

### Limitations

-   A single resource has an upper capacity limit.
-   May require a restart or maintenance window.
-   Does not by itself provide application-level high availability.
-   Larger resource sizes can become expensive.

## 5. Combining EDA with Horizontal and Vertical Scaling

EDA and scaling complement each other. Event routing and queues decouple
services; consumers can then scale independently according to workload.

Example: an e-commerce application receives a sudden increase in orders.

1.  The order API publishes an event to EventBridge.
2.  EventBridge routes the event to an SQS queue or relevant targets.
3.  Worker services consume messages asynchronously.
4.  EC2 Auto Scaling, ECS Service Auto Scaling, EKS workload scaling, or
    Lambda concurrency increases processing capacity as appropriate.
5.  If a particular worker needs more CPU or memory per task, its task
    or instance size can be increased vertically.
6.  Monitoring and alarms identify backlogs, errors, and capacity
    constraints.

**Key point:** Horizontal scaling increases the number of resources;
vertical scaling increases the capacity of an individual resource; EDA
enables components to react and scale independently.

## 6. Hands-on AWS Lab

**Objective:** Build a simple event-driven order-processing workflow.

1.  Create an Amazon SQS queue and a dead-letter queue.
2.  Create an AWS Lambda function that processes an order message.
3.  Configure the queue as the Lambda event source.
4.  Send test messages and verify processing in Amazon CloudWatch Logs.
5.  Configure retry and DLQ behavior; test a deliberately failing
    message.
6.  Monitor queue depth and message age.
7.  For a scaling exercise, deploy a worker service on EC2 Auto Scaling
    or ECS and configure scaling based on workload metrics.
8.  Document architecture, IAM permissions, failure handling, scaling
    behavior, and estimated cost.
9.  Delete test resources after the lab to avoid ongoing charges.

## 7. Exam and Architecture Revision

-   Use **EventBridge** for event routing and rules across services and
    applications.
-   Use **SNS** for pub/sub and fan-out notifications.
-   Use **SQS** to buffer messages and decouple processing.
-   Use **Lambda** for event-triggered serverless compute.
-   Use **horizontal scaling** when more parallel capacity is needed.
-   Use **vertical scaling** when one resource needs more CPU, memory,
    or other capacity.
-   Consider retries, idempotency, DLQs, observability, IAM, and service
    quotas when designing event-driven systems.
