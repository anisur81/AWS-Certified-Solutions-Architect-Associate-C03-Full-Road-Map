 
# Service Quotas and Throttling in AWS

## 1. Introduction

**Service quotas** (formerly called service limits) are the maximum number of resources, operations, or requests that an AWS account can use within a specific scope.

AWS defines default quotas for its services to maintain service reliability and prevent excessive resource consumption.

Examples:

- Maximum number of EC2 vCPUs in a Region.
- Maximum number of Elastic IP addresses.
- Maximum number of VPCs per Region.
- Maximum API requests per second.

If a workload exceeds a service quota, AWS might reject the request, causing deployment failures or application disruptions.

**Throttling** occurs when an application sends requests to an AWS service faster than the permitted request rate.

Both service quotas and throttling must be considered when designing highly available and disaster-recovery architectures.

## 2. Understanding AWS Service Quotas

AWS Service Quotas provides a centralized way to view and manage service limits.

### Key features

- View default and applied service quotas.
- Monitor quota utilization.
- Request quota increases.
- Create CloudWatch alarms for supported quotas.
- Manage quotas across AWS services and Regions.

### Types of quotas

| Type                  | Description                                                        |
| --------------------- | ------------------------------------------------------------------ |
| Adjustable quotas     | Can request an increase through AWS Service Quotas or AWS Support. |
| Non-adjustable quotas | Cannot be increased through the normal quota request process.      |
| Account-level quotas  | Apply to an AWS account.                                           |
| Resource-level quotas | Apply to an individual resource.                                   |
| Regional quotas       | Apply separately within an AWS Region.                             |
| Global quotas         | Apply across Regions, depending on the service.                    |

**Important:** Quota scope depends on the AWS service. Do not assume that a quota increase in one Region automatically applies to another Region.

## 3. Why Service Quotas Matter in Disaster Recovery

Consider an application deployed across two AWS Regions:

- Primary Region: us-east-1
- Standby Region: us-west-2

The primary Region handles normal production traffic, while the standby Region operates with reduced capacity.

When the primary Region fails, the standby Region must handle the entire production workload.

### Example scenario

| Resource                     | Primary Region | Standby Region |
| ---------------------------- | -------------- | -------------- |
| Required EC2 instances       | 20             | 20             |
| Available EC2 instance quota | 30             | 10             |
| Current running instances    | 20             | 2              |
| Required recovery capacity   | 20             | 20             |

**Problem:**

The standby Region has an EC2 quota of only 10 instances.

During failover, AWS cannot launch the required 20 instances because the standby Region's quota is insufficient.

Even though the infrastructure and application configuration are available, recovery can fail.

**Solution:**

Configure sufficient service quotas in both Regions before a disaster occurs.

The standby Region should have enough quota to support the expected recovery workload.

## 4. How to Configure Service Quotas for a Standby Environment

Follow these steps to prepare the standby Region.

### Step 1: Identify required AWS resources

List all AWS resources required to recover the production workload.

For example:

- Amazon EC2
- Amazon EBS
- Amazon VPC
- Elastic Load Balancing
- Amazon RDS
- Amazon EKS
- AWS Lambda

Identify the relevant quotas for each service.

### Step 2: Check quotas in both Regions

1. Open the AWS Management Console.
2. Navigate to **Service Quotas**.
3. Select AWS services.
4. Choose the required service.
5. Review the default quota and applied quota.
6. Repeat the process for the standby Region.

Compare the quota values between both Regions.

### Step 3: Calculate standby capacity requirements

Estimate the resources required to support the complete production workload during failover.

Example:

- Production EC2 requirement: 20 instances.
- Standby EC2 requirement: 20 instances.
- Additional capacity buffer: 20%.

Required standby capacity:

`20 × 1.20 = 24 instances`

Request a quota that accommodates the expected recovery capacity.

Consider other resource constraints, such as instance-family vCPU quotas, EBS volumes, IP addresses, and load balancer limits.

### Step 4: Request a quota increase

1. Open Service Quotas.
2. Select the standby Region.
3. Select the relevant AWS service.
4. Choose the quota that needs adjustment.
5. Select **Request increase**.
6. Enter the required quota value.
7. Submit the request.
8. Monitor the request status.

AWS may automatically approve smaller requests or review larger requests through Support.

**Important:** Request increases well before a disaster. Approval and implementation are not guaranteed to be immediate.

### Step 5: Configure CloudWatch alarms

Create CloudWatch alarms for supported service quotas.

Example monitoring thresholds:

- 70% utilization: Early warning.
- 80% utilization: Review capacity.
- 90% utilization: Take corrective action.

These are recommended operational thresholds, not mandatory AWS defaults.

CloudWatch alarms help identify potential quota exhaustion before it affects production.

### Step 6: Validate the standby environment

Perform regular DR tests to verify that the standby Region can:

- Launch the required EC2 instances.
- Scale Auto Scaling groups.
- Create or attach required storage.
- Scale database capacity.
- Handle production traffic.
- Support required network and load-balancing resources.

Do not rely only on matching quota values. Test actual recovery operations.

## 5. Understanding AWS API Throttling

AWS APIs have request-rate limits to protect services and maintain reliable performance.

When an application exceeds the allowed request rate, AWS may return throttling errors.

Examples:

- `ThrottlingException`
- `RequestLimitExceeded`
- `TooManyRequestsException`

The exact error depends on the AWS service and API.

### Example

An application sends 100 requests per second to an AWS API.

However, the API permits only 50 requests per second.

The additional requests may be throttled.

### Common causes

- Too many concurrent API requests.
- Excessive polling.
- Multiple applications using the same account-level quota.
- Sudden traffic spikes.
- Automated resource provisioning.

## 6. How to Handle AWS API Throttling

### A. Exponential Backoff

When AWS returns a throttling error, wait before retrying.

Increase the waiting time after each unsuccessful attempt.

Example:

| Attempt | Waiting time |
| ------- | ------------ |
| 1       | 1 second     |
| 2       | 2 seconds    |
| 3       | 4 seconds    |
| 4       | 8 seconds    |

### B. Add Jitter

Jitter introduces a random delay into retry intervals.

It prevents multiple applications from retrying simultaneously.

### C. Configure Retry Limits

- Set a maximum number of retries.
- Configure maximum retry delays.
- Set appropriate request timeouts.
- Avoid infinite retry loops.

AWS SDKs provide built-in retry functionality that can be configured.

### D. Reduce API Request Rates

If throttling happens frequently:

- Reduce unnecessary API calls.
- Implement caching.
- Avoid excessive polling.
- Use event-driven architectures where appropriate.
- Limit concurrent API requests.
- Use request batching when supported.

**Important:** Retries help applications recover from temporary throttling, but they do not solve consistently excessive API request rates.

## 7. AWS Architecture Example: Multi-Region DR

```
             Production Workload
                     |
              Route 53 / DNS
                     |
          -----------------------
          |                     |
     Primary Region        Standby Region
       us-east-1             us-west-2
          |                     |
     Application           Application
       Servers               Servers
          |                     |
      Amazon RDS          Standby Database
          |                     |
      Auto Scaling        Auto Scaling
          |                     |
    Normal Capacity      Recovery Capacity
          |                     |
    Quota Monitoring     Quota Monitoring
          |                     |
       CloudWatch           CloudWatch

          Both Regions:
       Sufficient Service Quotas
       DR Testing and Validation
       Throttling Protection
```

During normal operations, the primary Region handles production traffic.

If the primary Region becomes unavailable, traffic is redirected to the standby Region.

The standby Region must have sufficient quotas to launch and operate the complete recovery workload.

## 8. Amazon Application Recovery Controller (ARC)

AWS provides Amazon Application Recovery Controller (ARC) to help manage application recovery across Regions.

Its Region switch capability includes service quota checks.

### Service quota checks

- Compare applied quota values across accounts and Regions in a recovery plan.
- Identify quota mismatches between primary and standby Regions.
- Highlight cases where the standby Region has lower quotas.
- Help identify quota-related recovery risks.
- Support automatic quota increase requests for eligible mismatches.

New Region switch plans have service quota checks enabled by default.

**Important:** Quota parity does not guarantee successful recovery. Actual resource usage, concurrent recovery operations, and other constraints must also be considered.

## 9. Best Practices

1. Identify all relevant service quotas before deploying production workloads.
2. Maintain sufficient quota capacity in primary and standby Regions.
3. Monitor quota utilization using CloudWatch.
4. Request quota increases before reaching limits.
5. Review account-level and resource-level quotas.
6. Include quota validation in DR planning.
7. Implement exponential backoff with jitter.
8. Avoid unnecessary API requests.
9. Perform regular failover and recovery tests.
10. Review quota differences whenever production capacity changes.

## 10. SAA-C03 Exam Tips

| Exam scenario                                                     | Recommended solution                                              |
| ----------------------------------------------------------------- | ----------------------------------------------------------------- |
| Standby Region cannot launch enough EC2 instances                 | Request sufficient EC2 quota in the standby Region.               |
| Primary and standby Regions have different quotas                 | Review and align the required quotas.                             |
| AWS API requests are frequently throttled                         | Implement exponential backoff and jitter.                         |
| Quota utilization is approaching its limit                        | Configure CloudWatch alarms.                                      |
| DR recovery fails because of insufficient capacity                | Validate service quotas and resource constraints before failover. |
| Multiple applications generate excessive API requests             | Reduce request rates and control concurrency.                     |
| Need to identify quota mismatches in a multi-Region recovery plan | Consider AWS ARC Region switch service quota checks.              |

### Key Exam Takeaways

- Service quotas define the maximum permitted resource usage or operations.
- Quotas can be Regional, global, account-level, or resource-level.
- Increasing a quota in the primary Region does not necessarily increase it in the standby Region.
- Standby environments must have sufficient quotas for full recovery capacity.
- Exponential backoff and jitter help handle throttling.
- CloudWatch alarms help monitor quota utilization.
- AWS ARC Region switch can identify quota mismatches.
- Matching quotas alone do not guarantee successful disaster recovery.
