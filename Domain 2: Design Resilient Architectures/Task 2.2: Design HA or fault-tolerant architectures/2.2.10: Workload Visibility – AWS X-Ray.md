# Workload Visibility – AWS X-Ray

## 1. Introduction

**Workload Visibility** is the ability to understand how applications and their underlying infrastructure perform, communicate, and behave.

In AWS, workload visibility helps identify:

- Application performance bottlenecks.
- Slow database queries and API calls.
- Communication failures between microservices.
- Application errors and exceptions.
- High-latency requests.
- Dependencies between application components.

**AWS X-Ray** is an AWS service that collects and analyzes application request data. It helps developers and operations teams trace requests across distributed applications, identify performance issues, and troubleshoot errors.

Official documentation: [https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html](https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html)

## 2. What Is AWS X-Ray?

AWS X-Ray provides distributed tracing for applications running on AWS and other environments.

It tracks an application request from its starting point through different services and resources until the request is completed.

For example, consider an online banking application:

1. A customer sends a login request.
2. Amazon API Gateway receives the request.
3. An AWS Lambda function processes authentication.
4. The application queries Amazon RDS.
5. The database returns the result.
6. The application sends a response to the customer.

X-Ray helps visualize the complete request journey and identify which component causes delays or errors.

## 3. AWS X-Ray Architecture

### Basic Architecture

```
             End User
                 |
                 v
          API Gateway
                 |
                 v
          Application
          (EC2 / ECS)
                 |
          +------+------+
          |             |
          v             v
       Lambda        Amazon RDS
          |             |
          +------+------+
                 |
                 v
          Trace Collection
                 |
                 v
             AWS X-Ray
                 |
                 v
       CloudWatch Console
                 |
                 v
      Trace Map & Analysis
```

**Architecture explanation:**

- Application components generate tracing information.
- Instrumentation collects request and response details.
- AWS X-Ray receives trace information.
- X-Ray combines related information into traces.
- The trace map visualizes application components and dependencies.
- Engineers analyze traces to identify problems.

## 4. Core AWS X-Ray Concepts

### 4.1 Traces

A trace represents the complete journey of a single request through an application.

Example:

```
User Request
    |
    v
API Gateway
    |
    v
Application Service
    |
    v
Lambda Function
    |
    v
RDS Database
    |
    v
Response
```

A trace ID connects the different components involved in processing the same request.

**Purpose:**

- Understand end-to-end request processing.
- Identify slow services.
- Troubleshoot failed requests.

### 4.2 Segments

A segment represents the work performed by an instrumented application service while processing a request.

It can contain:

- Service information.
- Request details.
- Response information.
- Execution duration.
- Errors and exceptions.
- Subsegments.

Example:

```
Application Segment
    |
    +-- Request Information
    |
    +-- Response Information
    |
    +-- Execution Time
    |
    +-- Database Subsegment
    |
    +-- API Subsegment
```

### 4.3 Subsegments

Subsegments provide additional details about operations performed by an application.

Examples:

- Database queries.
- HTTP requests.
- Calls to AWS services.
- External API calls.

They help identify exactly which operation is causing performance problems.

### 4.4 Service Map / Trace Map

The X-Ray trace map provides a visual representation of application services and their dependencies.

It helps identify:

- Service relationships.
- High-latency connections.
- Failed requests.
- Application errors.
- Downstream dependencies.

The trace map uses different colors to indicate service health:

| Color  | Meaning                 |
| ------ | ----------------------- |
| Green  | Successful requests     |
| Red    | Server faults (5xx)     |
| Yellow | Client errors (4xx)     |
| Purple | Throttling errors (429) |

### 4.5 Sampling

Sampling determines which application requests are recorded as traces.

AWS X-Ray uses sampling to reduce the amount of trace data collected.

Default X-Ray SDK sampling configuration:

- Reservoir: 1 request per second.
- Fixed sampling rate: 5% of additional requests.

Sampling helps reduce unnecessary data collection and associated costs.

### 4.6 Annotations and Metadata

**Annotations**

- Indexed key-value pairs.
- Can be used to filter and search traces.
- Useful for identifying specific requests.

Example:

```
{
  "environment": "production",
  "customer_type": "premium"
}
```

**Metadata**

- Additional information attached to segments.
- Not indexed for filtering.
- Useful for debugging and investigation.

Use annotations for searchable information and metadata for additional diagnostic context.

## 6. How AWS X-Ray Works

The basic workflow is:

**Step 1: Instrument the application**

Configure application instrumentation to generate trace information.

**Step 2: Generate trace data**

When users access the application, tracing captures request information.

**Step 3: Collect segments**

Application components generate segments and subsegments.

**Step 4: Send trace data**

Trace information is sent to AWS X-Ray through supported instrumentation and collection components.

**Step 5: Analyze traces**

Use the AWS Console to examine:

- Trace IDs.
- Request duration.
- Service dependencies.
- Errors and exceptions.
- Performance bottlenecks.

**Step 6: Troubleshoot**

Identify the problematic service or operation and optimize the application.

## 7. AWS X-Ray Instrumentation

Instrumentation enables applications to generate tracing information.

There are three common approaches:

| Type                    | Description                                                          |
| ----------------------- | -------------------------------------------------------------------- |
| Auto instrumentation    | Automatically collects tracing information with minimal code changes |
| Library instrumentation | Uses supported libraries and frameworks to collect trace data        |
| Manual instrumentation  | Developers add custom tracing information to application code        |

### AWS Distro for OpenTelemetry (ADOT)

AWS Distro for OpenTelemetry is an AWS-supported distribution of OpenTelemetry.

It provides:

- Distributed tracing.
- Metrics collection.
- Automatic instrumentation.
- OpenTelemetry SDKs and collectors.
- Integration with AWS monitoring services.

ADOT can export tracing data to AWS X-Ray and other supported observability platforms.

## 8. AWS X-Ray and Amazon CloudWatch

AWS X-Ray and Amazon CloudWatch complement each other.

| Feature              | AWS X-Ray              | Amazon CloudWatch                      |
| -------------------- | ---------------------- | -------------------------------------- |
| Primary purpose      | Distributed tracing    | Monitoring and observability           |
| Request tracking     | Yes                    | Through integrations                   |
| Service dependencies | Trace map              | Application Signals service map        |
| Metrics              | Trace-related metrics  | Application and infrastructure metrics |
| Logs                 | Correlation with logs  | Log collection and analysis            |
| Troubleshooting      | Request-level analysis | Metrics, logs, alarms and traces       |

### CloudWatch Application Signals

CloudWatch Application Signals provides application performance monitoring.

It helps:

- Discover application services.
- Monitor service health.
- Track service-level objectives (SLOs).
- Visualize service dependencies.
- Correlate metrics, logs, and X-Ray traces.

**Important:** AWS now combines the X-Ray service map and CloudWatch ServiceLens map into the X-Ray trace map within the CloudWatch console.

## 9. Practical Example: Troubleshooting a Slow Application

Consider an e-commerce application experiencing slow checkout requests.

Architecture:

```
Customer
   |
   v
API Gateway
   |
   v
Order Service (EC2)
   |
   +------> Payment Service
   |
   +------> Inventory Service
   |
   +------> Amazon RDS
```

Problem: Checkout requests take 8 seconds to complete.

Using X-Ray:

1. Open the CloudWatch console.
2. Navigate to X-Ray Traces.
3. Open the Trace Map.
4. Identify the affected application service.
5. Select the service node.
6. Review request duration and error information.
7. Open an individual trace.
8. Examine its segment timeline.
9. Identify the slow database query or downstream service.
10. Optimize the problematic component.

Example findings:

| Component         | Response Time |
| ----------------- | ------------- |
| API Gateway       | 100 ms        |
| Order Service     | 200 ms        |
| Payment Service   | 300 ms        |
| Inventory Service | 400 ms        |
| RDS Database      | 7,000 ms      |

**Conclusion:** The database is the primary performance bottleneck.

## 10. Workload Visibility Best Practices

1. Instrument all important application services.
2. Implement distributed tracing across microservices.
3. Use appropriate sampling rules.
4. Monitor application latency and error rates.
5. Correlate metrics, logs, and traces.
6. Use annotations for searchable trace attributes.
7. Avoid exposing sensitive customer information in trace data.
8. Apply least-privilege IAM permissions for trace collection.
9. Monitor service dependencies and downstream calls.
10. Use CloudWatch Application Signals for service health and SLO monitoring.

## 11. AWS X-Ray vs CloudWatch vs CloudTrail

| Service           | Main Purpose                    | Example                                        |
| ----------------- | ------------------------------- | ---------------------------------------------- |
| AWS X-Ray         | Distributed application tracing | Find a slow database operation                 |
| Amazon CloudWatch | Monitoring and observability    | Monitor CPU utilization and application errors |
| AWS CloudTrail    | AWS account activity auditing   | Identify who modified an IAM policy            |

**Remember:**

- X-Ray = How does an application request flow?
- CloudWatch = How healthy is the application and infrastructure?
- CloudTrail = Who performed an AWS API action?

## 12. Important AWS Updates (2026)

AWS has transitioned toward OpenTelemetry as its primary application instrumentation standard.

Important dates:

| Date              | Change                                         |
| ----------------- | ---------------------------------------------- |
| February 25, 2026 | X-Ray SDKs and daemon entered maintenance mode |
| February 25, 2027 | X-Ray SDKs and daemon reach end of support     |

AWS recommends migrating existing X-Ray SDK-based instrumentation to OpenTelemetry.

Recommended technologies:

- AWS Distro for OpenTelemetry (ADOT).
- OpenTelemetry SDKs.
- OpenTelemetry Collector.
- CloudWatch Agent.
- CloudWatch Application Signals.

**Important distinction:** AWS X-Ray remains useful as a trace analysis and visualization service. The maintenance-mode announcement applies to the legacy X-Ray SDKs and daemon, not the entire X-Ray service.

### Common Exam Scenarios

**Scenario 1:** An application has multiple microservices, and you need to identify which service causes high latency.

Answer: AWS X-Ray.

**Scenario 2:** You need to visualize dependencies between application services.

Answer: AWS X-Ray Trace Map.

**Scenario 3:** You need to monitor EC2 CPU utilization and memory metrics.

Answer: Amazon CloudWatch.

**Scenario 4:** You need to identify who deleted an AWS resource.

Answer: AWS CloudTrail.

**Scenario 5:** You want standardized instrumentation across multiple cloud platforms.

Answer: OpenTelemetry / AWS Distro for OpenTelemetry.
