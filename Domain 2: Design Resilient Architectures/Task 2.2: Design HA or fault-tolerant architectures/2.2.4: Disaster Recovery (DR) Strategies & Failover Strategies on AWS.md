
# Disaster Recovery (DR) Strategies & Failover Strategies on AWS

## 1. Introduction to Disaster Recovery (DR)

**Disaster Recovery (DR)** is the process of preparing, recovering, and restoring IT infrastructure, applications, and data after an unexpected disruption.

Disasters may include:

- AWS Region or Availability Zone (AZ) failure.
- Hardware or infrastructure failure.
- Cyberattacks, ransomware, or data corruption.
- Accidental deletion of critical resources.
- Application failures or network outages.
- Natural disasters and power outages.

**Main objectives of DR:**

- Minimize application downtime.
- Minimize data loss.
- Maintain business continuity.
- Restore applications and infrastructure quickly.
- Ensure application availability during disasters.

AWS recommends defining recovery objectives, selecting an appropriate DR strategy, testing recovery procedures, managing configuration drift, and automating recovery.

## 2. Key DR Concepts: RTO and RPO

Two important metrics determine the effectiveness of a disaster recovery strategy.

### 2.1 Recovery Time Objective (RTO)

**RTO** is the maximum acceptable time required to restore an application or service after a disruption.

Example:

- Application failure occurs at 10:00 AM.
- Business requires service restoration within 2 hours.
- Maximum acceptable downtime = 2 hours.

### 2.2 Recovery Point Objective (RPO)

**RPO** is the maximum acceptable amount of data loss measured in time.

Example:

- Database backups run every 30 minutes.
- A disaster occurs at 10:00 AM.
- The latest recoverable backup is from 9:30 AM.
- Potential data loss = 30 minutes.

### RTO vs RPO

| Comparison        | RTO                          | RPO                       |
| ----------------- | ---------------------------- | ------------------------- |
| Full form         | Recovery Time Objective      | Recovery Point Objective  |
| Measures          | Downtime                     | Data loss                 |
| Focus             | How quickly service recovers | How much data can be lost |
| Lower value means | Faster recovery              | Less data loss            |
| Example           | 1 hour                       | 15 minutes                |

**Important:** RTO and RPO are business requirements, not guaranteed AWS service recovery times.

## 3. AWS Disaster Recovery Strategies

AWS describes four major DR strategies, arranged from lower cost and slower recovery to higher cost and faster recovery.

### 3.1 Backup and Restore

**Concept:** Back up application data and infrastructure configurations. When a disaster occurs, restore the resources in the recovery Region.

Architecture:

```
       Primary AWS Region
       ------------------
       EC2 Application
             |
       RDS Database
             |
       AWS Backup
             |
       Cross-Region Backup
             |
             v
       Recovery AWS Region
       --------------------
       Restore EC2
       Restore RDS
       Restore Application
             |
       Application Available
```

**AWS services:**

- AWS Backup
- Amazon S3
- Amazon EBS Snapshots
- Amazon RDS Snapshots
- AWS CloudFormation
- Amazon EC2

**Recovery process:**

1. Configure automated backups.
2. Copy backups to another AWS Region.
3. Maintain infrastructure templates.
4. Detect a disaster.
5. Restore databases and application resources.
6. Deploy application configurations.
7. Redirect traffic to the recovery environment.

**Advantages:**

- Lowest DR infrastructure cost.
- Simple implementation.
- Suitable for non-critical workloads.

**Disadvantages:**

- Longer recovery time.
- Potentially greater data loss.
- Requires infrastructure restoration.

**Use cases:** Development environments, internal applications, and non-critical business systems.

### 3.2 Pilot Light

**Concept:** Maintain a minimal version of the infrastructure in another Region. Critical components, especially databases and data replication, remain available.

When a disaster occurs, provision the remaining infrastructure and activate the recovery environment.

Architecture:

```
       Primary Region
       --------------
       Application (EC2)
             |
       RDS Database
             |
       Data Replication
             |
             v
       DR Region
       ---------
       Replicated Database
       Minimal Infrastructure
             |
       Disaster Occurs
             |
       Launch EC2 Resources
             |
       Activate Application
             |
       Redirect Traffic
```

**AWS services:**

- Amazon RDS Read Replicas
- Amazon S3 Cross-Region Replication
- Amazon EC2
- Amazon EBS
- AWS CloudFormation
- Amazon Route 53

**Recovery process:**

1. Replicate critical data to the DR Region.
2. Maintain minimal infrastructure.
3. Monitor replication health.
4. Launch additional EC2 instances when required.
5. Promote the database replica if necessary.
6. Validate the application.
7. Redirect production traffic.

**Advantages:**

- Faster recovery than backup and restore.
- Lower cost than maintaining a fully operational standby environment.
- Critical data is already replicated.

**Disadvantages:**

- Requires additional provisioning during recovery.
- Infrastructure deployment takes time.
- Requires synchronization between Regions.

**Use cases:** Business applications requiring moderate recovery speed at a controlled cost.

### 3.3 Warm Standby

**Concept:** Maintain a fully functional but smaller version of the production environment in another AWS Region.

The DR environment continuously runs and can handle limited traffic. During a disaster, scale up resources to support production workloads.

Architecture:

```
       Primary Region
       --------------
       Load Balancer
             |
       EC2 Application
             |
       RDS Database
             |
       Data Replication
             |
             v
       DR Region
       ---------
       Load Balancer
             |
       Smaller EC2 Fleet
             |
       Replicated Database
             |
       Disaster Occurs
             |
       Scale Up Resources
             |
       Redirect Traffic
```

**AWS services:**

- Amazon EC2 Auto Scaling
- Elastic Load Balancing
- Amazon RDS
- Amazon Route 53
- Amazon CloudWatch
- AWS CloudFormation

**Recovery process:**

1. Maintain a running application environment in the DR Region.
2. Replicate application data continuously.
3. Monitor application and database health.
4. Detect primary Region failure.
5. Scale up EC2 and other resources.
6. Promote database replicas if necessary.
7. Redirect traffic to the DR Region.

**Advantages:**

- Faster recovery than pilot light.
- Infrastructure is already operational.
- Supports rapid scaling.

**Disadvantages:**

- Higher operational cost.
- Requires continuous infrastructure maintenance.
- DR capacity may initially be insufficient for full production traffic.

**Use cases:** Business-critical applications, banking systems, and customer-facing services.

### 3.4 Multi-Site Active/Active

**Concept:** Run fully operational application environments in multiple AWS Regions simultaneously. Both Regions serve production traffic.

If one Region fails, the remaining healthy Region continues serving users.

Architecture:

```
              Users
                |
        Route 53 / Global
             Accelerator
                |
          Traffic Routing
           /          \
          v            v
     Region A        Region B
     --------        --------
     Application     Application
     EC2 / ECS       EC2 / ECS
          |               |
       Database        Database
          <------------>
       Data Synchronization
```

**AWS services:**

- Amazon Route 53
- AWS Global Accelerator
- Amazon EC2 / ECS / EKS
- Amazon Aurora Global Database
- Amazon DynamoDB Global Tables
- Amazon CloudWatch

**Recovery process:**

1. Deploy production workloads in multiple Regions.
2. Synchronize application data.
3. Distribute traffic across healthy Regions.
4. Monitor regional health.
5. Detect Region failure.
6. Stop routing traffic to the unhealthy Region.
7. Continue serving requests from healthy Regions.

**Advantages:**

- Very low recovery time.
- Minimal data loss when data synchronization is properly designed.
- Both Regions actively serve traffic.
- High availability and resilience.

**Disadvantages:**

- Highest infrastructure cost.
- Complex architecture and data synchronization.
- Requires conflict resolution for concurrent writes.
- More complex operational management.

**Use cases:** Global applications, financial services, large-scale e-commerce, and mission-critical systems.

## 4. Comparison of AWS DR Strategies

| Strategy                 | RTO                      | RPO                | Cost      | Recovery Speed |
| ------------------------ | ------------------------ | ------------------ | --------- | -------------- |
| Backup and Restore       | Hours                    | Hours              | Low       | Slow           |
| Pilot Light              | Tens of minutes to hours | Minutes            | Medium    | Moderate       |
| Warm Standby             | Minutes                  | Seconds to minutes | High      | Fast           |
| Multi-Site Active/Active | Seconds                  | Near zero          | Very High | Fastest        |

*Note: These are indicative planning ranges, not AWS guarantees. Actual RTO/RPO depend on workload architecture, replication, data volume, and recovery procedures.*

## 5. Failover Strategies on AWS

### 5.1 What is Failover?

**Failover** is the process of switching application traffic from an unhealthy primary environment to a healthy secondary environment.

Example:

```
Normal Operation:

Users
  |
  v
Primary Region (Healthy)
  |
Application Available


Disaster Scenario:

Users
  |
  v
Failover Mechanism
  |
  v
DR Region (Healthy)
  |
Application Available
```

### 5.2 Types of Failover

**A. Automatic Failover**

The system automatically detects failures and switches to a standby resource.

Examples:

- Amazon RDS Multi-AZ automatic failover.
- Route 53 health-check-based DNS failover.
- Elastic Load Balancing health checks.

**B. Manual Failover**

An administrator initiates the failover after verifying the disaster.

Examples:

- Manually promoting an RDS Read Replica.
- Initiating AWS Elastic Disaster Recovery.
- Changing traffic routing through AWS Application Recovery Controller (ARC).

**C. Active/Passive Failover**

- Primary environment handles production traffic.
- Secondary environment remains on standby.
- Secondary takes over when the primary fails.

**D. Active/Active Failover**

- Multiple environments serve production traffic simultaneously.
- Traffic is routed to healthy environments.
- Failed environments are removed from traffic distribution.

## 7. Database Failover: Amazon RDS Example

Amazon RDS Multi-AZ provides automatic database failover.

```
             Application
                  |
                  |
           RDS Endpoint
                  |
             Primary DB
             (AZ-A)
                  |
          Synchronous
            Replication
                  |
             Standby DB
             (AZ-B)

       Primary DB Failure
                  |
                  v
       Standby Promoted
          to Primary
                  |
                  v
       RDS DNS Endpoint
          Updated
                  |
                  v
       Application Reconnects
```

**Key points:**

- RDS automatically detects certain primary database failures.
- The standby database is promoted.
- The database endpoint is updated through DNS.
- Applications must reconnect using the endpoint.
- Existing connections may be interrupted during failover.

For standard RDS Multi-AZ DB instance deployments, failover typically takes 60–120 seconds. Multi-AZ DB clusters have different failover characteristics.

## 8. Disaster Recovery Best Practices

1. **Define RTO and RPO:** Establish recovery requirements based on business impact.
2. **Use Multi-AZ architecture:** Protect against Availability Zone failures.
3. **Implement Cross-Region DR:** Protect against regional disasters when required.
4. **Automate Backups:** Use AWS Backup and automated snapshot policies.
5. **Replicate Critical Data:** Use appropriate database replication and S3 Cross-Region Replication.
6. **Automate Infrastructure:** Use Terraform or AWS CloudFormation.
7. **Monitor Infrastructure:** Use CloudWatch alarms and health checks.
8. **Test DR Regularly:** Perform recovery drills and failover exercises.
9. **Manage Configuration Drift:** Keep primary and recovery environments synchronized.
10. **Document Recovery Procedures:** Maintain an operational DR runbook.
11. **Plan Failback:** Define how to return workloads to the original environment after disaster recovery.

## 9. DR Testing and Recovery Process

A complete DR plan should include:

```
Identify Disaster
       |
       v
Assess Business Impact
       |
       v
Initiate DR Procedure
       |
       v
Recover Infrastructure
       |
       v
Restore / Promote Database
       |
       v

       |
       v
Redirect Production Traffic
       |
       v
Monitor Recovery Environment
       |
       v

```

**Important:** AWS recommends regularly testing DR implementations to validate actual recovery capabilities against RTO and RPO objectives.

## 10. SAA-C03 Exam Tips

| Exam Scenario                                             | Recommended Solution                |
| --------------------------------------------------------- | ----------------------------------- |
| Lowest-cost DR strategy                                   | Backup and Restore                  |
| Faster recovery with minimal infrastructure               | Pilot Light                         |
| Running but reduced-capacity DR environment               | Warm Standby                        |
| Both Regions serve production traffic                     | Multi-Site Active/Active            |
| Automatic database failover within an AZ failure scenario | RDS Multi-AZ                        |
| Database replication for regional recovery                | Cross-Region Read Replica           |
| DNS-based regional failover                               | Route 53 Failover Routing           |
| Static IP-based regional traffic routing                  | AWS Global Accelerator              |
| Server replication and recovery to AWS                    | AWS Elastic Disaster Recovery       |
| Centralized backup management                             | AWS Backup                          |
| Controlled recovery and routing operations                | AWS Application Recovery Controller |

### Important Exam Distinctions

- **High Availability (HA)** protects against component or Availability Zone failures.
- **Disaster Recovery (DR)** focuses on restoring workloads after major disruptions.
- Multi-AZ does not automatically provide protection against an entire Region failure.
- Replication alone is not a substitute for backups. Replicated corruption or accidental deletion can also affect recovery data.
- AWS Elastic Disaster Recovery launches recovery instances, but production traffic failover must be handled separately.
- Automatic failover is not always the best option; false-positive health checks can cause unnecessary disruption.
- Always select a DR strategy based on RTO, RPO, cost, and business requirements.
